# Windows service lab

## Disposable Hyper-V VM

Run issue #23 end-to-end in a fresh, network-disconnected VM:

```powershell
powershell -File test/windows-service-lab/lab-vm.ps1 -Build
```

The script creates a differencing disk from the read-only Windows Server 2025 golden image, waits for PowerShell Direct, runs the existing lab, prints the result and rollback summaries, and deletes only the verified disposable VM and child VHDX. The run also starts the real Approval Authority service (`build:approval-authority`; `-Build` runs it) against signing keys that `new-authority-key.ps1` creates in the guest: checks `k_*` expect a good key to start, an exportable key and a key with an extra Everyone ACE to be refused with service exit code 78, and a missing key to end with 77. Checks `m1` to `m4` (issue #84) run the real Broker service against journals of its own: generation advance and refusal (1066 / 76), migration of a version 2 journal (the fixture comes from `lab-inputs.json`, generated on the host), an `inspect` that writes nothing, and a restore of a stopped service's journal followed by a replay. Checks `p1` to `p6` (issue #115 step 3a) run the same Authority service against its tier policy file, `policy.json`, in the Authority's own config folder: no file starts as careful (the approver pipe says rev 0), a config folder that `BUILTIN\Users` can write is refused (1066 / 73), an unsigned `standard` file is refused (1066 / 79), the running service writes `policy.json` itself when the approver pipe sends a `policy_set` that only adds a prompt (no signature needed), a restart reads that file back, and an unsigned `policy_set` that would loosen the policy is refused. A correctly signed `standard` policy cannot be made in the VM (it needs a real Windows Hello signature), so that direction stays host-tested. Clock rollback is deliberately NOT in the lab: it needs the test-only clock offset, which the published Broker does not contain; it is host-tested. Use `-KeepVm` for investigation, or override `-VmName`, `-PasswordFile`, and `-EvidenceDir` as needed. Exit codes are 0 for no failures, 1 for one or more failed checks, and 2 for setup or cleanup errors.

## Nested Hyper-V rights check (`-HyperV`)

ADR-002 puts the room's VM operations in a privileged Windows Broker (virtual account `NT SERVICE\AlberaHostBroker`, restricted service SID, `SeChangeNotifyPrivilege` only) whose SID is a member of Hyper-V Administrators. This mode measures whether a service of that shape may call the two Hyper-V WMI operations the Broker will own: a screen capture (`GetVirtualSystemThumbnailImage`) and input (`Msvm_Keyboard`, `Msvm_SyntheticMouse`). It is a different lab from the default one and from `-HostInstall`; pick one.

```powershell
powershell -File test/windows-service-lab/lab-vm.ps1 -HyperV -Build
```

Before running: the lab VM is 5 GB (the free-memory guard asks for 9 GB free: 5 GB VM + 4 GB headroom), so check the host first. The host is changed in no other way than creating and deleting this one VM; nested virtualization is switched on for that VM only.

What it does:

1. Creates the usual differencing-disk VM, offline, with `Set-VMProcessor -ExposeVirtualizationExtensions $true` while it is still off.
2. In the guest, `Install-WindowsFeature Hyper-V -IncludeManagementTools`, then restarts the guest and reconnects PowerShell Direct (up to 20 minutes, by comparing the boot time).
3. Makes an inner VM (Gen2, 512 MB fixed, no disk, no network). It stays at the UEFI screen, which is enough to capture and to type at.
4. Runs `albera-lab-service-shim.exe hyperv <inner VM GUID>` as four virtual-account services, each with `sc privs SeChangeNotifyPrivilege`: restricted or unrestricted service SID, each member of Hyper-V Administrators (`S-1-5-32-578`) or not. The probe (`HyperVProbe.cs`) uses COM late binding on `WbemScripting.SWbemLocator` in its own process, which is how the C# Broker will call WMI. It also runs the Broker's real Hyper-V desktop adapter (`HyperVDesktop` with `ComWmiConnection` from `src/runtime/windows-broker`, compiled into the shim by source include; PR #161) for `adapter_capture` (a 640x480 capture that must come back as a PNG with a valid signature, IHDR and IEND) and `adapter_input` (one move, one tap of Shift, one press and release of mouse button 1). Every WMI result is read through `Properties_.Item(...).Value`, never by property name (a by-name read made every later call in the process fail with `0x80004005`, which is what the first run saw for the keyboard and the mouse). Each service's token is read back first (`hv_<identity>_token`); a token that is not the cell's shape makes that cell BLOCKED, not a quiet pass.
5. Writes `hyperv-results.json` and `lab-output.txt` in the evidence folder and prints the table. The VM and its disk are deleted as in the other modes (`-KeepVm` also removes the lab services, group memberships and the inner VM inside the guest).

Checks are `hv_prereq_role`, `hv_prereq_inner_vm`, then for each identity (`r_member`, `r_nonmember`, `u_member`, `u_nonmember`) `hv_<identity>_token` and `hv_<identity>_<operation>` for `wmi_connect`, `vm_lookup`, `mgmt_read`, `thumbnail`, `keyboard_typekey`, `mouse_setabsoluteposition`, `adapter_capture` and `adapter_input`:

| Identity | `wmi_connect`, `vm_lookup` | `thumbnail`, `keyboard_typekey`, `mouse_setabsoluteposition`, `adapter_capture`, `adapter_input` | `mgmt_read` (read only; the Broker never calls it) |
|---|---|---|---|
| unrestricted, member | PASS if allowed | PASS if allowed | MEASURED |
| restricted, member | MEASURED | MEASURED (allowed or denied; either answer is the result) | MEASURED |
| restricted or unrestricted, not a member | MEASURED | PASS if refused (access denied, or the VM is not visible); FAIL if allowed | MEASURED |

Status values: PASS, FAIL, BLOCKED (could not be measured: wrong token shape, no probe output, an error that is not about access), MEASURED (the observation is recorded as the result). Exit code 0 means no FAIL and no BLOCKED; 1 means either; 2 is a setup or cleanup error. If the restricted member row says `denied`, the decision to fall back to `sidtype unrestricted` is the shareholder's, not this lab's. The adapter hides why it failed (one reason word), so an `adapter_*` failure counts as refused only when the raw check of the same operation (`thumbnail`; `keyboard_typekey` or `mouse_setabsoluteposition`) was refused in the same run; otherwise it is an error (BLOCKED), including a capture that is not a valid PNG. A "not found" from the probe itself (`management_service_not_found` and the like: the object is hidden from that caller) counts as not visible. The `adapter_*` operations and the property-reading fix have not been run in a VM yet; the logic is covered by `hyperv-rights-checks.test.mjs`, and the probe's COM calls were run once on a development host against a VM GUID that does not exist (connect and read worked; every VM call said not found).

### The Broker desktop pipe, as the real service (checks `bd_*`, after the four identities)

The same `-HyperV` run then installs the REAL Broker as it will be installed and uses its desktop pipe (Broker PR #164, ADR-002 "Amendment 2026-11-03"). It needs the Broker build, the Control Plane pipe client (`npm run build:windows-broker` makes both) and the shim (`-Build` makes all of them; without `-Build` the driver checks for them before it creates the VM). The Broker publish folder is copied to `bin\broker` in the guest, the pipe client's to `bin\helper`. Three services, all virtual accounts with `SeChangeNotifyPrivilege` as the only privilege:

| Service | Shape | Role |
|---|---|---|
| `AlberaHostBroker` (fixed: the Broker derives the service SID it trusts from this name) | sidtype `unrestricted`, member of Hyper-V Administrators; config `computers` = the inner VM's GUID | `albera-windows-broker.exe service <config>` |
| `AlberaLabHvCP` | sidtype `restricted`, no group; its SID is the Broker's `controlPlaneSid`; it may query the Broker service status (as the Control Plane may) | the Control Plane |
| `AlberaLabHvOther` | same shape as the Broker (unrestricted, member), but not the Control Plane | "somebody else" |

The two callers run `albera-lab-service-shim.exe desktop <pipe> <identity> <step>...` (`DesktopClient.cs`), the lab's own small client, kept for the checks that need to see the Broker's raw frames (a refusal at the pipe, a closed connection, the session ended by a newer claim). The Control Plane's real client is the pipe client helper in desktop mode; the `bh_*` checks below go through that. This client keeps the helper's rules for knowing who answers (pipe opened with exactly `0x00120083` at SECURITY_IDENTIFICATION; owner SID, server PID and, for a service, session 0 are checked on the connected handle before a byte is sent). The Control Plane finds the PID through the SCM (`service:AlberaHostBroker`); the other caller may not query the service, so it is given PID and owner SID (`pid:<pid>:<sid>`). Steps are `open:<view|act>:<computerId>` (an act open names its lease: `open:act:<computerId>:<operationId>:<leaseGeneration>`), `capture:<w>x<h>`, `input:<op>=<n>[,<n>][+<op>...]`, `claim` and `end:<ms>` (see the header of `DesktopClient.cs`); the first PNG is saved (`save=`) and the driver brings it back as `bd-view-capture.png` next to `hyperv-results.json`, so a person can look at the inner VM's screen.

| Check | PASS when | Not PASS |
|---|---|---|
| `bd_prereq_broker` | the Broker build is in the guest | BLOCKED |
| `bd_broker_ready` | the service reaches RUNNING (the Broker reports RUNNING only after the pipes exist) | FAIL, with the service exit codes; every later check is BLOCKED |
| `bd_broker_token` | the live Broker token (read as Administrator with `token-of <pid>`): user = its service SID, no restricting SIDs, Hyper-V Administrators enabled, exactly `SeChangeNotifyPrivilege` | FAIL on another shape; BLOCKED if the token cannot be read |
| `bd_cp_token` | restricted, Hyper-V Administrators absent, exactly `SeChangeNotifyPrivilege` | FAIL |
| `bd_other_token` | unrestricted, Hyper-V Administrators enabled, exactly `SeChangeNotifyPrivilege` (so its refusal is not for want of the group) | BLOCKED (the other results are then not used) |
| `bd_desktop_pipe` | the Control Plane opens `<pipeName>_desktop`: owner = Broker SID, ACEs only for the Broker (and SYSTEM) plus exactly one Control Plane ACE `0x120083`, served by the Broker's PID in session 0 | FAIL |
| `bd_cp_view_open` | a `view` open from the Control Plane is answered `{"ok":true}` | FAIL if refused; BLOCKED if no session could be made |
| `bd_cp_view_capture` | a 640x480 capture returns a header for that size and one PNG frame of exactly `bytes` bytes with a valid signature, IHDR of that size, 8-bit truecolour and IEND | FAIL (denied, or a PNG that is not valid); BLOCKED if the connection broke without a reply |
| `bd_other_refused` | the other caller gets no session: the pipe's DACL refuses the open (access denied), or the Broker answers the fixed `denied` frame. The evidence says which layer. | FAIL if a session opens; BLOCKED if it could not be measured |
| `bd_cp_act_before_claim_refused` | the Control Plane connects and an `act` open for operation `lab-bd-act-1`, generation 1 is answered with the fixed `denied` frame: nothing has been claimed, so the Broker holds no lease. A closed pipe without that frame is not a pass. | FAIL if accepted; BLOCKED otherwise |
| `bd_cp_task_start_claim` | the Control Plane's fence reply is used to sign a receipt v2 (`guest.command` / `task.start`, DTO `{task}`, project `lab-project`, computer `lab-room`, operation `lab-bd-act-1`) and the helper sends it with its action DTO: `{"ok":true,"state":"UNKNOWN","action":"task.start"}`, not a replay | FAIL if the Broker refuses it (the evidence has its fixed reply); BLOCKED if the fence or the helper gave no usable reply, or the helper is not in the guest. If this is not PASS, the six checks below are BLOCKED |
| `bd_cp_act_open` | the open that was refused before the claim (`lab-bd-act-1`, generation 1) is accepted | FAIL if refused |
| `bd_cp_act_input` | in that session one `input` request, `tap` of VK 16 (Shift), is answered `{"ok":true}` | FAIL if refused (the Broker answers the same `denied` for a lease, a shape, a limit or an adapter failure; its own log would say which) |
| `bd_cp_act_input_mouse` | **MEASURED, never PASS or FAIL.** The same session, one request: `move 100,100`, button 1 `down`, button 1 `up`. The inner VM has no OS, so the synthetic mouse call is known to fail (32768, as measured in the previous lab run); the Broker then answers `denied` and ends the session, which is the expected observation (`refused_reply`). `allowed` would mean the mouse worked | BLOCKED if the keyboard request did not go through (the mouse request is then not sent) or no answer came |
| `bd_cp_act_wrong_generation_refused` | an act open for `lab-bd-act-1` with generation 2 (the lease is generation 1) is answered `denied` | FAIL if accepted |
| `bd_cp_act_revoked_by_new_claim` | one client process holds an act session on `lab-bd-act-1` open, makes the second claim (`lab-bd-act-2`) through the helper as a child of the same process, and then waits up to 15 s without sending: the Broker ends the first session with its `denied` frame | FAIL if the claim went through and the session is still open after 15 s, or answered something else; BLOCKED if no session was held, or the second claim did not go through |
| `bd_broker_restart_drops_lease` | the second lease (`lab-bd-act-2`, generation 2) opens an act session; then the Broker service is stopped and started, and the very same open is answered `denied`: the lease lived in memory only | FAIL if it is accepted after the restart; BLOCKED if it was not accepted before (the refusal after would prove nothing), or the Broker did not come back |

How a claim is made in the guest: the lab script creates an ECDSA P-256 key in the guest (`New-LabAuthority`, an ephemeral CNG key: never exported, never written, gone with the script process). Its public half is pinned in the Broker's config (`authorityKeys`, kid `lab-hv-authority-1`); its private half signs the receipts. The Control Plane service runs the helper (`bin\helper\albera-windows-broker-pipe-client.exe`, with the Broker found by service name) for the fence, then `New-LabTaskStartReceipt` builds the receipt (action digest v1 computed in PowerShell, SHA-256 over the contract's canonical encoding; lease id and policy version are the config's; iat now, 240 s) and signs it, and the helper sends it as the three-key claim. Nothing of this touches the host, and no key material comes from the host. Each Control Plane job is one service start, so the second claim in `bd_cp_act_revoked_by_new_claim` is sent by the `claim` step of the client that holds the session (a second job could not run while the first holds the one Control Plane service).

Mouse input in an inner VM that has no OS: the observation is recorded by `bd_cp_act_input_mouse`. Only keyboard input decides `bd_cp_act_input`. A guest with a real OS inside the inner VM would make the mouse request succeed, and the check would then record `allowed` as its measurement.

Not covered here: the Broker's per-connection peer check (thread token user SID = the Control Plane SID) is only reached by a caller the pipe DACL lets through, and the DACL lets through nobody else; it is host-tested (`test/runtime-windows-broker-desktop-pipe.test.mjs`). The Broker's own log (`DESKTOP_DENY=<reason>`) is not collected from the service, so a refusal is told apart by its layer, not by the Broker's reason word. The `input` replies cannot say why a request was refused (a lease, a shape, a limit, the adapter), so the input checks name what was sent and what came back, not the cause.

### The same Broker through the REAL pipe client helper (checks `bh_*`, PR #168)

The `bd_*` checks above use the lab's own client. Before #168 (the helper's `desktop` mode and `src/runtime/windows-desktop-broker-client.mjs`) is merged, the lab must show that the real helper, running as the Control Plane service, reaches a Broker that runs as a service. The guest has no Node, so the shim plays the Node client: `albera-lab-service-shim.exe desktop-helper <helperExe> <desktopPipe> <identity> <step>... [image=<sha256>] [save=<path>]` (`DesktopHelperClient.cs`). It checks the helper against the SHA-256 manifest next to it (as the Node client does before every launch), starts it with the argument `desktop`, sends the start frame (pipe name, timeouts, `expect`, `open`), then one request frame at a time (`capture`, `input`), and reads the frames back; the frames are the ones in `DesktopSession.cs` and `windows-desktop-broker-client.mjs`. The PNG is checked again by the shim. An act open may leave the generation out (`open:act:<computerId>:<operationId>`, the room's form since #170); the Broker then joins the current lease of the operation, and the accepted answer must be `{"ok":true,"leaseGeneration":n}` (the shim reports `joinedGeneration` and refuses a bare `{"ok":true}`, a generation that is not a lease, or one other than the named). The helper, not the lab, opens the pipe and decides who the server is. The identity is `service:AlberaHostBroker` (serviceName mode: the SCM PID, the `NT SERVICE` owner, session 0) **without** `imageSha256`. The `bd_*` checks are all kept as they are (they cover what the helper hides: which layer refused, a connection that ended on its own, the session ended by a newer claim, which the helper does not see because it reads the pipe only while a request is in flight).

**Decision 2026-11-03 (provisional): the Control Plane uses serviceName mode and does not pin the image.** The first run of this lab (evidence: `docs/architecture/benchmarks/broker-desktop-helper-lab-2026-11-03.json`, 41 PASS / 4 FAIL / 3 BLOCKED / 17 MEASURED) pinned `imageSha256` = the Broker file's hash. The Control Plane service may not open the Broker process (every `OpenProcess` mask `denied`, also `PROCESS_QUERY_LIMITED_INFORMATION`; the earlier service lab said the same), so the helper cannot hash the image and every pinned open ended in `server_identity_unavailable` (helper exit 70, before anything was sent). The same sessions without the pin passed: view open, a 640x480 PNG (21687 bytes, valid), act open and keyboard input; both squatter checks passed. The checks were then reduced to the shape below. That run used the earlier ids (`bh_cp_image_readable`, `bh_view_service_only`, `bh_act_service_only`, `bh_wrong_image_refused`, and the pinned `bh_view_*` / `bh_act_*`); the benchmark file keeps them. A wrong pin is refused with `server_identity_mismatch` when the image can be read: that is covered on a host with the real Broker (`desktop-helper-client.test.mjs`), not in the VM.

| Check | PASS when | Not PASS |
|---|---|---|
| `bh_view_open` | helper, serviceName mode, no pin: a `view` open on the inner VM is accepted | FAIL if refused (the evidence has the helper's code: `server_identity_unavailable` = the SCM or the image could not be read; `server_identity_mismatch` = the wrong process answered; `denied` = the Broker refused); BLOCKED if the helper did not start or the pipe was not there |
| `bh_view_capture` | the same session: a 640x480 capture returns a header for that size and one PNG frame of exactly `bytes` bytes with a valid signature, IHDR of that size and IEND | FAIL (denied, or a PNG that is not valid); BLOCKED if the connection broke without a reply |
| `bh_act_open` | after the lab's `task.start` claim (`bd_cp_task_start_claim`), the helper's act open for `lab-bd-act-1` **that names no generation** (`open:act:<computerId>:<operationId>`, as the room does; PR #170) is accepted, and the answer `{"ok":true,"leaseGeneration":n}` names generation 1, the lease it joined (`joinedGeneration` in the evidence) | FAIL if refused, or accepted with another generation; BLOCKED when no claim was recorded (like the `bd_cp_act_*` checks) |
| `bh_act_input` | in that session one `input` request, `tap` of VK 16 (Shift), is answered `{"ok":true}` | FAIL if refused |
| `bh_act_wrong_generation_refused` | an act open for `lab-bd-act-1` that **names** generation 2 (the lease is generation 1) is answered `denied` by the Broker, through the helper. A refusal needs a named generation; an open without one always joins | FAIL if accepted; BLOCKED when no claim was recorded |
| `bh_image_pin_unavailable` | **MEASURED, never PASS or FAIL.** The same view open with `imageSha256` = the Broker file's hash. Expected: `identity_unavailable` (the Control Plane cannot read the Broker image). The evidence also has `openproc` as the Control Plane on the Broker PID (the cause). `allowed` would mean the pin works from this identity | BLOCKED if there was no answer (helper not started, no pipe, a timeout) |
| `bh_squatter_broker_stopped` | the Broker service is stopped and `AlberaLabHvOther` (a different identity) holds `<pipeName>_desktop` with the `squat` probe. The helper in serviceName mode ends with `server_identity_unavailable` (the SCM has no running Broker, so it cannot even say who it expects; `server_identity_mismatch` also counts) and the squatter reports no byte | FAIL if the squatter received a byte, or the session opened; BLOCKED if the squatter was never in place (no `ready` line) or the helper gave no usable answer |
| `bh_squatter_owner_mismatch` | the same state; the helper is given the Broker's old PID and owner SID (`pid:<pid>:<sid>`). It connects to the squatter, finds another owner and ends with `server_identity_mismatch` before it writes; the squat probe reports `connected: true` and `bytesReceived: 0` | FAIL if a byte arrived; BLOCKED if the helper never connected (no `done` line with `connected`) or ended with another code |

Order in the run: the view checks and `bh_image_pin_unavailable` come after `bd_other_refused` and need no lease; the act checks run on the lease of the first claim, after `bd_cp_act_wrong_generation_refused` and before the second claim replaces it; the squatters are last because they stop the Broker. Each helper session ends by closing the shim's stdin; the `close` line in the evidence has the helper's exit code (0 expected for a session that was accepted; 70 when the helper ended on an identity it could not establish) and the number of bytes it said that nobody asked for (0 expected). If the helper file is not in the guest all `bh_*` checks are BLOCKED; if its manifest does not match the file the shim does not start it (`helper_unavailable`).

The logic of these checks is covered without a VM: `broker-desktop-checks.test.mjs` (what the guest script installs and asks; the verdict functions on made-up client lines, for both clients; the throwaway authority key and the receipt it signs, checked against the contract's digest, signature and validator), `desktop-client.test.mjs` (the lab client against a scripted Broker; against the real service loop; and the whole lease flow of the lab, with the lab script's own receipt functions and the real pipe client helper, against the real Broker service loop with a test key and no VM) and `desktop-helper-client.test.mjs` (the `desktop-helper` probe with the real helper: against a scripted Broker, against hostile same-user servers that must receive no byte, and against the real Broker service loop, including the image pin, a wrong pin and the lease flow; on a host the PID and owner are given, the service identity is covered by the lab). The `bd_*` checks and the first version of the `bh_*` checks ran once in a VM (2026-11-03, the benchmark file above); the `bh_*` set as described here (serviceName mode, no pin) has not run in a VM yet.

## Control Plane as a virtual-account service (`-ControlPlaneService`)

Easy setup, stage 1 moves the Control Plane from an ordinary user to a service under a virtual account: `NT SERVICE\AlberaControlPlane` (ADR-002 "Process and identity contract"), sidtype `restricted`, `SeChangeNotifyPrivilege` as its only privilege. Before that is designed, this mode measures what the Control Plane needs, as that very identity. It is a different lab from the default one, `-HostInstall` and `-HyperV`; pick one. The guest is the usual offline Windows Server 2025 VM (4 GB, no Hyper-V role, no reboot).

```powershell
powershell -File test/windows-service-lab/lab-vm.ps1 -ControlPlaneService -Build
```

Status: **not run in a VM yet.** The probes (`ControlPlaneProbe.cs`, `cp-node-probe.mjs`) and the verdict logic are covered on the host by `control-plane-service-checks.test.mjs`; what only the VM shows is how the service identity answers. Expect first-run fixes.

What it does:

1. Creates the usual differencing-disk VM, offline, and waits for PowerShell Direct.
2. Copies the lab shim, the pipe client helper (`npm run build:windows-broker` makes it; `-Build` runs that and the shim build), `cp-node-probe.mjs` and `lab-person.ps1` into `C:\albera-cp-lab`. The Approval Authority and the Broker service are not used.
3. Makes sure `C:\Program Files\nodejs\node.exe` exists (next section).
4. Runs `lab-control-plane-service.ps1` in the guest. It installs three stand-in services: `AlberaControlPlane` (the real name; restricted, `SeChangeNotifyPrivilege` only), `AlberaLabCpOther` (another virtual account of the same shape) and a "shareholder" stand-in, a plain local user in `BUILTIN\Users` that `lab-person.ps1` creates and runs as a service (`AlberaLabHolder`). Each probe runs as the child of the lab shim, which is the service, so it carries the service's own token. Nothing joins any group.
5. Writes `control-plane-service-results.json` and `lab-output.txt` in the evidence folder and prints the table. The VM and its disk are deleted as in the other modes (`-KeepVm` also removes the services, the user, the ProgramData folder and the lab root inside the guest).

### Node in the guest

The Control Plane is a Node program, so the guest needs `node.exe` where a real install puts it. The golden image probably has none. The driver asks the guest first (`Test-Path 'C:\Program Files\nodejs\node.exe'`); if it is there nothing is copied (`nodeSource` = `golden`). If not, it copies **the host's own `node.exe`** (`-HostNodeExe`, default `%ProgramFiles%\nodejs\node.exe`): one file read on the host, **nothing is downloaded**. Before it copies, the driver requires a Node version of 22.13 or newer (`node:sqlite` without a flag; the repo's `engines`), a valid Authenticode signature, and after the copy a guest SHA-256 equal to the host's. The version, size, hash and signer are printed and recorded as `nodeSource` = `copied_from_host:<version>:<sha256>:<bytes>`. `node.exe` is a single self-contained file (the npm folders are not needed). The copy goes through PowerShell Direct (about 90 MB).

### The checks

Every check has an `id`, a status (PASS, FAIL, BLOCKED, MEASURED), an observed value and the lines it was read from. `expected` is what the lab's author expects; the driver's exit code is 0 only when every status equals its `expected`, 1 otherwise (including a FAIL, which is the useful finding), 2 for a setup or cleanup error.

| Id | Item | PASS when | Expected | Not PASS |
|---|---|---|---|---|
| `cp0_token` | the identity is what ADR-002 names | the live token (read by the shim at the service start): user = the service SID, restricting SIDs present, `Administrators` and `Hyper-V Administrators` absent or deny-only, exactly `SeChangeNotifyPrivilege` | PASS | FAIL; every later check is then BLOCKED (`token_shape_not_as_intended`) |
| `cp1_node_sqlite` | 1. node + `node:sqlite` | the shim starts `node.exe cp-node-probe.mjs <folder>` as the service's child; it opens a journal as `src/runtime/sqlite-operation-store.mjs` does (WAL, `synchronous = FULL`, `quick_check`), writes a row in a transaction, closes, reopens and reads the row back | PASS | FAIL (node gave no answer, or failed at the step the line names); BLOCKED if node.exe is not in the guest or the job could not be started |
| `cp2_pipe_client_helper` | 2. the pipe client helper | the helper starts as the service's child twice, once with `expect:{ownerSid,pid}` and once with `expect:{serviceName:"AlberaControlPlane"}` (SCM and account lookup under this token), and both end with `{ok:false,code:"broker_unavailable"}`: it started, read its input and reached the pipe open, where no Broker pipe exists | PASS | FAIL (no answer, or another code such as `server_identity_unavailable`); BLOCKED if the job could not be started |
| `cp3_dpapi_currentuser` | 3. DPAPI | CurrentUser scope (no `LOCAL_MACHINE`) with entropy: Protect then Unprotect gives the plaintext back, and the same blob with other entropy is refused. It goes through crypt32 (`CryptProtectData`), the call `ProtectedData.Protect` makes, because `ProtectedData` is a NuGet package and the lab tool is BCL only. The plaintext is never printed, only its SHA-256 | PASS | FAIL (with the Win32 error) |
| `cp3_profile` | 3. the profile | **MEASURED, never PASS or FAIL.** `USERPROFILE`, `APPDATA`, whether the profile folder exists, whether `HKEY_USERS\<sid>` is loaded, the `ProfileList` path, and whether `%APPDATA%\Microsoft\Protect\<sid>` exists (the DPAPI master key), taken right after the Protect | MEASURED | BLOCKED if there was no Protect line |
| `cp4_dpapi_other_identity_refused` | 4. other identities | the blob (the admin hands it over through a file in `config\`) cannot be Unprotected by `AlberaLabCpOther` (another virtual account), `AlberaLabHolder` (a plain local user) and Administrator (the PowerShell Direct session). The virtual account and Administrator must both have been measured | PASS | FAIL if any opens it; BLOCKED if one was not measured or could not read the blob |
| `cp5_tcp_loopback_other_user` | 5. loopback TCP | **MEASURED, never PASS or FAIL.** The service listens on `127.0.0.1` port 0 and says the port; `AlberaLabHolder` (as a service) and Administrator connect and say hello. Expected: both connect. This is recorded, not judged | MEASURED | BLOCKED if the listener or every client gave no line; `listen_failed:<socket error>` is still MEASURED |
| `cp6_programdata_acl` | 6. FAIL only if the socket error is `AccessDenied`: this identity itself may not connect out. PASS would mean the guest has a network, which the driver reports as "not as expected" |

The `cp` probes of the shim (`albera-lab-service-shim.exe cp <probe> ...`, `ControlPlaneProbe.cs`) are: `dpapi-protect`, `dpapi-unprotect`, `tcp-listen`, `tcp-connect`, `acl-file`, `file-access`, `https`. Each prints JSON lines `{"probe":"cp","id":...}`.

Not covered here: the Control Plane's real code (its journal store, settings, pipe use) is not run, only the system calls it will depend on; Node is the host's file, not whatever version the product will pin; the profile and DPAPI findings are for a virtual account on Windows Server 2025, and the answer for a client edition is not measured; `cp5` does not test what a remote or other-session client can reach (only loopback from two local accounts).

## Host migration (`-HostMigrate`)

`scripts/host/albera-host.ps1 -Mode migrate` moves an install of the first layout (the local account `albera-cp`) to the Control Plane service. This mode makes that first-layout install in a disposable VM, with the installer of an old commit, and migrates it.

```powershell
powershell -File test/windows-service-lab/lab-vm.ps1 -HostMigrate -LegacyRef 303ec40
```

`-LegacyRef` is the commit whose `scripts/host` installer made the first layout (hex, 7 to 40 characters). The driver puts that commit's tree into `legacy-src` under the VM's folder (`git archive`, no `.git`), builds the Broker, pipe client and Approval Authority there with that commit's own build scripts (nothing is downloaded), and removes the copy at the end; this happens before the VM exists, so a wrong ref or a failed build costs no VM. The five current builds must exist (`npm run build:windows-broker`, `build:approval-authority`, `build:control-plane`, `build:approver`, or `-Build`). Standard 4 GB VM, no Hyper-V role in the guest, no reboot.

`lab-host-migrate-check.ps1` runs in the guest as Administrator and prints one JSON object (`host-migrate-results.json`, plus `lab-output.txt`). Its steps: the old installer's `-Mode install` with `-ControlPlanePassword` (made in the guest, never printed) and `-GrantHyperVToBroker -VmId <fixed lab GUID>`; one program started as `albera-cp` with `Start-Process -Credential -LoadUserProfile` (the way `runas` starts it) so that `C:\Users\albera-cp` exists and is not loaded; the current installer's `-Mode plan -PlanFor migrate -TrustLocalBuilds`, `-Mode migrate -TrustLocalBuilds`, each service started once and stopped, `-Mode status`, `-Mode uninstall`.

| Check | PASS when |
|---|---|
| `legacy_*` | the old install is complete and of the first layout, the Broker's SID is in Hyper-V Administrators, `albera-cp` ran once, and its profile exists and is not loaded (a loaded profile cannot be deleted by anyone, so that would be the lab's fault) |
| `plan_*` | the plan exits 0, no step is `[blocked]`, and nothing changed |
| `migrate_exit_0`, `status_exit_0`, `uninstall_exit_0` | exit 0 (migrate also says `Migrated.`) |
| `approver_values_carried`, `vm_guid_carried`, `computer_id_and_project_carried`, `grant_choice_carried` | the key id, public key and SID, the VM GUID (Broker config and grant record), the computer id, the project id and the grant are the old install's; `authority_key_made_again`: the Broker config names a new Authority key |
| `albera_cp_account_gone`, `albera_cp_profile_gone` | no local user `albera-cp`, no `C:\Users\albera-cp`, no `Win32_UserProfile` entry |
| `delayed_auto_*`, `cp_runs_as_its_service_identity`, `cp_sidtype_restricted`, `cp_privileges_minimal`, `configs_name_the_cp_service_sid` | read with `Win32_Service`, `sc.exe` and the config files, not through the installer: the three services are `Auto` and delayed, the Control Plane's account is `NT SERVICE\AlberaControlPlane`, restricted, `SeChangeNotifyPrivilege` only, and both configs name its service SID. `cp_process_owner_is_its_service_sid` is added when the Control Plane runs |
| `broker_sid_in_hyperv_admins`, `only_the_broker_in_hyperv_admins`, `broker_unrestricted_authority_restricted` | the Broker's service SID is in the group and nobody else of ALBERA is; the Broker's SID type is unrestricted, the Authority's restricted |
| `nothing_left_behind`, `group_otherwise_unchanged`, `final_status_not_installed` | after the uninstall: no service, account, profile, shortcut, Run value, machine key, folder or `HKLM\SOFTWARE\Albera` key, the Broker's SID is out of the group and the group is as before |

Not shown: the installer's "stop `albera-cp`'s processes by PID" step (a process started as another user in a PowerShell Direct session has no desktop and ends at once, and a scheduled task or a service leaves the profile loaded, which breaks the profile check; `test/host-install.test.mjs` covers the step with fakes), the old Control Plane itself, the lookup of a real VM by name, a real Hello key, and where the builds came from (`-TrustLocalBuilds` hashes the copies in the guest). The state of the Broker and the Authority after their one start is reported in `serviceStarts`, not required. `host-migrate-checks.test.mjs` checks the scripts' text on the host and that the hook refuses to run outside a lab VM.
