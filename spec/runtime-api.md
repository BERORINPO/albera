# Runtime API (Phase 2, isolated prototype)

## Status

`src/runtime/api.mjs` is an authenticated loopback API module. It is not wired to the existing read-only Observer, its HTTP server, UI, or default application startup. The separate `albera-runtime` command composes this API with the Runtime Gateway, approval broker, journal, and `approval-host.mjs` UI host. The API does not supply or weaken Gateway authorization; the Gateway's default-deny callback remains authoritative. The API exposes the bounded in-process approval queue only through separately minted `approvals:read` and `approvals:decide` capabilities; the browser never receives the API bearer credentials. The separate host requires a one-time terminal bootstrap code, then uses a short-lived HttpOnly/SameSite cookie, strict Host/Origin and CSRF checks, and a fixed route proxy. It accepts at most 64 simultaneous connections by default (configurable from 1 to 64), gives request headers 5 seconds, and bounds total request duration to the configured body timeout plus 5 seconds. All POST request bodies are capped at 20 KiB and must finish within the configured 15-second default (100 ms–120 seconds when explicitly configured); a timed-out body is destroyed, and a bootstrap timeout does not consume its code.

## Network boundary

- `listen()` binds only to IPv4 `127.0.0.1`; callers cannot choose a public interface. Port `0` is the default.
- The trusted creator can mint up to 256 random 256-bit bearer credentials with `health`, `providers:read`, `runs:read`, `events:read`, `runs:start`, `runs:stop`, `runs:input`, `approvals:read`, and `approvals:decide` scopes. Approval scopes can only be minted when a broker is injected. By default, each credential receives its own private, in-memory session boundary; runs started by that session and their events are visible only to it. A trusted host may intentionally reuse a validated 32-character session ID for multiple credentials in one process. Other sessions cannot list those runs, read their events/SSE, stop them or send input (foreign run IDs return 404). Credentials expire within 24 hours (one hour by default), can be revoked independently, and are cleared when the API closes. The API has no credential-minting route.
- The host may inject an `audit-journal.mjs` instance, and must provide a Gateway with `close()` so the API can fail closed. When present, API start/stop/input requests write a requested phase before calling the Gateway and an accepted/denied/failed result afterward. The Runtime Gateway can notify trusted subscribers of allowlisted lifecycle changes (`started`, stop transitions, `stopped`, `exited`, `failed`, `input_sent`); the API uses each notification to promptly capture from the bounded Gateway event ring, with periodic polling retained as a safety net. It exposes monotonically increasing event IDs within the owning session, including when no journal is configured; interleaved events from other sessions do not create cursor gaps. Without a journal, the API keeps up to 256 events for each of at most 256 session logs in memory. With a journal, events are persisted with per-session cursors and replayed from that session's journal records. Records contain only session/request IDs, action/phase or event type, timestamp, provider, run ID and stable error/result metadata; never credential values, prompts/input text, paths, argv, environment or process output. Any journal write failure permanently disables the API and closes the Gateway.
- Every route requires `Authorization: Bearer <credential>` with its matching scope. Token hashes are compared in constant time. API authorization grants only the scoped local API access; it does not authorize a process start, stop or input send.
- Host must be exactly `127.0.0.1:<port>` or `localhost:<port>`. If an Origin header is present, it must be the matching HTTP loopback origin. No CORS permission is returned.
- JSON responses use `no-store`, `nosniff`, `no-referrer`, a restrictive CSP and same-origin resource policy. Errors expose stable codes, not exception messages.

## Routes

| Method and route | Behavior |
|---|---|
| `GET /v1/health` | Returns only `{status:"ok"}` |
| `GET /v1/providers` | Requires `providers:read`; returns static provider/profile readiness metadata without probing or launching CLIs |
| `GET /v1/approvals` | Requires `approvals:read`; returns the broker's bounded pending request projections, including exact prompt/input and redacted environment/endpoint metadata |
| `POST /v1/approvals/:id` | Requires `approvals:decide`; accepts only `{ "decision": "approve" | "deny" }`; each pending approval ID can be decided once |
| `GET /v1/runs` | Returns Gateway run projections with an explicit field allowlist |
| `GET /v1/events?after=&limit=` | Returns bounded lifecycle event projections |
| `GET /v1/events/stream?after=` | Authenticated SSE; resumes from a validated session-local `Last-Event-ID` header (which takes precedence over `after`), up to four clients, 250 ms default polling, 60 second maximum lifetime, and 64 KiB write-buffer cap |
| `POST /v1/runs` | Accepts only `provider`, `cwd`, `prompt`, and optional `profile`; Gateway host authorization still decides whether to start |
| `POST /v1/runs/:id/stop` | Requests a stop through the Gateway, which independently requires host authorization |
| `POST /v1/runs/:id/input` | Requires `runs:input`; accepts only `{ "text": string }`; session ownership and a separate exact-text Gateway host approval are both required |

Request bodies are JSON and capped at 20 KiB. Output, prompt, paths, argv, and environment are not projected into run/event responses. Runs created outside the API or under another API credential are not visible to a session. There is no route for arbitrary argv, caller-supplied confirmation, direct provider stdin, or filesystem operations.

The provider catalog reports Claude as `profile-only`, with `read-only` and `read-only-streaming` profiles, per-profile minimum CLI versions, `runtimeValidation: approved-version-preflight-and-synthetic-transport`, lifecycle-only events, and a Guardian-backed input transport. The documented minimums are Claude Code v2.1.248 for `--restricted` and v2.1.259 for `--permission-prompts none` used by streaming. Following explicit host approval, Runtime runs a bounded `--version` probe with a minimized environment and refuses to launch when the version is missing, invalid, or below the profile minimum. This check verifies only the reported version; it does not validate managed policy, credentials, or actual CLI safety semantics. The synthetic transport test does not claim installed Claude CLI compatibility beyond the version preflight. Codex and OpenCode are `unavailable` with `profile_unavailable`. The catalog itself is static: it does not inspect installed versions, settings, credentials, or managed policy and must not be read as a compatibility or safety certification.

## Security limits and unfinished work

- Loopback plus a bearer token is not OS-user authentication. A local process that obtains an in-memory credential can use the API; a process that observes the one-time terminal bootstrap code can access the browser host. HTTP is not encrypted against privileged local packet inspection. Do not expose or persist tokens. The broker's approval scopes remain server-side and separate from browser task sessions. The standalone runtime UI displays exact prompt/input, root, executable, fixed args, and endpoint metadata, but does not identify the configured provider account or estimate cost. Approved input may be sent to the provider account/API and incur cost. No real CLI or GUI acceptance has been verified.
- The optional journal persists API start/stop/input decisions and captured lifecycle events. Without a journal, the API keeps a bounded in-memory ring of 256 events per session for at most 256 session logs; eviction or API restart loses that event history. The standalone command stores a non-secret 128-bit session identity beside the journal and reissues it on restart, so journaled run/event projections are restored in the UI. Any unfinished run without a captured terminal event is conservatively marked `interrupted` and cannot be stopped through the new Gateway instance; active processes are not restored. Per-session event IDs do not expose other sessions' event counts. Startup requires each session's persisted event IDs to be contiguous from 1; duplicate, skipped, or reversed IDs make the journal invalid, and startup refuses it without modifying the file. Lifecycle notifications trigger capture promptly and a periodic poll remains as a backstop, but a hard host crash between event emission and completed journal append can still lose the final event; this does not restore a running process. Retention/backup policy and long-term compaction are not implemented. The journal is single-writer, append-only, bounded, validates all existing records, and refuses corrupt/incomplete data without changing it. Use a user-private directory; the journal is not encrypted. The session-identity sidecar has the same no-repair Windows DACL checks as the journal and POSIX owner/mode checks; cross-platform CI verified the Windows integration in run 40487083932. Production OS-user authentication and storage recovery remain unverified.
- The Gateway default spawn path has a parent-liveness guardian. Phase 1 RT-10 is verified for the tested host crash/stop contract; Guardian failure, Windows PID reuse, cross-restart host session continuity, and active-run recovery remain unresolved. Keep the opt-in Runtime process local and supervised. Provider output remains discarded, real CLI compatibility and browser GUI acceptance are unverified, and tests use only synthetic child processes.
- API tests use a fake Gateway and the default-deny real Gateway. No AI CLI is invoked.
