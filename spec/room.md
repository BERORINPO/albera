## 1. What it is

`albera-runtime room` = the wall turned into a canvas. Cameras (live VM screens with the AI cursor) sit on a dotted canvas.
Bero, the main AI, floats over it: it looks around, notices (stall, a DONE claim, a limit), points at a camera, says one line,
draws a figure built from the real log, and opens a decision card. Every hands step and every human choice goes into the ledger.

Same host model as the wall: 127.0.0.1 only, bootstrap code -> HttpOnly cookie, CSP `default-src 'none'` (+ self), no-store,
text only through `textContent` / DOM APIs. New: one write route (`POST api/decide`) that can start or stop hands on a VM, so
it is guarded like `approval-host` (Origin, Sec-Fetch-Site, JSON content type, session cookie, card + choice must be open and unused).

Bero is rule-based in v0.8 (no LLM): words come from dictionaries by code. An LLM wording step can be added later behind the same codes.

## 2. Data flow

```
agent-fleet (hands loops) --onEvent(vmId, ev)--> room-journal.recordFleetEvent  --> ledger entries
                                     \--> agent-status-board (cursor, step, usd, note)
host tick (1 s):  director.tick({now, agents: board.snapshot(), entries: journal.since(cursor)})
                  -> {acts, ledger}  -> host appends RoomEvents (bero / ledger)
UI poll (1 s):    GET api/state?since=N -> {now, staleAfterMs, vms, events, nextSince}
UI:               app.mjs plays bero acts in order (await each), adds ledger rows, cards open via the 'card' act
human choice:     POST api/decide {cardId, choiceId} -> director.decide -> Effect -> host runs it on the fleet
                  -> ledger 'human_choice' + RoomEvent card_closed
```

## 4. Codes and params

Ledger (`LEDGER_CODES`, words: C):

| code | actor | params |
|---|---|---|
| `hands_started` | hands | `task` (cut to 200) |
| `hands_step` | hands | `step`, `usd`, `action` (last action name or ''), `note` (the AI's own text this step, cut to 160) |
| `hands_ended` | hands | `outcome` (HAND_OUTCOMES), `claim` (cut to 200), `steps`, `usd` |
| `hands_stalled` | bero | `seconds` (no action for that long while running) |
| `bero_noticed` | bero | `what` (a CARD_CODES value) |
| `bero_figure` | bero | `kind` (FIGURE_KINDS) |
| `bero_card` | bero | `cardCode` |
| `human_choice` | human | `cardCode`, `choiceCode`, `effect` |
| `start_approved` | bero | none. A job on this VM (a card's, or an initial job of a gated room) was approved (only with a start gate); the job starts next |
| `start_refused` | bero | `code`: a fixed code of task-start-gate.mjs, or the fleet's own (`vm_busy`, `over_budget`, ...). No job was started |

Say (`SAY_CODES`, words: D). Params: `cam` (camera label), `seconds`, `claim`, `usd`, `count`, `steps`.
Card (`CARD_CODES`, words: D). Choice codes are D's own (for example `close_it`, `check_again`, `mark_done`, `stop_it`, `later`).

## 7. Automatic checks (v0.9)

Why: a DONE claim made the person the checker for every VM. Now ALBERA checks the VM itself and the person is asked only when the check fails or cannot run.

Flow:
```
hands 'end' with claimed_done, and the VM has checks
  -> host records `check_started` {count} BEFORE `hands_ended` (same moment, in this order)
  -> host runs checker.run(vmId, checks) (async, one at a time per VM, 60 s timeout)
  -> host records `check_done` {verdict, checks, failed, detail} (detail: first failing "path: finding", cut to 200)
Director: hands_ended(claimed_done) for a VM with a pending check_started -> no card, say `checking`.
          check_done passed -> say `verified` (no card). failed -> card `check_failed`. unavailable -> card `check_unavailable`.
          A VM without checks keeps today's `claimed_done` card.
```
`recheck` jobs end like any job, so their DONE is checked again.

Ledger params: `check_started` {count}; `check_done` {verdict, checks, failed, detail}. Actor of both: `bero` (Bero had them checked).
Say params: `cam`, `checks`, `failed`, `detail`. Card params: `cam`, `detail`, `claim`.
Choices (D): check_failed -> check_again = recheck, mark_done = accept (the person overrides), later = dismiss;
check_unavailable -> mark_done = accept, check_again = recheck, later = dismiss.

Checker (B):
```js
// fake-guest-checker.mjs
createFakeGuestChecker(script) -> { run(vmId, checks) -> Promise<CheckReport> }      // script: vmId -> CheckReport[] in order
// hyperv-guest-check-prototype.mjs  (same-user prototype, like the desktop broker)
createHyperVGuestChecker({ user = 'Administrator', passwordFile }) -> { run(vmId, checks) -> Promise<CheckReport> }
  // <absolute path to pwsh.exe> -NoProfile -File hyperv-guest/check-io.ps1, request on stdin as JSON {vmName, user, password, checks}
  // the script runs Invoke-Command -VMName with ONE fixed script block that only uses .NET calls ([System.IO.File]::Exists,
  // [System.IO.Directory]::Exists, a bounded [System.IO.File]::Open read) and compares inside the VM. Only findings come back.
  // The password is read from the file at each run, never logged, never put on a command line, never in an event, error or report.
```
A passed check trusts the guest: an AI with admin rights inside the VM could fake it, so it is not tamper-proof.
CLI (B): `room --job ... --checks <file.json> --guest-password-file <file>`; checks file = `{ "<vmId>": [Check, ...] }`, validated
with `validCheck`, at most 8 per VM, unknown VM ids rejected. `--demo` uses the fake checker: Booking form passes, Tests' DONE fails once.

## 8. Workspace file (v0.9)

One JSON file names a room's VMs, tasks, camera labels, automatic checks and limits, so a team keeps it in a repository and
reviews it like code. `albera-runtime room --workspace <file> [--guest-password-file <file>] [--port <n>]`; no other room
option is accepted with it. Example: `examples/albera.workspace.example.json`. Parser: `src/runtime/workspace.mjs` (pure).

```json
{ "version": 1, "name": "booking-site",
  "vms": [ { "vm": "<hyper-v-vm>", "label": "<any script, 1-32>", "task": "<1-2000>", "checks": [Check, ...] } ],
  "limits": { "model": "claude-haiku-5-5", "maxSteps": 40, "maxUsdPerVm": 0.5, "maxUsdTotal": 2, "maxMinutes": 15 } }
```

Rules: unknown fields are refused (a typo or a pasted secret fails loudly); 1-8 VMs, unique; checks as §7; limits within
the same table as the CLI (`LIMIT_RULES`), per-VM not above total; errors are fixed codes, the file content is never printed.

## 9. Start approval (A3 of #115 follow-up)

Without the option the room starts hands as before and says so (`Warning: ... NOT approved`). With `room --require-start-approval --approval <albera.approval.json>` (both or neither; `--job` and `--workspace` rooms, not `--demo`) every start goes through the gate:

```
entry: load the settings file -> check every VM is in "computers" and every task fits a task.start -> open the SQLite flow journal
       -> bind the pipe clients (Host Broker, Approval Authority) -> approved-operation flow -> task-start gate   (room-approval-wiring.mjs)
fleet: created with jobs: [] and keepAlive: true (the room host requires initialJobCount 0 when it has a gate)
room:  listen -> fleet.run() -> host.requestStart(vm, task) for each initial job -> 'pending_approval' at once
       -> ledger start_approved and the job starts, or start_refused {code} and nothing starts
```

Settings file (parser `parseApprovalSettings`, pure; unknown keys refused; paths and names only, never a secret; errors are fixed `runtime_room_approval_*` codes that never print the content or a path):
`{ "version": 1, "projectId", "broker": { "pipeName", "expect": { "serviceName" } }, "authority": { "pipeRoot", "expect": { "serviceName" } }, "journal": "<absolute SQLite path>", "computers": { "<vm>": "<computerId>" | { "computerId", "vmId", "expectedGeneration" } }, "attestation": null | { "keyFile", "keyId", "cloneRoot" } }`.
Example: `examples/albera.approval.example.json`. Operator steps: `docs/architecture/approval-tiers.md`, "Room start approval".

## 10. Talk panel (Phase 1 of `docs/architecture/mission-approval.md`)

The room can be talked to. The person writes, the main AI (Claude Code with no tools) answers, and when something should be done on a computer it proposes ONE job. This phase changes no approval: a proposal is shown as a job request card, and the card's button sends its goal to the existing job route as the task (`POST api/jobs`, the same call as the Jobs panel), so the person approves that one task in the approval window, one at a time, as before. `mission.start`, grants and the mission loop are Phases 2 to 4 and are not here.

```
person ─words─▶ POST api/talk ─▶ room-talk-routes ─▶ mainAi.turn({ words, state }) ─▶ { ok, text }   (main-ai-claude.mjs; fake-main-ai.mjs in tests)
                                   parseReply(text) ─▶ say (+ propose, shown as a card)             (main-ai-contract.mjs; a reply that fails is ONE fixed code, never retried)
card "Ask to start" ─▶ POST api/jobs { computerId, task: goal } ─▶ the existing approval flow ─▶ the person, with Hello
```

Routes (`room-talk-routes.mjs`, pure; the host's own checks run first: Origin, Sec-Fetch-Site, JSON, session cookie, body at most 4 KiB): `GET api/talk` -> `{ ok, available, busy, messages }`; `POST api/talk { words }` -> the same with the answer in it; `POST api/talk/reset {}`. `Message = { id, who: 'you' | 'bero', text, proposal?: { goal, computerId, label } }`. Words: 1 to 1000 characters, newline and tab allowed, no other control or direction mark. The conversation is in the host's memory only: 40 messages at most, the last 10 shown to the model; a turn that fails keeps nothing (the page keeps the words in the box). One turn at a time (`409 busy`). Failures are fixed codes: the adapter's own (`MAIN_AI_FAILURES`; a missing token is `credential_missing`, never folded into `start_error`), or `reply_invalid`. Logs carry codes only.

The reply is untrusted text. `parseReply` accepts one JSON object (one surrounding code fence is the only repair): `say` 1 to 2000 characters, shown with `textContent` only, line breaks and tabs folded into a space, any other control or direction character makes the reply invalid; and at most one of `propose { goal, computerId, maxStarts, minutes }` (goal as a task: 1 to 256 safe bytes; `computerId` one this room offers; `maxStarts` 1 to 20; `minutes` 5 to 480), `next { task }`, `done: true`. Phase 1 acts on `say` and `propose` only; `next` and `done` are valid and ignored. `maxStarts` and `minutes` are checked and then dropped: nothing enforces them yet, so no screen, word or card states a number of runs or minutes.

Main AI adapter (`main-ai-claude.mjs`): one `claude -p` run of the pinned executable per turn, with `--tools ""`, the usual tool names denied again, an EMPTY MCP configuration, no settings and no session, the stored token in the child's environment only, the person's words on stdin only, and its own new run folder (`run-<16 hex>`, checked by the driver's `preflight`, deleted after the turn; the startup sweep also removes what a killed service left). The child reaches the same pipes as the Control Plane, so "no tools" is its only boundary, and the adapter does not take it on trust: the `init` message must show `tools` and `mcp_servers` present and both empty, else the child is stopped by its own PID (`capability_unverified`: no proof, or none in 30 s; `unexpected_capability`: something listed). Any `tool_use` stops it too. The hands' check (six tools and one MCP server) is not reused. A turn is limited to 90 s; at the limit, on `stop()` and on `close()` only the PID this adapter started is ended (never by image name).

Off by default: the real adapter runs only when the service file says `"mainAi": true` (optional boolean, `room-service-config.mjs`). Off, the panel is there and says it is not available (`disabledMainAi`, `available: false`, `main_ai_disabled`), no token is read and no process is started. Turn it on only after M6 (`control-plane-service.md` section 11) has shown that `--tools ""` really leaves the child with no tool.

NOT VERIFIED (nothing here started a real `claude` or sent anything to a model): that the pinned `claude` obeys the flags above (M6) and what its `init` lists with `--tools ""` (if it lists something harmless, the strict check refuses every turn until it is widened on purpose); that a system prompt with quotes and line breaks survives the Windows command line into `claude.exe`; `--disable-slash-commands` (read from `--help` of 2.1.310, never run with this token); the user message is written at once, so a model request may start before `init` is read (with `--tools ""` working there is nothing to use; the check ends a child that has tools, but a tool call could precede it, which is why the setting is off); what the subscription's limits do to a turn (M5); how the panel looks in a browser (it was run on a fake DOM only).
