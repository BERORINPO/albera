# Runtime Gateway (Phase 1 foundation)

## Scope and status

`src/runtime/gateway.mjs` is an isolated process lifecycle foundation. Its default spawn path uses `supervisor.mjs` and `guardian.mjs`: the Gateway keeps a private stdin pipe open to the guardian, which starts the approved provider and reaps its process tree if the Gateway process disappears. The existing `albera` dashboard remains a read-only Claude Code session observer. The Gateway is not imported by the Observer or its HTTP routes. An opt-in `albera-runtime` command composes the Gateway with a separate authenticated Runtime API, journal, and loopback approval/control UI (see `spec/runtime-api.md`). It remains a local prototype rather than a signed or production-packaged service. Tests use fakes and local Node.js helper processes; no AI CLI is invoked.

The opt-in Runtime command provides an approval UI, but is not an OS sandbox or production-ready service. Authenticated read-only browser acceptance is recorded in `docs/progress.md`; start/input/stop action-flow browser acceptance remains unverified. Guardian-process failure, Windows PID reuse, breakaway descendants, and durable active-process recovery are not solved. Do not expose it as a persistent service.

## Launch contract

- A trusted host must inject an `authorize` callback. The default callback denies. A request field such as `confirmed: true` cannot authorize a launch or stop.
- For a start decision, the callback receives an immutable tuple containing the action, fixed provider ID, named launch profile, canonical executable path, canonical working directory and exact generated argv array. The separate approval host displays the approved request and binds the decision to that request. Raw request `args` are rejected; the default Gateway creates provider argv internally.
- Provider IDs are fixed to `claude`, `codex` and `opencode`. A provider selects its command name; callers cannot choose an executable.
- The command is resolved from PATH, canonicalized, and checked as a file with executable permission on POSIX. Windows accepts `.exe` only. `.cmd` and `.bat` shims are rejected; no shell is used.
- The working directory must resolve to an existing directory inside one of the configured absolute roots. This constrains only the selected working directory, not filesystem access by the child.
- Two Claude Code profiles are generated internally: `read-only` is the default one-shot profile; `read-only-streaming` uses the same restricted/safe/MCP-deny/plan policy and `--permission-prompts none` with print-mode `stream-json` input/output. Initial and follow-up text travels as a fixed JSONL user-message envelope over the child's private stdin pipe, never in argv. The Guardian accepts input only for this fixed profile/mode. Follow-up messages are size-bounded, serialized, independently approved by the trusted host callback with the exact prefixed text, and acknowledged by the Guardian; timeout or pipe failure fails the run closed. The current event/output projection remains lifecycle-only and provider stdout/stderr are discarded. The streaming profile uses `--max-turns 1`, which Claude documents as a per-turn limit for stream-json input; this code has only been verified with a synthetic Node helper, not a real CLI.
- Codex and OpenCode currently fail closed before executable resolution or approval. Codex's read-only filesystem sandbox alone does not establish that MCP tools or other external side effects are disabled, and an empty config override is not proven to remove merged configuration. OpenCode merges remote, user, project, plugin and inline configuration. Both remain unavailable until ALBERA can own and verify the complete per-run tool/configuration policy.
- Claude profile construction and the Guardian input transport are tested with fixed argv and a synthetic helper. After the host explicitly approves the exact executable and launch request, Runtime runs that executable with only `--version`, a 3-second timeout, bounded output, a temporary working directory, and a minimized environment. It refuses to launch below the documented profile minimum (2.1.248 for `--restricted`; 2.1.259 for streaming `--permission-prompts none`) and revalidates executable identity after the probe. This confirms only the executable's reported version; it does not prove managed policy, account settings, or runtime safety semantics. The approval screen discloses the probe before approval. No provider task prompt or credential is sent to the version check.
- The stream-json envelope shape, print-mode input format and per-turn `--max-turns` behavior follow the [Claude CLI reference](https://code.claude.com/docs/en/cli-reference) and [Claude streaming input guide](https://code.claude.com/docs/en/agent-sdk/streaming-vs-single-mode). Those docs do not replace an installed-version integration test.
- Generated argument vectors are capped at 128 entries and 32 KiB, prompts at 16 KiB, and NUL is rejected. The host must approve the exact profile and arguments.
- Child environment inherits only a small OS allowlist plus a provider-specific credential/configuration allowlist. The host authorization callback receives a frozen summary of provider-variable names and endpoint protocol/host; it never receives credential values or endpoint userinfo, path, query or fragment. Arguments and the exact child-environment snapshot are copied before authorization and reused for spawn, so caller mutation during an asynchronous approval cannot change the approved launch. Environment values and arguments are never returned, persisted or included in lifecycle events.
- At most four runs are active; run duration is capped at 60 minutes (default 15 minutes). Run records are capped at 64 and lifecycle events at 256 in memory. These limits are not CPU or memory quotas.

## Lifecycle and cleanup

The Gateway reports `starting`, `running`, `stopping`, `stopped`, `exited` and `failed`. A stop records one fixed `stopReason`: `user_cancel` for an approved user stop, `timeout` for the run-duration limit, or `host_shutdown` for trusted host cleanup. Natural exits retain a null reason and their exit code/signal distinguishes normal from abnormal completion. Lifecycle events expose the bounded `stopReason` only on stop-related events; arbitrary reason strings are never accepted. Events contain generated run IDs, allowlisted provider IDs, timestamps, and an exit code or signal when available. Output, prompt, arguments, paths, environment, and raw OS error text are excluded. `close()` permanently closes that Gateway instance: a start awaiting authorization is rejected before spawn if close begins, and later starts return `gateway_closed`.

An authorized stop sends `SIGTERM` to the POSIX process group. If group signaling fails, Guardian still attempts the bounded `SIGKILL` escalation; only a successful group signal or `ESRCH` (group already absent) confirms the process tree. A direct-child fallback may be attempted after other signal errors, but its success does not confirm descendants. Windows uses `taskkill.exe` with fixed numeric PID arguments, `/T` and `/F`, without a shell: Node documents Windows `SIGTERM` as abrupt, and `taskkill /T` alone can fail to terminate descendants. The host callback receives `force: true` for Windows stops so the user can be told before approval. The Guardian reports the termination adapter result over its private control pipe; pipe write acceptance alone is not tree confirmation. A Windows direct-child fallback is reported as unconfirmed because descendants may remain. The Gateway escalates again after three seconds if the process has not closed. The snapshot's `treeStopConfirmed` is `true` only after the process-tree adapter succeeds, `false` when only direct-child cleanup can be attempted or the parent has already exited, and `null` when no tree signal was needed. If tree cleanup is uncertain, the run ends as `failed` and a trusted host's bounded `close()` includes its ID in the unresolved list. Before signaling by PID, the Gateway checks the child exit fields to avoid signaling a reused PID after the direct process has exited.

## Security limits and deferred gates

- The child runs with the current OS user's privileges. The allowed-root check is not filesystem isolation. Do not expose this Gateway until an OS-level sandbox/policy is designed and verified on each supported platform.
- PATH resolution verifies file type and executable permission, but does not attest vendor identity or prevent replacement between validation and spawn.
- Writable profiles, provider output parsing/projection, organization-managed secret redaction, OS sandboxing and OS resource quotas are not implemented. The separate Runtime host supplies a local approval UI that displays exact text and projected provider/endpoint context. Authenticated read-only browser acceptance is verified; action-flow GUI acceptance and provider account/cost display are not. Approved input may reach the configured provider account/API and may incur cost. The Gateway still defaults to deny when no trusted host callback is supplied.
- The default spawn path now uses a per-run parent-liveness Guardian; `test/process-supervisor.test.mjs` verifies that the Guardian reaps a synthetic helper after its Gateway host is killed. GitHub Actions run 40465224570 passed the test and architecture matrix on Windows/macOS/Linux × Node 22/24. Orderly stop and shutdown requests use the Guardian control pipe. Guardian failure, Windows PID reuse, breakaway descendants and run/event state recovery remain unresolved. Keep this module disconnected and do not run it as a persistent user-facing service until durable restart semantics and stronger OS process containment are implemented.
- Windows `.cmd` and `.bat` providers are rejected. Supporting them requires a separately reviewed fixed adapter; do not enable `shell: true` or construct command strings from argv.
- Real Claude Code, Codex CLI and OpenCode compatibility, account cost and outbound data handling have not been verified. The authenticated read-only Runtime screen was inspected in a real local browser; no approval/start/input/stop action was activated. Action-flow GUI acceptance and provider compatibility remain open; see `docs/progress.md`.

Reproducible local verification is recorded in `docs/progress.md`; Phase 1 acceptance status is in `docs/acceptance-criteria.md`.
