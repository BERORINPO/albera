# Runtime Gateway (Phase 1 foundation)

## Scope and status

`src/runtime/gateway.mjs` is an isolated, in-memory process lifecycle foundation. Its default spawn path uses `supervisor.mjs` and `guardian.mjs`: the Gateway keeps a private stdin pipe open to the guardian, which starts the approved provider and reaps its process tree if the Gateway process disappears. The existing local dashboard remains a read-only Claude Code session observer. No Observer layer, existing HTTP route, UI control, persistence layer or orchestration code imports or wires the Gateway. The separate authenticated API prototype is described in `spec/runtime-api.md`; it is not connected to application startup. Tests use fakes and local Node.js helper processes; no AI CLI is invoked.

The Gateway is not yet a user-facing Runtime feature and is not an OS sandbox. Guardian cleanup covers Gateway parent loss, but guardian-process failure, Windows PID reuse, breakaway descendants, and durable state recovery are not solved. The API prototype is not production-ready; neither module may be exposed as a persistent service.

## Launch contract

- A trusted host must inject an `authorize` callback. The default callback denies. A request field such as `confirmed: true` cannot authorize a launch or stop.
- For a start decision, the callback receives an immutable tuple containing the action, fixed provider ID, named launch profile, canonical executable path, canonical working directory and exact generated argv array. The host must show that tuple to the user and bind approval to that exact request. The module has no route or UI that implements this host contract yet. Raw request `args` are rejected; the default Gateway creates provider argv internally.
- Provider IDs are fixed to `claude`, `codex` and `opencode`. A provider selects its command name; callers cannot choose an executable.
- The command is resolved from PATH, canonicalized, and checked as a file with executable permission on POSIX. Windows accepts `.exe` only. `.cmd` and `.bat` shims are rejected; no shell is used.
- The working directory must resolve to an existing directory inside one of the configured absolute roots. This constrains only the selected working directory, not filesystem access by the child.
- The only default profile currently available is `read-only` for Claude Code. It is launched with `--restricted`, `--safe-mode`, an explicit `--disallowedTools mcp__*` rule, plan permission mode, print mode, one turn, and no session persistence. The explicit deny rule prevents any configured MCP tool from being called; safe mode disables local customizations. Restricted mode still loads organization-managed settings, so those remain part of the host trust boundary. This vector is generated by the Gateway; arbitrary argv is rejected. Prompts are prefixed as `ALBERA task:` so option-looking user text remains positional input.
- Codex and OpenCode currently fail closed before executable resolution or approval. Codex's read-only filesystem sandbox alone does not establish that MCP tools or other external side effects are disabled, and an empty config override is not proven to remove merged configuration. OpenCode merges remote, user, project, plugin and inline configuration. Both remain unavailable until ALBERA can own and verify the complete per-run tool/configuration policy.
- Claude profile construction is tested as argv only; no real AI CLI has been invoked, so executable/version compatibility is not claimed.
- Generated argument vectors are capped at 128 entries and 32 KiB, prompts at 16 KiB, and NUL is rejected. The host must approve the exact profile and arguments.
- Child environment inherits only a small OS allowlist plus a provider-specific credential/configuration allowlist. The host authorization callback receives a frozen summary of provider-variable names and endpoint protocol/host; it never receives credential values or endpoint userinfo, path, query or fragment. Arguments and the exact child-environment snapshot are copied before authorization and reused for spawn, so caller mutation during an asynchronous approval cannot change the approved launch. Environment values and arguments are never returned, persisted or included in lifecycle events.
- At most four runs are active; run duration is capped at 60 minutes (default 15 minutes). Run records are capped at 64 and lifecycle events at 256 in memory. These limits are not CPU or memory quotas.

## Lifecycle and cleanup

The Gateway reports `starting`, `running`, `stopping`, `stopped`, `exited` and `failed`. Events are fixed lifecycle records only; they contain generated run IDs, allowlisted provider IDs, timestamps, and an exit code or signal when available. Output, prompt, arguments, paths, environment, and raw OS error text are excluded. `close()` permanently closes that Gateway instance: a start awaiting authorization is rejected before spawn if close begins, and later starts return `gateway_closed`.

An authorized stop sends `SIGTERM` to the POSIX process group. Windows uses `taskkill.exe` with fixed numeric PID arguments, `/T` and `/F`, without a shell: Node documents Windows `SIGTERM` as abrupt, and `taskkill /T` alone can fail to terminate descendants. The host callback receives `force: true` for Windows stops so the user can be told before approval. The Gateway escalates again after three seconds if the process has not closed. The snapshot's `treeStopConfirmed` is `true` only after the process-tree adapter succeeds, `false` when only direct-child cleanup can be attempted or the parent has already exited, and `null` when no tree signal was needed. If tree cleanup is uncertain, the run ends as `failed` and a trusted host's bounded `close()` includes its ID in the unresolved list. Before signaling by PID, the Gateway checks the child exit fields to avoid signaling a reused PID after the direct process has exited.

## Security limits and deferred gates

- The child runs with the current OS user's privileges. The allowed-root check is not filesystem isolation. Do not expose this Gateway until an OS-level sandbox/policy is designed and verified on each supported platform.
- PATH resolution verifies file type and executable permission, but does not attest vendor identity or prevent replacement between validation and spawn.
- Writable provider profiles, prompt/input transport, output parsing, secret redaction, authentication, local API authorization, audit persistence and resource quotas are not implemented. The read-only profile vectors are not a substitute for the OS sandbox and host approval API.
- The default spawn path now uses a per-run parent-liveness Guardian; `test/process-supervisor.test.mjs` verifies that the Guardian reaps a synthetic helper after its Gateway host is killed. GitHub Actions run 40465224570 passed the test and architecture matrix on Windows/macOS/Linux × Node 22/24. Orderly stop and shutdown requests use the Guardian control pipe. Guardian failure, Windows PID reuse, breakaway descendants and run/event state recovery remain unresolved. Keep this module disconnected and do not run it as a persistent user-facing service until durable restart semantics and stronger OS process containment are implemented.
- Windows `.cmd` and `.bat` providers are rejected. Supporting them requires a separately reviewed fixed adapter; do not enable `shell: true` or construct command strings from argv.
- Real Claude Code, Codex CLI and OpenCode compatibility, account cost, outbound data handling, GUI approval, and GUI acceptance have not been verified.

Reproducible local verification is recorded in `docs/progress.md`; Phase 1 acceptance status is in `docs/acceptance-criteria.md`.
