# Approver app (`AlberaApprover.exe`): the human's console for the Approval Authority

**Status: Proposed, NOT VERIFIED.** The approver app is the human side of the Approval Authority (`approval-authority.md`). It lists the Authority's pending requests, shows every input of the action digest, approves or denies, and enrols the Windows Hello key. **The Windows Hello code is written and compiled into the shipped binary, but it has never run against a real Hello enrolment** (CI cannot; see "Real versus fake" and "Enrol and first approval"). **WebAuthn presence** (phase 3 of `approver-webauthn.md`: sign with a WebAuthn key, which works over Remote Desktop; `enroll --webauthn`, `keys`; see "WebAuthn presence") is written the same way: its logic is unit-tested with a software authenticator, and its `webauthn.dll` calls rest on the feasibility probe's one real run (create and sign over Remote Desktop, 2026-11-04) plus what "WebAuthn presence" lists as not run. This document does not edit ADR-002, the trust contract or the status documents; the lead folds the relevant parts into them. Related: #84.

## What it is

A .NET 10 program (a console program for the commands below, plus a tray and approval-window mode, `--tray`; `src/runtime/windows-approver/`, assembly `AlberaApprover`), built on demand with `npm run build:approver`. It talks only to the Authority's approver pipe `ALBERA\ApprovalAuthority\approver\v1` (wire protocol: `approval-authority.md`). It shares only the receipt v2 / action digest contract with the other projects, by source include (`../broker-contract/*.cs`); the Broker and Authority projects are not referenced, and nothing in the Observer or the npm package names it (`npm run arch` rule 11, `npm run package:smoke`).

```
human ── AlberaApprover.exe ──(approver pipe; server verified first)──▶ Approval Authority
            list / approve / deny
            │  recompute digest with ActionDigest (broker-contract)
            │  enroll: IHelloKeyStore ──▶ creates / shows the Hello key, prints the Authority config values
            │  enroll --check: opens the existing key, IPresenceSigner signs a self-check message, verified locally (no pipe)
            └─ IPresenceSigner ──▶ Windows Hello (KeyCredentialManager)   |   fake in-memory RSA key (test-faults build only)
```

## Commands

```
AlberaApprover.exe list
AlberaApprover.exe approve <approvalId>
AlberaApprover.exe deny <approvalId>
AlberaApprover.exe enroll [--show | --replace | --check [--expect <approverKeyId>]]
AlberaApprover.exe enroll [--replace] --accept-unattested
AlberaApprover.exe enroll --webauthn --accept-unattested
AlberaApprover.exe keys list
AlberaApprover.exe keys remove <keyId>
AlberaApprover.exe policy [show] | policy set <careful|standard> [--prompt <action>]...
AlberaApprover.exe --tray
```

`<approvalId>` is the Authority's lowercase uuid; anything else is a usage error (exit 64). There is no other option, config file or environment variable in the shipped build. **There is no `--yes`**: the typed confirmation cannot be skipped.

- **list**: asks for every page (`afterSeq` = `lastSeq` while `more`) and prints `pending: N`, then one block per request (below).
- **approve**: needs an interactive console. If stdin is redirected (a pipe, a file, a script) it exits 65 `not_interactive` **before** it reads anything or opens the pipe, even if "yes" is on stdin. Then it fetches a fresh `list` and finds the request. It **refuses** (nothing signed, nothing sent) if the id is not pending, the entry is malformed, or the digest it recomputed from the shown fields differs from the Authority's `actionDigest`. Otherwise it prints the request, asks you to type `yes` (every time), prints a line that Windows Hello is about to ask (the Hello prompt shows only the app name, so the details are already on screen), asks the presence signer for a signature over the presence message, and sends `decide` with it.
- **deny**: sends `decide` `deny` (no presence proof; a deny can only make a request fail). It does not need to list first and works without a console.
- **enroll**: makes the approver's Windows Hello key and prints what the Authority config needs (below). `enroll` creates it (Hello asks you once) and **refuses if the key exists** (exit 65 `already_enrolled`). `enroll --show` prints the same values for the existing key (no prompt, no change, no console needed). `enroll --replace` first asks you to type `replace`, then makes a new key in place of the old one (the old key is lost; the Authority rejects approvals until its config has the new values). `enroll` and `enroll --replace` need an interactive console like `approve`.
- **enroll --check** (self-check): proves on this PC, **without the Approval Authority**, that the enrolled Hello key works. It opens the **existing** key `AlberaApprover.v1` only (never creates, replaces or deletes one), asks Hello once (one prompt) to sign `"albera.selfcheck.v1" 0x00 <64 hex chars = 32 fresh random bytes>`, and verifies the signature **locally** with the public key of the same credential (RSA-2048, PKCS#1 v1.5 / SHA-256, a 256-byte signature, the same parameters the Authority checks presence with; the approver and the Authority share no code, so the parameters are repeated in `PresenceSignature.Verify`). Nothing is sent: no pipe, no network, no file. Needs an interactive console like `approve` (checked first, exit 65 `not_interactive`). `--expect <approverKeyId>` compares the key's id with the one you recorded at `enroll`; on a difference it prints `KEY_MISMATCH` and stops **before** Hello is asked.

  stdout on success is exactly these three lines (public values only):

  ```
  self-check: OK
  approverKeyId: hello-0123456789abcdef
  approverSid: S-1-5-21-...
  ```

  On `self-check: FAILED` (Hello signed, but the signature does not verify with the credential's public key) or `self-check: KEY_MISMATCH` the line is on stdout and an `error:` line is on stderr. The message is **domain-separated** from the presence message: `albera.selfcheck.v1` versus `albera.presence.v1`, so neither starts like the other and a self-check signature can never verify as a presence signature for any request (a unit check asserts this). A pass shows that the key signs and matches its public key; it does **not** show who created the key (see "Known limits": keep your own `enroll` output and use `--expect`).

### What `enroll` prints (stdout; public values only)

```
Windows Hello approver key (RSA-2048). Put these three values in the Authority config:
  "approverPublicKey": "<base64 SPKI>",
  "approverKeyId": "hello-<first 16 hex of SHA-256 of the SPKI>",
  "approverSid": "S-1-5-21-...",
Public values only. approverSid is this account: run approve as the same account, on this PC.
attestation: Success (Windows Hello reports the key as attested; certificate chain 1234 bytes, statement 567 bytes; the chain and statement are NOT verified by this program)
```

The `attestation:` line is printed only by `enroll` / `enroll --replace` for the key they just made (see "Attestation at enroll"); `enroll --show` never prints it, because it opens an existing key and claims nothing about it.

`approverPublicKey` is the credential's `RetrievePublicKey(X509SubjectPublicKeyInfo)`; the app refuses a key that is not RSA-2048. `approverKeyId` is a **suggestion** derived from the key: the Authority only requires its id grammar (`^[A-Za-z0-9][A-Za-z0-9._:-]{0,63}$`) and puts the value into receipts, so any id in that grammar works. `approverSid` is the SID of the account running `enroll` (the Authority requires the approver to be a user, `S-1-5-21-...`, and distinct from the Control Plane account). The private key never leaves Windows Hello; this code never reads, exports or stores it, and `enroll` writes nothing to disk.

### Output format (stdout; `\n` line ends; printable ASCII only)

```
pending: 1
request 3f2b8c1e-5d4a-4b6f-9a7e-0c1d2e3f4a5b
  purpose: "broker.operation"
  action: "environment.start"
  projectId: "proj-alpha"
  computerId: "pc-01"
  args: 3
    "cpu" = 2 (int)
    "fast" = true (bool)
    "vmName" = "alpha" (string)
  operationId: "op-1"
  expiresAt: 1800000117 (2027-01-15T08:01:57Z, in 117 s)
  actionDigest: sha256:2e4b6c62...
  digest check: OK (recomputed from the fields above)
```

Every digest input is shown (purpose, action, projectId, computerId, every arg in the digest's sorted order), then the operationId (which binds the request to the Control Plane's operation, but is not in the digest), the expiry, the Authority's digest and the check. A digest mismatch prints `digest check: MISMATCH (the fields above hash to sha256:...) DO NOT APPROVE`; an unreadable entry prints `REFUSED: invalid_entry` and none of its fields. `approve` prints the same block and ends with `result: approved`; `deny` prints `result: denied`.

**Safe rendering.** Strings are quoted. Only printable ASCII is shown as it is, `"` and `\` are backslash-escaped, and **everything else** (controls, bidi marks, line/paragraph separators, zero-width and combining characters, every non-ASCII letter, lone surrogates) is shown as `\u{HEX}` of the code point. So nothing can reorder, hide or imitate text, a Cyrillic "a" is visible as `\u{430}`, NFC and NFD forms look different (the digest does not normalize), and a newline inside a value cannot start a fake line. The Authority already rejects control and bidi characters; this is the second layer. A `note:` line counts the escaped characters. A readable mode for non-ASCII text is not built.

### Tier policy (step 3a of #115)

- `policy [show]` prints the Authority's policy and its hash (the app recomputes the hash and refuses a reply that disagrees, or one without `kid` / `audience`).
- `policy set <careful|standard> [--prompt <action>]...` sends a complete new policy with `rev + 1`. It prints which actions "will no longer ask you" and "will start asking you". A change that lets more actions skip a person needs a console, a typed `yes` and one Windows Hello signature over `UTF8("albera.policy.v1") 0x00 kid 0x00 audience 0x00 <hash>`; a change that only adds prompts is sent as it is.

## GUI mode (`--tray`)

**Status: Proposed, NOT VERIFIED on a real desktop with a real Windows Hello.** Added for the easy-setup plan (`(c) Approval GUI`); the window logic is unit-tested, the screen and Hello are not. `AlberaApprover.exe --tray` replaces the typed `yes` with a window; the CLI `approve` stays as the fallback and behaves exactly as before.

```
AlberaApprover.exe --tray
   Windows Forms (a framework that ships with .NET; no package)         one tray per logon session (Local\AlberaApproverTray)
   TrayHost ── every 2 s ──▶ ApproverCommands.ListPendingAsync ──▶ the same pipe, the same server check, the same parser as `list`
      │ one request at a time
      ▼
   ApprovalWindow ◀── ApprovalPrompt (rules, no UI) ◀── MatchCode.Choices(approvalId, RECOMPUTED digest)
      │ click on the correct candidate ──▶ ApproverCommands.ApproveShownAsync ──▶ IPresenceSigner (Hello) ──▶ decide approve
      │ 2nd wrong candidate / "拒否する" ──▶ ApproverCommands.DenyShownAsync ──▶ decide deny
```

Starting it at logon (an HKLM `Run` entry) is the installer's job; the app registers nothing and writes no file. A second start in the same session exits at once. The Run key starts it for every account that logs on; the approver pipe lets in the approver account only, so a tray whose first `list` gets `access_denied` ends quietly (and shows no icon before that first answer). "Not reachable" (the service is still starting) keeps polling. The exe keeps the console subsystem so the CLI works, so `--tray` drops its console as the first step (a console window may flash for an instant when started from the Run key).

**Which window.** One window per pending request, oldest first; the second request onward waits and the tray text says `ALBERA 承認: あと N 件`. A window the person closes without deciding leaves the request pending at the Authority; it is not shown again until the tray menu item "待っている依頼を開く" (or a double click on the icon) asks for it. A request that left the list (decided, expired) is forgotten.

**What the window shows** (our own Japanese text; request strings are never used as labels): what the action does, the task text exactly as sent (`task.start`), the VM (`computerId`, and `vmId` when the action names one), the project, `purpose / action`, every other argument, the operation id, the expiry with a countdown, and the digest this app recomputed (`一致しました` or `一致しません`). Non-ASCII characters have a yellow background. Under Remote Desktop (`SystemInformation.TerminalServerSession`) a banner says the verification screen appears on the PC the person connects from (WebAuthn; see "WebAuthn presence").

**When there is no approve button.** The three match-code buttons are not even built when any of these holds (only `拒否する` is offered): the entry cannot be read (the contract refused it, e.g. a control or bidi character in a string), the digest recomputed from the shown fields differs from the Authority's, or any shown string has a control, format (bidi marks, zero-width, soft hyphen, BOM), line / paragraph separator, lone-surrogate, private-use or unassigned character. This is wider than the CLI's `\u{HEX}` rule on purpose: the window shows text as it is, so anything that can hide or reorder text blocks approval; a non-ASCII letter, a full-width space or an emoji is only highlighted.

**Match code.** `MatchCode.Choices(approvalId, recomputedDigest)` gives three candidates (the correct code and two decoys that are never another pending request's code, in a hash-determined order); they are the only approve buttons. The room shows the same 4 digits for the same request. One wrong pick shows a warning and disables that button; the second wrong pick sends `decide deny` (no Hello). The correct pick starts Hello. **Closing a window never resets the guesses.** The tray keeps each request's wrong picks (`WrongPickLedger`, in the tray process's memory, until the request leaves the list) and hands them to the next window of that request, where the earlier wrong button stays disabled and counted. Closing a window that has one wrong pick sends `decide deny` (the tray's "終了" closes the open window first, so quitting does the same); if that deny cannot be sent the wrong pick is still remembered. With two wrong picks on record no candidate is clickable (the third would be a certainty); only deny is left. Limit: the count lives in the tray process, so killing and restarting the tray, or a request that outlives it, starts from zero again; that needs a process of the same account (see "Known limits").

**No focus steal, no keyboard decisions.** The window is shown with `ShowWithoutActivation` and the taskbar button flashes (`FlashWindowEx`); it is created with the extended styles `WS_EX_TOPMOST | WS_EX_NOACTIVATE` (`CreateParams`, not the `Form.TopMost` property, which together with `ShowWithoutActivation` can still activate the window), so it is seen above other windows but never takes the keyboard focus. There is no default or cancel button; the buttons cannot take keyboard focus (`Selectable` off), so Enter and Space reach nothing, and the window swallows Enter and Space as well. A button raises its click only after a left mouse press on it (a `PerformClick` call is dropped). A synthetic click from another process of the same account (`SendInput`, UI Automation, a posted `BM_CLICK`) looks like a real one and is not stopped by this; that is inside "Known limits", and the last line of defence is Windows Hello. The choice buttons are disabled for the first second after the window is shown, after expiry, while Hello / the Authority call runs, and once the prompt is over; `拒否する` waits for the same first second and stops at expiry too (a reflex click on a button that just appeared decides nothing).

**No automatic approval.** There is no "approve all", "remember" or "approve on timeout". The only call that approves anything is `ApproveShownAsync` in `HandleChoiceAsync`, reached only from the click handler of a match-code button (source-guarded in `test/runtime-approver-source.test.mjs`: the call sites are counted and located).

**Reuse, no copy.** The list, the strict parse, the digest recompute and the refusal on a mismatch are `ApproverCommands` (`ListPendingAsync`, `ApproveShownAsync`); the presence message, the signer call and the `decide` request are the one private `SignAndDecideAsync` that the CLI `approve` (after its typed `yes`) also ends in; deny is the same `DenyCoreAsync` as the CLI. The GUI files contain no JSON, no digest and no wire verb (source-guarded).

**Windows Hello.** Hello runs on a thread-pool thread (the call blocks; the window stays alive) after the window is brought to the front (`SetForegroundWindow`, allowed because the person just clicked it). The window handle is **not** passed to Hello: the plain `KeyCredentialManager` call of the CLI is used. The planned `IKeyCredentialManagerInterop` call (open the credential with the window handle) is not written, because it could not be checked here: there is no Windows SDK header on the build PC, and the interface is called through a hand-written vtable, where a wrong slot order could call `RequestCreateAsync` (create / **replace** the key) instead of `OpenAsync`. What was measured (2026-11-03, Windows build 26300, `RoGetActivationFactory` + `IInspectable::GetIids` only; no credential opened, no prompt): the `Windows.Security.Credentials.KeyCredentialManager` factory implements `6AAC468B-0EF1-4CE0-8290-4106DA6A63B5` (the projection's `IKeyCredentialManagerStatics`) and two more IIDs, `6439895D-68C5-521B-9DC4-7C199794F0D8` and `30B1B9C9-61EF-43E8-88AC-CC433B38D1A6`; one of them should be the interop interface. Mapping them needs the SDK header (or a disassembly) on a PC that has it. Until then, "Hello in front of the window" rests on Windows placing its own prompt in front; the window is topmost and never activates, so it may sit above the prompt. That is an open check on the owner's PC (below), and the interop call is the follow-up.

**Only a real desktop and a real Hello can show** (not run by any test, here or in CI; the owner's PC, M14): (1) the layout and the Japanese text on a real screen; (2) that a window shown with `WS_EX_TOPMOST | WS_EX_NOACTIVATE` really takes no keystrokes while the person types in another window, and that the taskbar button flashes; (3) that the topmost window does not cover the Windows Hello prompt, and that the prompt appears at all for this exe; (4) that a real mouse click raises the button's click; (5) the Remote Desktop banner; (6) the console flash when the exe is started from the Run key; (7) that the enrolled Hello key is found from this exe.

**Results the window can show** (`ApprovalPrompt.ApproveResultText`): approved; Hello key missing / not ready or no connection (nothing was sent, the request stays pending, the person may click again); the Authority refused (its fixed code); Hello was cancelled or the outcome is unknown (the Authority fails the request; the Control Plane resubmits); an internal error.

**Known limits.** The tray exe is an ordinary same-user process like the CLI: any process of the account can still call Hello directly (see "Known limits"). The match code is a display aid, not an authorization: the Authority's check of the presence signature over the recomputed digest is. A first-second delay and a 3-way pick stop a reflex click; they do not stop a person who is determined to approve.

## Server identity (before the first write)

Same order and checks as `windows-broker-pipe-client` (copied; that project is not referenced): open with SQOS **identification** (the server learns who we are but cannot act as us) and specific rights `0x00120083` (never `GENERIC_WRITE`) -> on the connected handle read the pipe **owner SID**, the **server PID** and (service mode) the **session id** -> only then write the frame. Production expects the owner `NT SERVICE\AlberaApprovalAuthority`, the PID the SCM reports as RUNNING for service `AlberaApprovalAuthority`, and session 0. Any failed check is a pre-send code (66); a server that squats the pipe name receives 0 bytes. The expected pipe root, service name and owner are constants of the shipped build. The server image hash is not pinned (the Node client can; the approver has no place to get the hash from).

## Presence signing

`IPresenceSigner.Sign(byte[] message)` returns `Signed(signature)`, `Unavailable` (the key exists but Hello gave no proof: cancelled, locked) or `NotReady` (no usable key: Hello not supported or not set up, credential not enrolled, API unusable). The message is `"albera.presence.v1" 0x00 approvalId 0x00 actionDigest 0x00 challenge` (UTF-8), **built from the digest this app recomputed**, never the Authority's; the Authority rebuilds the same bytes from its own entry and verifies one pinned RSA-2048 key, RSA PKCS#1 v1.5 / SHA-256, a 256-byte signature. A signature therefore binds the id, the exact action and the entry's random challenge.

- `Signed` -> `decide approve` with the signature.
- `Unavailable` -> `decide presence_unavailable`; the Authority fails the request (final; the Control Plane resubmits).
- `NotReady` -> exit 69 with an `enroll` hint, **nothing sent**; the request stays pending.

A wrong signature makes the Authority finalise the request as `presence_mismatch`.

`WindowsHelloPresenceSigner` (`WindowsHello.cs`): `KeyCredentialManager.IsSupportedAsync()` (false -> `NotReady`), `OpenAsync("AlberaApprover.v1")` (`NotFound` -> `NotReady`; cancelled, locked, other -> `Unavailable`), then `RequestSignAsync(message)` over the exact message bytes. Only a `Success` with a 256-byte signature is `Signed`. Any exception from the API becomes `NotReady` (nothing is sent; no exception text is printed). The prompt Hello shows names the app, not the action, so `approve` prints the request and takes the typed `yes` first. The plain WinRT API is used, without a window handle; see "Open points".

## WebAuthn presence (phase 3 of `approver-webauthn.md`)

The owner reaches the host only over Remote Desktop, where `KeyCredentialManager` does not work. The Windows WebAuthn API (`webauthn.dll`) does: Remote Desktop forwards it, so Hello asks on the PC the person connects from. The contract (key record, `keys`, the proofs, the messages, the codes) is the "Wire contract" section of `approver-webauthn.md`; this section is what the approver does with it. Nothing here changes the Authority side: that is phase 2.

**The proof.** The approver builds the client data itself from the message it recomputed (never the Authority's): `{"type":"webauthn.get","challenge":"<base64url(SHA-256(message))>","origin":"albera://approver","crossOrigin":false}`. The relying party id is the constant `approver.albera.local`; user verification is required; attestation is none. `WebAuthnSigner` hands the client data and the allowed credential ids to the authenticator and sends an assertion only if it is for a credential that was asked for, its authenticator data satisfies the Authority's rule (exactly 37 bytes, the rp id hash, user present and user verified set, attested data and extensions clear; the backup flags and the sign count are not judged) and it has a signature. The frame then carries `"presence":{"kind":"webauthn","credentialId":"<b64url>","authenticatorData":"<b64>","signature":"<b64>"}` instead of the base64 RSA string. The client data is not sent.

**Which key signs** (`PresenceSigning`). The Authority's `keys` verb lists the registered keys (id, kind, credential id; no secret). Any registered WebAuthn key wins, with `allowCredentials` = all their credential ids, at the console and over Remote Desktop. Windows Hello (`KeyCredentialManager`) signs only when no WebAuthn key is registered **and** the session is not remote (`SM_REMOTESESSION`, read once at start). The legacy Hello presence stays the plain base64 RSA string; only a WebAuthn proof is the JSON object. A remote session with no WebAuthn key stops with `remote_session` (exit 69) and a hint ("Windows Hello does not work over Remote Desktop for this key; make a WebAuthn key with `enroll --webauthn --accept-unattested` and add it with the elevated `set-approver`"), **before the typed yes** (`approve`, `policy set`, `keys remove`) or **before any digit is offered** (the approval window shows the reason, has no match-code buttons, and offers deny only); nothing is asked, signed or sent. An Authority from before WebAuthn does not know `keys` and answers `request_invalid`: it has Hello keys only, so it is treated as "no WebAuthn key". Without a WebAuthn kit in the wiring (the unit tests, a test-faults build without `--test-webauthn`) the Authority is never asked for its keys and Hello always signs: exactly the behaviour before WebAuthn. If a WebAuthn key is registered and its prompt fails, the approver does not fall back to Hello.

**`enroll --webauthn --accept-unattested`.** Needs the opt-in (a WebAuthn key is made with attestation none, so it is not proven to be hardware-backed; without the flag: exit 65 `unattested_not_accepted`, nothing made) and a console. Makes the credential (one prompt, on the device that will hold the key; the console window is the parent), reads the authenticator data (the rp id hash, user present and verified, the credential id inside the data equal to the one returned, the COSE key read strictly), and builds the key record: `keyId` = `webauthn-` + the first 8 bytes of SHA-256 over the SPKI in lower-case hex, `alg` -7 (ES256, P-256) or -257 (RS256, 2048 to 4096 bits), the SPKI, the credential id. It refuses a key the contract would refuse. It prints the fields and `approverSid`, writes the canonical record JSON (the contract's key order, no spaces, no trailing newline) to `%LOCALAPPDATA%\Albera\approver-keys\<keyId>.json`, prints `attestation: none (accepted with --accept-unattested: this key is NOT proven to be hardware-backed)`, and then the next step, exactly: `next (the owner, in an elevated prompt; Windows asks for the administrator's consent): albera-host.ps1 -Mode set-approver -ApproverKeyFile "<that file>"`. The user id is fresh random bytes, so each run makes a new credential and never replaces another. **It does not register the key**: it never talks to the Authority, and there is no run-time add (a same-user process could get one signature at a real approval and register its own key). Only the elevated `set-approver`, behind UAC, adds a key to the Authority.

**`keys`.** `keys list` prints the Authority's keys (read only, no console). `keys remove <keyId>` needs a console, refuses locally an unknown key and the last key, stops with `remote_session` if nothing can sign, asks for a typed yes, asks for a `key_challenge` (op `remove`; the approver never sends op `add`), signs `albera.keyremove.v1` 0x00 keyId 0x00 challenge with any registered key (one prompt) and sends `key_remove`. The message is only the key id and the challenge: it needs no record of the key, so a key from another device (a lost one) is removed from here like any other; the registered key that signs may be a different one. A remove is reported done only when the reply's key list no longer shows the key. When the reply carries `"policyReset":true` (the removed key had signed the policy in force, so the Authority put the policy back to careful) the person is told so: `policy: set back to careful ...`. `policyReset` is accepted only as `true` and only in the `key_remove` reply. **There is no `keys add` and no `key_add` verb** (decision 2026-11-04, Zaku review of phase 2). A reply is accepted only in the contract's exact shape (entries, kinds, ids, base64url credential ids, no duplicates, at most 16 keys, a 22-character challenge).

**Record files** are the only file code in the approver (`KeyRecordFile.cs`, source-guarded): a file is created (`CreateNew`), never overwritten, deleted, moved or appended; the name is a derived key id. `enroll --webauthn` writes one, for the elevated `set-approver -ApproverKeyFile` to read; nothing else in the approver reads it. The file is an ordinary same-user file: whoever can write it can change what the installer is later told to pin, so the installer should show the key id and the owner should compare it with the one `enroll --webauthn` printed.

**Policy.** `policy set` (the loosening kind) uses the same route: the typed yes comes after the key choice, and `policy_set` carries the WebAuthn proof over `albera.policy.v1` ... when a WebAuthn key is registered. A change that only adds prompts never asks for keys.

**Window.** The approval window passes its own handle as the parent of the WebAuthn prompt (read on the UI thread, the prompt runs on a thread-pool thread). The Remote Desktop banner now says the verification screen appears on the connecting PC; the old text ("approve in front of this PC") was written for Hello.

**What the probe verified and what it did not.** The probe (2026-11-04, the owner's Remote Desktop session) ran `WebAuthNAuthenticatorMakeCredential` and `WebAuthNAuthenticatorGetAssertion` with the structure layouts and version-1 options that `WebAuthn.cs` reuses unchanged: create gave attestation format none, a 32-byte credential id, ES256, user present and verified; sign gave user present and verified, sign count 1, and a signature that verified; the console window handle worked. **Not run by anyone:** the approval window's handle as the parent; the cancel and error HRESULTs the code maps (`NTE_USER_CANCELLED`, `ERROR_CANCELLED`, `ERROR_TIMEOUT` = dismissed, everything else = nothing sent); an RS256 credential; a phone or a security key (the hybrid prompt); `allowCredentials` with more than one id; a registered credential that lives on a device that is not reachable; WebAuthn redirection turned off by policy; and `keys remove` end to end (one prompt), including the removal of a key whose device is not reachable.

**Frame size.** Frames are 1 to 2048 bytes (the Authority's limit is the same constant). Measured for a `decide` frame with a WebAuthn proof (the largest frame the approver sends; `key_remove` is smaller): ES256 374 bytes with a 32-byte credential id (1695 with 1023 bytes); RS256-2048 622 (1943 with 1023 bytes); RS256-4096 962 (2283 with 1023 bytes). Only an RS256-4096 key with a very long credential id goes over: the app then refuses before sending (`request_too_large`, exit 66).

## Build and the one dependency

`npm run build:approver` publishes `src/runtime/windows-approver/bin/Release/net10.0-windows10.0.19041.0/win-x64/publish/AlberaApprover.exe` (git-ignored, self-contained, about 100 MB with the .NET runtime) and writes `AlberaApprover.exe.manifest.json` (`{"sha256": ...}`, via `captureExecutableIdentity`). It only builds: no install, service registration, elevation, key, signing or Hello enrolment.

**Hardened build environment** (issue #102; all `build:*` scripts, shared helper `scripts/dotnet-build-env.mjs`): dotnet is taken only from `<ProgramFiles>\dotnet\dotnet.exe`, where the Program Files folder is read from HKLM (`C:\Windows\System32\reg.exe`, fixed path; `ProgramW6432Dir`, else `ProgramFilesDir`) and must agree with `HKLM\SOFTWARE\dotnet\Setup\InstalledVersions\x64` `InstallLocation` when that is set; never PATH and never the ProgramFiles environment variables; there is deliberately no override variable. Every MSBuild call gets `-noAutoResponse` and switches off the 12 `ImportUserLocationsByWildcard*` imports from the user's MSBuild folder. The child environment is an allowlist (TEMP, USERPROFILE, LOCALAPPDATA and a few more; SystemRoot, ProgramFiles and PATH are set from C:\Windows and the registry, PATH = System32 + the dotnet folder; APPDATA is a fresh empty folder, because NuGet still parses the user-level `NuGet.Config` even with `--configfile`), so MSBuild*, NuGet*, DOTNET_* (except three we set: no logo, no telemetry, no first-run work), DefineConstants and Albera* variables never reach the build. Restore is a separate locked step (`--locked-mode`, `--configfile scripts/nuget.publish.config`: `<clear/>` plus nuget.org only); publish then runs `--no-restore`. A project without `packages.lock.json` is refused. After each build the script prints two lines to compare two builds: `dotnet sdk <version>` and `sha256 <hash> <path>`.

The only external dependency is the **Windows SDK projection** for WinRT: the target framework `net10.0-windows10.0.19041.0` makes the SDK restore the targeting pack **`Microsoft.Windows.SDK.NET.Ref` version `10.0.19041.57`** from NuGet (Microsoft, signed; the nupkg is 12,719,136 bytes, about 12 MB, 75 MB unpacked in `~/.nuget/packages`; `Microsoft.Windows.SDK.NET.dll` of 24.9 MB is copied into the publish folder). It is not a `PackageReference`: the csproj pins it with `WindowsSdkPackageVersion`, and `packages.lock.json` (which records no targeting pack) only records the new target framework. Arch rule 11e (`scripts/approver-build-inputs.mjs`, tested by `test/approver-build-inputs.test.mjs`) is an **exact pin**: the csproj text must equal the string kept in the script (only CRLF/LF and trailing newlines are ignored), so any change to the csproj, including the pinned `WindowsSdkPackageVersion`, must change the script in the same PR; no `Directory.Build.props/.targets`, `Directory.Packages.props`, `global.json`, `nuget.config` or similar may exist from the project directory up to the repository root; nothing from the project directory up to the root (and no entry in the project directory) may be a symbolic link or junction; and the project directory holds only `.cs` files, the csproj and `packages.lock.json`. The first restore on a machine needs the network; after that it is in the NuGet cache. CI runs with the network.

## Attestation at enroll (issue #101)

`enroll` and `enroll --replace` ask Windows to attest the key they just made (`KeyCredential.GetAttestationAsync`) and keep it only when the answer is acceptable (`AttestationPolicy` in `HelloKeyStore.cs`, one place; the real and the fake key store both use it). `KeyCredentialAttestationStatus` has four values:

| status | meaning | enroll |
|---|---|---|
| `Success`, with a **non-empty certificate chain buffer and a non-empty attestation statement buffer** | Windows produced an attestation for the key | **accepted** (the only pass) |
| `NotSupported` (with empty buffers) | no attestation is possible for this key (Windows says this PC cannot attest it; **measured: this PC returns exactly this**) | **refused by default**; kept only with `--accept-unattested` (below) |
| `TemporaryFailure` | try later | refused, **also with the flag** (accepting it would let an unattested key through; run `enroll` again) |
| `UnknownError`, an exception from the API, a status name this code does not know (a future value), `Success` with an empty buffer, `NotSupported` with a non-empty buffer, another spelling (`success`, `notsupported`) | | refused, **also with the flag** |

A refusal removes the key that was just made (`KeyCredentialManager.DeleteAsync` on the fixed name, in the Hello file only; with `--replace` the old key was already replaced and is gone, as for any replace), exits **69** `attestation_refused` naming the status and buffer sizes, and prints no config value, so an unattested key is never left behind for `enroll --show` or `approve` to find.

**`--accept-unattested` (opt-in, `enroll` and `enroll --replace` only).** Measured on the author's PC (2026-11-01, read-only probe: open the existing credential `AlberaApprover.v1`, call `GetAttestationAsync`, no prompt): status `NotSupported` with empty buffers. Without an opt-in the owner could never enrol here, so `enroll --accept-unattested` (or `enroll --replace --accept-unattested`) keeps a key whose attestation is `NotSupported` with empty buffers, and nothing else. It does not weaken the other results: `TemporaryFailure`, `UnknownError`, an exception, an unknown status, `Success` with an empty buffer and `NotSupported` with a buffer are refused with the flag too (the hint then does not offer the flag). Without the flag, the `NotSupported` refusal removes the key and its hint names the flag. When the flag is used, `enroll` prints a fixed line every time and exits 0:

```
attestation: NotSupported (accepted with --accept-unattested: this key is NOT proven to be hardware-backed)
```

That line is the only record: it is **not** a fourth value in the Authority config. The Authority config reader has a strict key list (`AuthorityConfig.cs`), so an `approverAttestation` field would need an Authority change (and tests) that this PR does not make; the three config values are unchanged. `enroll --show` opens an existing key and says nothing about attestation, so the owner sees the line only at `enroll` time. The flag is parsed only for `enroll` / `enroll --replace` (flag last); with `--show`, `--check`, `--expect`, `approve`, `deny`, `list`, `policy`, twice, first or alone, the command line is not a command (exit 64) and nothing is done. The flag reaches nothing but the key store's `Create` (source guard). An unattested key is an RSA-2048 Hello credential that Windows will not vouch for as hardware-backed; everything in "Known limits" still applies to it.

**What a pass does and does not verify.** Verified: Windows returned status `Success` and two non-empty buffers, from the Hello API of this process. **Not verified by this program** (and the printed line says so): the certificate chain is not parsed or validated (no root pinned, no revocation, no check that it is a TPM vendor chain), the attestation statement's signature is not verified, the statement is not matched to the key's public key (no binding), and nothing is fresh (no challenge). The buffers are not stored or printed (only their sizes), so the Authority cannot check them later. So the line is "Windows says it attested this key", not proof for a third party; the Authority still pins the key by hand. **Observed on the author's PC:** `NotSupported` with empty buffers for the existing credential (a read-only probe; an `enroll` that creates a new key and attests it has not been run, so the status for a fresh key is assumed to be the same). A PC that returns anything other than `Success` or `NotSupported` gets `attestation_refused` even with the flag.

## Known limits (v1, unpackaged; final for the Hello key)

The approver is an unpackaged console exe, so Windows treats everything running as your account as one party. Plainly:

- **The self-check is not provenance.** `enroll --check` proves the key signs and matches its public key; another app of your account could have made that key first. Compare with the `approverKeyId` your own `enroll` printed (`--expect`).
- **Same-user processes are trusted.** Another app of the same account can create or open the credential `AlberaApprover.v1` before you do (so `enroll` refuses an existing key and `enroll --show` warns), and can call `RequestSignAsync` on it directly, with any message, without this program. The typed `yes` and the check in `approve` are not a boundary against such a process.
- **Hello's prompt does not show the action.** It names the app only. A process that gets a human to verify at the same moment (a racing presence message for another request, or an agent driving `approve` through a pseudo-console, which still counts as "not redirected") can have a different request approved than the one the person is looking at. The whole request (the id, every digest input, the digest and the recompute check) is printed, and the exact typed `yes` is taken, before the prompt (unit-tested: the text on screen at the moment Hello is called); that only helps a person who reads them.
- **MSIX does not fix this (measured 2026-11-01, issue #101).** The planned fix was to package the approver as a self-signed MSIX so Windows would scope the Hello key to the package family name. It was built and installed on the author's PC (family `Albera.LocalApprover_rfb9xr8x8ned2`, started through the WindowsApps alias), and `enroll --show` from the installed package printed the OLD key made by the unpackaged exe (`hello-951a135537287eae`). So `KeyCredentialManager` credentials of a full-trust packaged desktop app are per user account, not per package (the same is reported at https://learn.microsoft.com/en-us/answers/questions/5912130/what-is-the-security-boundary-of-windows-hello-key; Microsoft's per-app isolation applies to UWP / AppContainer apps). The packaging code was therefore removed again (decision `2026-11-01+approver-no-msix` in `spec/architecture.md`). **This limit is final for `KeyCredentialManager`: same-user processes remain trusted.** AppContainer was not tried: no documented key isolation, it would break the pipe to the Authority, and it is untested.
- Keep the account that approves free of untrusted software, approve only while no agent is driving the console, and treat a surprise Hello prompt as a reason to refuse.

## Open points (not verified; need the owner's machine)

- **Window handle.** (GUI mode, 2026-11-03: still open; "GUI mode" records the interface IDs measured and why the interop call is not written.) The plain `KeyCredentialManager` API is called without a window handle. Whether Windows shows the Hello prompt in front of a console process, and finds the credential from this exe, could not be tested without triggering Hello. If it does not, the follow-up is `IKeyCredentialManagerInterop` (`RequestCreateAsync` / `OpenAsync` with the console window handle); the CsWinRT projection does not contain that interop, so it would be hand-written COM. Nothing else changes (one class).
- **Credential scope.** Measured 2026-11-01: the credential is per user account even for an MSIX-packaged full-trust app (see "Known limits"). If the exe is rebuilt to another path or replaced, `approve` may report `presence_signer_unavailable` and `enroll --show` `not_enrolled`; run `enroll` (or `--replace`) again and update the Authority config. This path-change behaviour is not verified.
- **This PC at the time of writing.** `KeyCredentialManager.IsSupportedAsync()` returned `False` for a probe run from a non-interactive shell here, so Hello (PIN) may need to be set up first.
- **Provenance.** The Authority's open precondition: the pinned key must be proven to be a Hello key credential, not just any RSA-2048 key. `enroll` now refuses a key Windows will not attest ("Attestation at enroll"), but it does not verify the attestation, so the Authority still pins the key by hand and the precondition stays open in the strict sense.
- **Code signing.** No Authenticode certificate; SmartScreen may warn on first run of an unsigned exe. None is created here.
- **Policy knobs left.** Per-call timeout (10 s; the signing step is outside it); whether the typed `yes` stays once Hello shows its own prompt (it stays: the Hello prompt shows no details).
