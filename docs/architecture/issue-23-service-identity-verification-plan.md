## Service identity decision for the approved lab

Follow ADR-002's proposed two-service model. Run each service as its own virtual service account in an own-process service:

| Process | Logon account | Service SID | Required token shape | Minimum authority |
|---|---|---|---|---|
| Node Control Plane | `NT SERVICE\AlberaControlPlane` | `NT SERVICE\AlberaControlPlane` | Service SID enabled and present in `TokenRestrictedSids`; session 0; no admin groups or Hyper-V group | Read/execute signed CP files; write only its own state; connect to the fixed Broker pipe. No service-control, Broker-data, key, provider, shell, or Hyper-V rights. |
| C#/.NET Host Broker | `NT SERVICE\AlberaHostBroker` | `NT SERVICE\AlberaHostBroker` | Service SID enabled and present in `TokenRestrictedSids`; session 0; no admin groups or Hyper-V group | Read/execute signed Broker files/config; create the fixed pipe; read the pinned public key; read/write only Broker-owned journal directory. No network listener or arbitrary process execution. |
| Approval Authority | Separate service identity/process, not CP or Broker | Separate SID | Private key unavailable to CP/Broker | Sign only after independent human authorization. Key provider and user-presence ceremony remain a separate gate. |

Configure both SCM services with `SERVICE_SID_TYPE_RESTRICTED` (`sc.exe sidtype <name> restricted` equivalent). Keep one service per process: Windows requires all services sharing a process to use restricted service SID type if any one does. A restricted service SID adds a restricting-SID access check; it does **not** by itself remove user rights or prove least privilege. Do not grant `Se*` privileges unless a later, action-specific experiment identifies a required one. The default virtual-account service token already carries `SeImpersonatePrivilege` and `SeCreateGlobalPrivilege` (lab runs 1-3 measured both at high integrity), so each service is cut down to `SeChangeNotifyPrivilege` with `sc privs` (accept condition C1; installer precondition 6 below). Do not use LocalSystem, Administrators, `Hyper-V Administrators`, or NetworkService. The product has no approved remote resource requirement; outbound and inbound network access remain denied by policy. If a platform limitation prevents a virtual account, stop and revise ADR-002 before substituting LocalService.

Let SCM manage the virtual-account service logon. Do not add a broad user or group to “Log on as a service” to make the test start. Any required user-right assignment is an explicit deployment review item.

Microsoft documents `SERVICE_SID_TYPE_RESTRICTED` as adding the service SID to the process token's restricted SID list, along with World, the service logon SID, and the write-restricted SID; the change takes effect at the next service start. It also says all co-hosted services must use restricted SID type. [SERVICE_SID_INFO](https://learn.microsoft.com/en-us/windows/desktop/api/winsvc/ns-winsvc-service_sid_info)

`LocalService` has minimum local privileges and anonymous network credentials, while `NetworkService` uses the computer identity for remote access. Those built-in accounts are fallback comparison points, not the ADR-selected identities. [LocalService account](https://learn.microsoft.com/en-us/windows/win32/services/localservice-account), [Windows local accounts](https://learn.microsoft.com/en-us/windows/security/identity-protection/access-control/local-accounts)

### Object ACL policy

| Object | Read/use | Write/control | Explicit denial / rationale |
|---|---|---|---|
| Broker named pipe | Control Plane service SID: only `FILE_READ_DATA | FILE_WRITE_DATA | FILE_READ_ATTRIBUTES | READ_CONTROL | SYNCHRONIZE` (`0x00120083`; `READ_CONTROL` added so the client can read the pipe owner before it sends); SYSTEM/Broker as required | Broker service SID and SYSTEM manage/create the pipe instance | No Everyone, Users, Interactive, Guest, Anonymous, or Network ACE. No `FILE_APPEND_DATA`, generic write, or `FILE_CREATE_PIPE_INSTANCE`. Require first-instance and reject remote clients. Validate the actual client token, not message claims. |
| Broker journal directory, DB, `-wal`, `-shm`, backups | Broker SID; SYSTEM and administrator recovery identity | Broker SID; SYSTEM and administrator-controlled installer/recovery | Control Plane, Guest, Observer, and Approval Authority cannot read or write journal data. Restrict the parent directory so SQLite sidecars inherit the Broker ACL. Verify each file and directory after create/restore. |
| Pinned Approval Authority verification key | Broker reads; installer may verify during install | Installer/SYSTEM only | Public key confidentiality is unnecessary; integrity is essential. CP cannot replace Broker trust configuration. |
| Approval Authority private signing key | Approval Authority identity only; SYSTEM-backed key service only if the selected key provider requires it | Key provider/administrator ceremony only | No Control Plane, Broker, Guest, or Main AI read/export/sign rights. Prefer non-exportable CNG/KSP key; explicit human approval must gate signing. |
| Service executable and config | Corresponding service SID: read/execute | Signed administrator-controlled installer/SYSTEM | Neither service can write/reconfigure its executable, other service, service registry configuration, or trust anchor. |
| SCM service object | Installer/SYSTEM: create/configure/start/stop/delete; administrators retain recovery control | Installer/SYSTEM only Control Plane gets no start/stop/change/delete rights. Grant query-only status only if a reviewed feature actually needs it: the pipe client's server-identity check (`SERVICE_QUERY_STATUS` for the SCM-reported PID) now does, so lab step 4a decides whether to grant exactly that.

The Issue #22 prototype's same-user pipe DACL (one ACE for the Broker's own user SID, written out explicitly because `PipeOptions.CurrentUserOnly` cannot be combined with an owner) denial test below does not inspect a service pipe's live security descriptor. The Issue #21 Win32 mask evidence is same-user prototype evidence and must not be treated as proof of the service-SID DACL. Inspect the actual service pipe DACL and token groups/restricted SIDs during the separately approved lab.

## Denial test implemented without a second account

`test/runtime-windows-restricted-token-pipe.test.mjs` starts a disposable .NET Broker pipe under the current user's SID. A C# test helper creates a restricted token containing a synthetic restricting SID that is not present in the pipe DACL, impersonates that token only around a synchronous local pipe open, and asserts Windows denies the connection. This is an OS DACL/access-check result; no user, group, service, persistent ACL, or privilege was changed.

Local Windows evidence: the test passed **1/1**. The restricted token retained the same `TokenUser` as the test harness; only its restricting SID set differed. Therefore this proves restricted-token access checking against a live pipe, **not** cross-account denial, a Control Plane service SID, a restricted service process token, token revert behavior, or a service boundary. True distinct-user and service-SID tests remain **BLOCKED** pending a pre-provisioned non-admin test principal / service identity and explicit approval for the service lifecycle test.

## Reversible service lab runbook — executed 2026-10-30 in a disposable VM

### Preconditions

1. Use a disposable, fully patched supported Windows x64 VM with a snapshot and console recovery. Do not use a developer workstation with unrelated services/data.
2. Obtain explicit approval for the exact service names, signed test artifacts, service identities, temporary data directory, ACL ACEs, event-log channels, test time window, and rollback operator.
3. Confirm both service names are absent, the install/data roots are new dedicated paths, and the pre-test service/ACL inventories are saved outside the test roots. Never reuse or edit an existing service.
4. Stage only signed binaries. Prepare separate non-admin Control Plane and Broker identities, plus an independently controlled Approval Authority identity/key. Do not create users/groups in this issue.
5. Disable all Hyper-V action adapters; use only the synthetic no-op action and temp journal. Keep external network access denied and host/network isolation controls in force until separately reviewed.

### Preconditions for any installer (CISO review of the service host, 2026-10-30; `broker-service-hardening`)

The Broker now refuses to start (service-specific exit code 73, reason `config_untrusted` / `database_untrusted`) unless its config file and its database folder (plus any journal, `-wal`, `-shm`, `-journal` file that exists) satisfy the rule in `src/runtime/windows-broker/ServicePathGuard.cs`. Whatever installer is written later has to create them that way; creating them with the inherited `C:\ProgramData` ACL fails the check by design, and a service that cannot start is the safe outcome. Without this check `BUILTIN\Users` could pre-create `journal.sqlite` or a fake `-wal` (breaking replay protection) or pre-create the config.

1. Create the install folder, the config folder and the database folder **with inheritance removed** and an explicit DACL: `NT AUTHORITY\SYSTEM` and `BUILTIN\Administrators` full control, the Broker's service SID (`NT SERVICE\<name>`) Modify on the database folder only, read-only (or nothing) for everyone else. No other principal may hold write-data, append-data (add file / add subdirectory), delete-child, delete, write-DAC or write-owner, **including inherit-only ACEs**. `CREATOR OWNER` is accepted.
2. The owner of the config file, the database folder and the journal files must be SYSTEM, `BUILTIN\Administrators` or the service SID itself. Create the config as an administrator (owner `BUILTIN\Administrators`), never as a standard user.
3. None of these paths, nor any parent, may be a reparse point (junction, symlink, mount point), and the config must be written in the exact canonical long-form path the service is given (no 8.3 short names, no `..`, no UNC).
4. The check does **not** look at the ACLs of the parent folders (`C:\ProgramData` lets `Users` create sub-folders by default, so every real parent would fail). Keep the parents administrator-only for rename and delete (`DELETE`, `DELETE_CHILD`, `WRITE_DAC`, `WRITE_OWNER`); creating a *sibling* folder is harmless, replacing the broker folder is not. Why this matters (CISO re-review of PR #82): the database is checked at start-up but reopened per request, so if an ordinary user pre-created `C:\ProgramData\Albera`, they could grant themselves delete on the `broker` child and swap it for an empty journal between requests, replaying an unexpired receipt. Create the parent as an administrator before any user can. Since accept condition C3 the running Broker also holds the database folder open without `FILE_SHARE_DELETE` (`DatabaseFolderPin.cs`), so the folder cannot be renamed, deleted or swapped while the service runs; the parent rule still covers the time the service is stopped (and `service-check` run by an installer pins nothing).
5. Run `albera-windows-broker.exe service-check <config>` as the pre-flight (it prints `SERVICE_CONFIG=ok` or `invalid:<reason>`, creates and changes nothing) and treat any `invalid:` as a failed install.
6. **Least privilege (CISO accept condition C1, 2026-10-30).** Right after `sc create` and before the first `sc start`, run `sc privs <ServiceName> SeChangeNotifyPrivilege` for **both** the Broker and the Control Plane service. Without it the SCM gives each virtual-account service `SeImpersonatePrivilege` and `SeCreateGlobalPrivilege` at high integrity, which is what potato-class local escalation needs and which neither service uses (the Broker's peer check opens the client token at `SECURITY_IDENTIFICATION`; named pipes need no global-namespace privilege). The installer verifies with `sc qprivs <ServiceName>` (exactly `SeChangeNotifyPrivilege`) and treats anything else as a failed install; the lab asserts the live process token holds exactly that one privilege (`a_token` in `lab-guest.ps1`). The change takes effect at the next service start.
7. Journal folder pin (C3): nothing to configure. The running Broker holds the database folder open without `FILE_SHARE_DELETE`; an installer must not expect to rename or remove that folder while the service runs (stop the service first).

### Install and verify

1. Through an administrator-launched fixed installer (not an arbitrary script API), create the two own-process services on demand under their exact virtual accounts.
2. Set each service SID to restricted and each service's privileges to `SeChangeNotifyPrivilege` only (precondition 6); install service-object DACLs and protected file/directory ACLs before starting either service. Persist the exact service configuration and SDDL evidence.
3. Start Broker, then Control Plane. Record `QueryServiceConfig[2]`, service status/PID, service object SDDL, process TokenUser, enabled TokenGroups, TokenRestrictedSids, integrity label and session ID. Redact secrets and unrelated account identifiers.
4. Inspect pipe DACL via the kernel object; assert only the intended service/SYSTEM ACEs and exact access masks. Verify CP connects, a pre-existing second principal is denied by DACL, and a connected wrong token is denied by Broker token validation before journal/provider access.
4a. Control Plane pipe client verifies the Broker pipe server before it writes (`broker-server-identity`). The code path exists and passed only against same-user test servers; for each item below, run the helper as the Control Plane identity against the real Broker service pipe and record the result code and what the server received:
   - Owner SID vs an interactive squatter: stop the Broker, let a process of the interactive user create the pipe name, expect `server_identity_mismatch` and 0 bytes received (the squatter's owner is not `NT SERVICE\AlberaHostBroker`).
   - Restricted SID owner: with `SERVICE_SID_TYPE_RESTRICTED`, read the live pipe owner and confirm it equals the SID the helper derives with `LookupAccountName("NT SERVICE\AlberaHostBroker")`. If the default owner differs, confirm the Broker's explicit owner takes effect or that it exits 72 (`PIPE_OWNER_UNAVAILABLE`) instead of serving.
   - `SERVICE_QUERY_STATUS`: confirm the Control Plane account can open the Broker service with exactly `SC_MANAGER_CONNECT` and `SERVICE_QUERY_STATUS` (and nothing more) and that `QueryServiceStatusEx` returns RUNNING and the PID of the Broker process. Without that grant the helper must fail closed (`server_identity_unavailable`).
   - `OpenProcess` across accounts: the optional image-hash check opens the server with `PROCESS_QUERY_LIMITED_INFORMATION`. Record whether the Control Plane account may do that to the Broker process; if not, the hash check is `server_identity_unavailable` and must stay unconfigured in service mode.
   - Session 0: `GetNamedPipeServerSessionId` is 0 for the service; a Broker-lookalike in an interactive session is refused.
   - Effective access mask: inspect the live pipe DACL and the Control Plane account's effective rights on it. The helper's `0x00120083` open succeeds (including `READ_CONTROL` for the owner read); an open with `GENERIC_WRITE` / `FILE_APPEND_DATA` (pipe-instance creation) is denied.
   - Which process SCM reports (found while preparing the lab, 2026-10-30; host-tested, not yet service-tested): the helper compares the SCM-reported PID with the **pipe creator's** PID. A launcher that starts the Broker as a child makes SCM report the launcher, so a correct Broker is refused with `server_identity_mismatch` (`test/runtime-windows-service-lab.test.mjs` shows both cases). The Broker therefore has to be the SCM service process itself. The first lab run (2026-10-30) used the lab tool to host the Broker's assembly in the service process (`mode: inproc`) as a stand-in. **Service host implemented (2026-10-30, `broker-service-host`): the Broker now has a `service <config>` entry that calls `StartServiceCtrlDispatcher` itself, so SCM reports the pipe-creating PID without the shim. Host-tested only; VM verification pending** (checks `g_two_requests_one_service_then_stop` and `g_fatal_exit_codes` in `lab-guest.ps1`, below).
   - A stopped service never reaches the owner check: with the Broker service not RUNNING, the SCM lookup fails first and the helper reports `server_identity_unavailable` (pre-send), not `server_identity_mismatch`. To observe the owner mismatch the service must be RUNNING while another principal holds the pipe name (the lab keeps the service RUNNING without a pipe with the tool's `linger` option).

5. As each service identity, attempt bounded read/write probes against the other's state, the Broker DB/WAL/SHM, verification-key file, private signer key, SCM service config, and a synthetic host-protected path. Expected outcome is denial except the matrix grants above. Do not probe arbitrary host paths.
6. Exercise Broker restart and approval replay only with a temp DB and signed synthetic receipt. Preserve `UNKNOWN`; assert one journal claim and zero provider effects.
7. Capture Windows Security/System service events and test logs; verify no key bytes, receipts, user secrets or private paths appear.

### Rollback

1. Stop only the newly created named services (two, or three when the lab's "other principal" service is used). Confirm their PIDs have exited; do not terminate unrelated processes.
2. Delete only the services created for this run. Wait for SCM removal and verify both names are absent.
3. Remove only the dedicated temp install/data roots after preserving the test report, journal metadata, ACL/SDDL evidence, and logs. If cleanup is denied, leave the artifacts and report them; do not take ownership or broaden permissions to force deletion.
4. Compare the service, ACL, user/group, privilege, firewall, and network inventories with the preflight snapshots. Any unexpected delta blocks cleanup completion and requires the approved administrator to restore that exact delta.

These steps require admin rights and persist SCM/ACL state until rollback. They were intentionally **not run**. Windows documents that service-object DACL changes persist until the service is removed, and service configuration updates require explicit SCM rights. [Modifying a service DACL](https://learn.microsoft.com/en-us/windows/win32/services/modifying-the-dacl-for-a-service), [Service configuration](https://learn.microsoft.com/en-us/windows/win32/services/service-configuration)
