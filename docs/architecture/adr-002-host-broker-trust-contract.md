# ADR-002 implementation slice: Windows Host Broker trust contract

- **Status:** Accepted (Broker/IPC scope) on 2026-10-30 after the C1 lab re-run passed (16 PASS / 1 BLOCKED, [evidence](benchmarks/issue-23-least-privilege-lab-2026-10-30.json)) (CISO accept conditions C1-C3, decision-log row `2026-10-30+adr002-broker-accept-conditions`). The main ADR-002 file (`decisions/ADR-002-control-guest-trust.md`) remains **Proposed**; Hyper-V rights, the approval authority, the installer and the Guest side are outside this scope and stay NOT VERIFIED
- **Scope:** Windows service identity, local IPC, request authorization, and a Mock IPC conformance test
- **Non-goals:** installing a service, changing ACLs or privileges, implementing a Windows named pipe, enabling Hyper-V, or changing the read-only Observer

This document makes the first Host Broker boundary reviewable without claiming that a Windows security boundary has been implemented. The production transport, installer, approval authority, and exact Hyper-V rights remain gates.

## Process and identity contract

| Process | Identity and rights | Must not have |
|---|---|---|
| Control Plane | Dedicated per-service virtual account (`NT SERVICE\AlberaControlPlane`) with its service SID enabled and restricted. It owns its own project/control database and may connect to the Broker pipe. Required privileges: `SeChangeNotifyPrivilege` only. | `SeImpersonatePrivilege`, `SeCreateGlobalPrivilege` or any other privilege; LocalSystem, Administrators or Hyper-V Administrators membership; Broker binary/config/state write access; host credentials; arbitrary process or shell authority. |
| Host Broker | Separate virtual account (`NT SERVICE\AlberaHostBroker`) with a restricted service SID. It owns its private replay/authorization state and fixed Provider adapter. Required privileges: `SeChangeNotifyPrivilege` only. | LocalSystem by default; shared identity with Control Plane; generic command execution; network listener; Guest-reachable endpoint; `SeImpersonatePrivilege`, `SeCreateGlobalPrivilege` or any other privilege (see "Least privilege" below). |
| Installer / service manager | Administrator-controlled installation/update path. Service configuration and image replacement are writable only by the installer trust root and Windows service-control principals. | Control Plane ability to replace, reconfigure, stop, or start the Broker service. |

**Least privilege (accept condition C1).** A virtual-account service token gets `SeImpersonatePrivilege` and `SeCreateGlobalPrivilege` by default and runs at high integrity, which is the setup potato-class local escalations need. Neither service needs them, so the installer restricts each service to `SeChangeNotifyPrivilege` (bypass traverse checking; every process has it) with `sc privs <name> SeChangeNotifyPrivilege` before the first start, and the lab asserts that the live token holds exactly that (`a_token`).

Why the Broker does not need `SeImpersonatePrivilege`: the peer check calls `ImpersonateNamedPipeClient` and reads only the thread token's user SID; it never acts as the client. The Control Plane's pipe client opens the pipe with `SECURITY_SQOS_PRESENT | SECURITY_IDENTIFICATION`. The impersonation level a server gets is capped by the client's SQOS, and the client allows identification only, so the privilege (which matters only for levels above identification) cannot change the outcome; a server without it may still impersonate at identification level and query the token. Evidence so far: the host tests run the Broker under a non-elevated token that holds no `SeImpersonatePrivilege` and the peer check passes, but that is same-user (the kernel would allow it anyway), so it is weak; the cross-account proof is the VM lab re-run with `sc privs` applied (every request check passes only if the peer check still works). If that re-run shows the peer check failing without the privilege, keep `SeImpersonatePrivilege` for the Broker only, record exactly which call failed and why, and re-open this section. The earlier lab note that the Broker holds `SeImpersonatePrivilege` "needed for the peer check" was wrong: it was only the default.

Neither service is to be placed in a broad administrator group. **Superseded for the Broker by "Amendment 2026-11-03" below:** the owner approved putting the Broker's service SID (only the Broker's, never the Control Plane's) into Hyper-V Administrators, because Windows offers no narrower grant; the operation-layer allowlist there is what keeps the Broker from using the mutation capability that group carries. The minimum Windows rights needed for each eventual Hyper-V API call have not been established. Until a reviewed per-action rights matrix is proven on supported Windows versions, the Broker must not be installed with Hyper-V mutation capability. The service-account selection also depends on a signed, administrator-controlled installer and update chain; that chain is not implemented here.

## Named-pipe candidate

- Endpoint: `\\.\pipe\ALBERA\HostBroker\v1`; local named pipe only. No TCP fallback.
- The Broker creates the first pipe instance with an explicit protected DACL and first-instance semantics; name squatting or an existing unexpected pipe fails closed.
- DACL principals: Broker service SID and `SYSTEM` receive server control; the Control Plane service SID receives only the read/write data, attribute, owner-read and synchronization rights needed to exchange messages: `FILE_READ_DATA | FILE_WRITE_DATA | FILE_READ_ATTRIBUTES | READ_CONTROL | SYNCHRONIZE` (`0x00120083`; `READ_CONTROL` is what lets the client read the pipe's owner before it sends, see below). Do not grant pipe-instance creation rights (`FILE_CREATE_PIPE_INSTANCE` / the pipe alias of `FILE_APPEND_DATA`) to the client, and open the pipe with these specific rights, never `GENERIC_WRITE`.
- Do not grant `Everyone`, `Authenticated Users`, `Users`, `Interactive`, `Network`, or `Anonymous`. The service configuration DACL is separate and must not let Control Plane reconfigure the Broker.
- Set remote-client rejection (`PIPE_REJECT_REMOTE_CLIENTS`), bounded message mode, one request per connection, and a 4 KiB maximum request message (2 KiB until the guest.command claim, see "Amendment 2026-10-31"; replies are far smaller). Close on malformed, oversized, or trailing data.
- **Client verifies server: owner SID + SCM PID + session 0, SQOS identification, before write.** The Control Plane side opens the pipe with `SECURITY_SQOS_PRESENT | SECURITY_IDENTIFICATION` (the server can inspect the client but never act as it). On the connected handle, before any byte is written, it requires: the pipe's owner (`GetSecurityInfo(OWNER)`) equals the Broker service SID (`NT SERVICE\AlberaHostBroker`); `GetNamedPipeServerProcessId` equals the PID the SCM reports for the running Broker service (`QueryServiceStatusEx`, state RUNNING); `GetNamedPipeServerSessionId` is 0; and, when configured, the SHA-256 of the server's image matches. Any mismatch is `server_identity_mismatch`, any failure to establish the facts is `server_identity_unavailable`; both are pre-send (the receipt never left, a retry is safe). The Broker, for its part, sets the pipe owner explicitly to its own SID and refuses to start if it cannot. Node cannot do this itself, so `src/runtime/windows-broker-client.mjs` launches a small .NET helper (`src/runtime/windows-broker-pipe-client/`) whose SHA-256 manifest is checked first; a failed check is `helper_unavailable`.
- Authenticate every connection from the kernel-provided named-pipe client token. A message's `subjectId`, SID, PID, approval claim, or other identity string is never proof of caller identity. PID is diagnostic only.
  - **Enforced by the Broker today (accept condition C2 ii):** the thread token's **user SID** (`WindowsIdentity.User` after `ImpersonateNamedPipeClient`) must equal the configured Control Plane SID, compared as an exact string. The configured SID is itself restricted at load time to a virtual service account (`S-1-5-80-` plus five sub-authorities, never `S-1-5-80-0`) or a SID the system resolves to a user (never a group or alias), so a group membership can never satisfy the check. A mismatch, or any failure to read the token, answers `denied` before the journal or the Provider is touched.
  - **Not checked by the Broker (known gap):** `TokenRestrictedSids` (that the service SID is among the restricting SIDs), the enabled or deny-only state of groups, the token's session ID (session 0), the integrity level, and the logon type (service or interactive). This contract used to list "enabled Control Plane service SID" and "service session 0" as peer checks; nothing in `Program.cs` reads them. What stands in for them: the pipe DACL grants the data rights (`0x00120083`) to that one SID only, so the kernel's own access check (including the restricting-SID pass for a restricted service token) has admitted the caller before the Broker runs; and a virtual-account SID is held by the service's own process (a process that can mint a token with that user SID, SYSTEM or an administrator, is outside this threat model). The gap matters if the configured SID is an ordinary user: that user in any session, from any process, then passes. The production configuration is the virtual account. Closing it (reading `TokenRestrictedSids`, `TokenSessionId` and `TokenIntegrityLevel` from the already-open identification token and denying on a mismatch) is open work, not a precondition of this acceptance.
- Impersonate only at identification level to inspect the peer token. Fail closed on impersonation/token-query failure. Always revert before Provider work; if `RevertToSelf` fails, terminate the Broker process. Never run Provider work under the caller token.

The exact SDDL mask and token-group rules must be validated against the supported Windows versions using the native pipe APIs before production deployment. The contract intentionally excludes broad generic write access; the client must not be able to create another server instance or alter the pipe security descriptor.

## Control Plane ↔ Broker request contract

**Wire shape (normative, accept condition C2 i).** Each direction is one frame: a 4-byte little-endian length followed by UTF-8 JSON, at most 4 KiB for a request (2 KiB until the guest.command claim) and 256 bytes for a reply. The request is `{ "receipt", "signature" }` (both base64; the signature is ECDSA P-256 / SHA-256 over the receipt's bytes with the pinned authority key), or `{ "receipt", "signature", "action" }` for a guest.command receipt (see "Amendment 2026-10-31"). Replies are exactly `{ "ok": true, "state", "action" }` or `{ "ok": false, "code": "denied" }`. The fields of the bounded `broker.operation.request` envelope (protocol version, unique request UUID, `operationId`, `expectedGeneration`, `actionDigest`, plus the Lease, project, policy, purpose and expiry binding) are the **signed content of the receipt** (JSON inside the base64 `receipt`), not a second frame around it; the Broker verifies the signature first and only then reads them. The receipt contains no caller identity, action-specific arbitrary arguments, host path, VM-native ID, shell text, PowerShell, executable name, or credential. `src/runtime/windows-broker-client.mjs` speaks this shape and enforces the 4 KiB request bound; the Broker refuses a larger frame while reading it, before the peer check. The Broker:

1. derives the caller only from the pipe token and requires the configured Control Plane service SID;
2. loads the exact journaled operation and current Lease/generation using Broker-trusted state;
3. verifies a single-use authorization receipt bound to operation ID, action digest, Lease ID/generation, project, policy version, purpose, and expiry; the receipt signer/key must be unavailable to the Control Plane process;
4. permits only the fixed typed actions `create`, `inspect`, `start`, `stop`, and `destroy`, with action and provider arguments resolved from the trusted record;
5. atomically consumes the authorization and records the operation ID/request ID before a side effect; duplicate operation or request IDs never call the Provider again;
6. returns only the fixed response schema, observed state, timestamp, and allowlisted error code. Exception messages, paths, native identifiers, guest output, and secret-shaped error codes are discarded.

**Prototype status (2026-10-30).** The frame above is what `src/runtime/windows-broker/Program.cs` implements. The prototype binds only the receipt fields its fixed `synthetic.noop` action needs; it does not yet check the project, purpose or request-UUID fields listed above. The client now verifies the pipe server's identity before it writes (2026-10-30, `broker-server-identity`): a .NET helper started by the Node client opens the pipe with SQOS identification and checks the owner SID and the server process ID (and, when configured, the server image SHA-256) on the connected handle; the Broker sets the pipe owner to its own SID. Because the prototype Broker exits after one request, this is what stops a process that takes the name afterwards from reading a signed receipt and forging a reply. It is **same-user verified only**: the tests use real and hostile same-user processes with an expected PID and owner SID supplied directly. The service path (SCM-reported PID, `NT SERVICE\AlberaHostBroker` as owner, session 0) is implemented but has never run against a real service; that is NOT VERIFIED and belongs to the approved lab (#23). The client must not be wired into any caller until then.

The exact authorization-receipt authority and protected store are still an ADR-002 decision. A database writable by a compromised Control Plane is not Broker-trusted state. The mock test exercises the current SQLite journal's single-use approval and expiry checks; it does not implement an independent verifier, choose a production signer, protect state with Windows ACLs, or provide a human approval service. A verified Windows service SID authenticates the Control Plane process; it does not by itself prove human approval or protect against a compromised Control Plane.

The low-privilege Control Plane and privileged Broker are separate processes with separate identities, binaries, writable directories, and service configuration. The Control Plane cannot invoke arbitrary OS commands or reach the Provider directly. The Broker accepts only the named typed protocol above. The existing Observer remains read-only and has no route, credential, pipe handle, or composition path to the Broker.

## Journal folder pinning (accept condition C3)

`ServicePathGuard` checks the journal folder once, but every request reopens the database by path. The service therefore opens the folder once at start (after the guard passed; `DatabaseFolderPin.cs`) with a data right (`FILE_LIST_DIRECTORY`) and **without `FILE_SHARE_DELETE`**, and holds the handle for the life of the serve loop. While it is held, a rename or delete of the folder fails for every principal, so the folder cannot be swapped for an empty one between requests (the replay that would enable is the reason for the guard). Requests keep using the same path. The guard is run again on the pinned folder. A folder that cannot be pinned ends the start with exit 73 (`database_pin`). The pin lasts only while the service runs: while the service is stopped, or between STOP and the next START, the folder is protected by its ACL and by keeping its parents administrator-only (installer precondition 4 in `issue-23-service-identity-verification-plan.md`). Tested on the host (`runtime-windows-broker-service-hardening.test.mjs`, "accept condition C3"); the VM lab does not repeat it.

## Amendment 2026-10-30: journal schema version, exact duplicate, inspect (issue #84)

> **Superseded in part by "Receipt v2" below (same day).** The current journal version is **3** (version 2 is migrated forward like version 0); inspect is now the receipt-less request `{inspect:{operationId}}` on the authenticated pipe and answers with action `synthetic.inspect`; the claim action allowlist is `synthetic.noop`. The exact-duplicate rule below still holds (the reply now also carries `replayed: true`). Read the bullets below as the history of version 2.

This is an amendment to the Accepted Broker/IPC scope; it changes the Broker's journal and adds one fixed action, and **does not change** the receipt fields, the signature scheme, TTL handling, the Lease/generation binding, the frame `{ "receipt", "signature" }`, the 2 KiB bound, the pipe, or either reply shape. Decision-log row `2026-10-30+broker-journal-parity`.

- **Schema version.** The journal carries `PRAGMA user_version` (the Node store's mechanism; the DDL and the number commit in one transaction). Current version: 2. The unversioned journal of #22 / #23 (a six-column `claims` table, version 0) is migrated forward at start-up: `request_digest` is added, every row is kept (digest NULL). A missing or empty file is created at version 2 by the first claim. Anything else is refused **before the pipe exists**, for `serve` and for the service alike: a version above 2 (`BROKER_FATAL=JOURNAL_NEWER`), version 1 / a negative version / a table or column set that is not exactly the known one (`JOURNAL_UNSUPPORTED`), a file SQLite cannot read (`JOURNAL_UNREADABLE`). The fixed exit code is **76** (service-specific exit code 76 under the SCM); nothing is written to a refused file, not even a `journal_mode` switch. There is no downgrade. If the version or shape changes while the service runs, each request is a plain `denied`.
- **Exact duplicate.** `request_digest` is the SHA-256 of the 4-byte little-endian receipt length, the receipt bytes and the signature bytes. A request whose uniqueness check collides is an exact duplicate only when the **same operationId** is recorded with the **same digest**; the Broker then returns the recorded state in the unchanged success shape `{ "ok": true, "state", "action": "synthetic.noop" }` and writes nothing. It is denied, as before, when the receipt differs (also: same bytes with a different signature), when another operation reuses a receiptId or approvalId, or when the stored row has no digest (a migrated row). The receipt checks (signature, issuer, audience, action, digest, Lease, generation, policy, expiry) still run first, so an exact duplicate of an expired receipt is denied. Consequence for callers: a first claim and its exact replay produce the same reply; the reply to a claim means "this operation is claimed and its outcome is the recorded state", never "execute now" (a Control Plane that gets `UNKNOWN` must reconcile, not retry the effect).
- **Inspect.** The action allowlist is exactly `synthetic.noop` and `synthetic.inspect`. An inspect request is the same signed twelve-field receipt with `action` `synthetic.inspect` (its `actionDigest` is the SHA-256 of that string) and the `operationId` to look up; it goes through the same pipe, the same peer check, the same frame and the same validation. The Broker opens the journal read-only (never creating it, never migrating it), writes no row, and does not consume the receipt, `receiptId` or `approvalId` (an inspect receipt can be sent again within its lifetime). It answers `{ "ok": true, "state": <recorded>, "action": "synthetic.noop" }` (the action of the inspected operation) or `denied` when there is no record, no journal file, or the journal is not at the current version. The reply carries no new field because the Node client accepts exactly `action,ok,state`; a caller knows it sent an inspect. Only `UNKNOWN` exists as a recorded state today. Moving `UNKNOWN` to a final state (reconcile against a Provider result) is not implemented: it depends on the receipt format of the Approval Authority design that is still open.

## Receipt v2 (enforced by the Broker since 2026-10-30; Approval Authority built, not deployed)

**Status.** Enforced. Since PR #90 the Broker accepts only receipt v2 (config `authorityKeys: [{kid, spki}]`, 1–2 pinned P-256 keys; a v1 `publicKey` config is refused with exit 73). Requests on the authenticated pipe are told apart by their key set: `{fence:{computerId}}` → `{ok, brokerEpoch, leaseGeneration, brokerChallenge}` (single-use 128-bit challenge, at most 64 kept, wiped when the epoch is bumped at start); `{receipt, signature}` → claim (challenge consumed, claim inserted and clock mark raised in one transaction; an exact duplicate returns the recorded outcome with `replayed: true`); `{inspect:{operationId}}` → read-only state, no receipt. Journal v3 keeps `broker_state` (epoch, lease generation, clock high-water) and `challenges`. At start the configured `generation` is a floor: higher advances the journal (revoking older generations), lower refuses start with exit 76 (`JOURNAL_GENERATION_REGRESSED`). The clock mark rises on every start, fence and accepted claim; a request when `now < mark − 30 s` is refused (`clock_rollback`). The Approval Authority (`src/runtime/windows-approval-authority/`, PR #89, see `approval-authority.md`) signs v2 receipts only after the approver's Windows Hello key co-signs the exact digest; it is built and tested with fakes, and not yet deployed (real Hello key, machine signing key and service install are owner decisions). `leaseId` and `policyVersion` come from the Broker config (required, contract id grammar; PR #92) and the fence reply carries `leaseId`, which the pipe client helper relays as a required field. The installer must give the Broker and the Authority the same `policyVersion` (no runtime cross-check). The Control Plane talks to the Authority's submit pipe through `src/runtime/approval-authority-client.mjs` (PR #93), via the same verified helper (owner SID + PID before the first write).

**Receipt.** The signed content is the JSON bytes exactly as sent (ECDSA P-256 / SHA-256 as in v1; verify the signature first, then validate those same bytes). Exactly 22 keys, no others, all required, flat, at most 1280 bytes (so base64 plus the 2 KiB frame still fits):

| key | type / format |
|---|---|
| `v` | integer, 2 |
| `kid`, `approverKeyId`, `operationId`, `idempotencyKey`, `projectId`, `computerId`, `leaseId`, `policyVersion` | id: `^[A-Za-z0-9][A-Za-z0-9._:-]{0,63}$` |
| `issuer` | `albera-approval-authority`; the schema also allows `albera-test-[a-z0-9-]{1,32}`, which production rejects |
| `audience` | `^[a-z][a-z0-9-]{0,63}$`; the relying party supplies the value it expects |
| `purpose` | `broker.operation` or `guest.command` |
| `action` | an action of `purpose`: `environment.create/inspect/start/stop/destroy`, `synthetic.noop` (broker.operation); `task.start/cancel`, `workspace.inspect`, `synthetic.noop` (guest.command) |
| `approvalId`, `receiptId` | lowercase UUID |
| `nonce`, `brokerChallenge` | 128 bits as unpadded base64url, canonical form (22 characters, last one in `A Q g w`) |
| `actionDigest` | `sha256:` + 64 lowercase hex |
| `leaseGeneration`, `brokerEpoch` | integer >= 1 |
| `iat`, `exp` | integer Unix seconds >= 1 |

The reader is strict: duplicate keys, `null`, arrays, nested objects, fractions, exponents, `-0`, leading zeros, integers above 2^53-1, lone surrogates, a BOM, comments, trailing commas and trailing data are all `malformed`. Checks run in a fixed order and the first failure is the verdict (a code and, only when useful, a fixed field name or `$extra`; never attacker text): `invalid_context`, `malformed`, `schema`, `version`, `issuer`, `action_pair`, `ttl`, `not_yet_valid`, `expired`, `binding`, `action_digest`.

- **Time.** `exp - iat` must be in 1..300 seconds (the Authority issues 120 by default); `iat <= now + 30`; `now < exp`. The clock is injected (Unix seconds).
- **Bindings.** The caller supplies, from Broker-trusted state, `audience`, `purpose`, `operationId`, `idempotencyKey`, `leaseId`, `leaseGeneration`, `brokerEpoch`, `brokerChallenge`, `policyVersion`, and the trusted action DTO (which also gives `projectId`, `computerId`, `action`). Any difference is `binding`. A missing or malformed piece of context is `invalid_context` (fail closed).
- **Digest.** The receipt's `actionDigest` is never trusted. The validator recomputes it from the trusted DTO and the receipt `purpose` and compares. The Authority computes the digest from the DTO it resolved itself; a digest sent by the Control Plane is not an input anywhere.

**Action digest v1.** The DTO is exactly `{action, projectId, computerId, args}`; `args` is a flat map (at most 16 entries, keys `^[a-z][A-Za-z0-9]{0,31}$`) of string (at most 256 UTF-8 bytes, well-formed, no control, line/paragraph separator, bidi or left/right-mark characters), safe integer, or boolean. Strings are never normalized, so NFC and NFD forms hash differently and must be shown to the human as the exact string. The digest is `sha256:` + lowercase hex of SHA-256 over

```
"albera.action-digest.v1" 0x00  enc(purpose)  enc(dto)
enc(string) = 0x53 u32be(utf8 length) utf8      enc(int) = 0x49 i64be      enc(bool) = 0x42 0x00|0x01
enc(map)    = 0x4D u32be(count) then enc(key) enc(value) for each entry, keys sorted by ordinal byte order
```

The domain prefix and the purpose make the same DTO hash differently per purpose; key order and JSON whitespace/escaping do not matter because the encoding is built from parsed values. A binary encoding was chosen over a canonical JSON text (JCS-style) because number, escape and Unicode handling differ between Node and .NET JSON writers.

**Differences from v1.** `expiresAt` becomes `iat` + `exp`; the digest is now over the DTO (v1 hashed the action name) and is lowercase with a `sha256:` prefix (as in `boundary-protocols.mjs`); `projectId`, `computerId`, `purpose`, `brokerEpoch`, `brokerChallenge`, `nonce`, `kid`, `approverKeyId` are new; ids are at most 64 characters (the boundary validators allow 128, which would not fit 22 fields in the frame).

**Evidence.** `test/runtime-broker-contract.test.mjs` runs `test-vectors.json` through the Node code and checks the schema file equals the validator's field table. `test/runtime-broker-contract-dotnet.test.mjs` builds the C# sources in a temp directory (`test/receipt-v2-dotnet-harness/`, skipped without a .NET 10 SDK) and requires identical digests, preimage bytes, verdict codes and fields for every vector. The preimage encoding was also cross-checked once with an independent Python encoder.

**Not decided here (left to the Broker / Authority work).** How the Broker issues and remembers `brokerChallenge` / `brokerEpoch`; the single-use store keyed on `receiptId` / `approvalId` / `nonce`; the `kid` to public key pinning; how `approverKeyId` is attested; the per-action `args` schemas; and the Authority's own request protocol.


**Restore of a journal backup (issue #84, 2026-10-31).** There is no separate restore mechanism: every start raises the epoch and deletes every outstanding challenge, so a receipt fenced before a backup, or fenced and claimed after it, is refused after the backup is restored (`challenge_unknown`), and receipts cannot outlive their TTL (300 s cap). A restored journal whose generation is below the configured floor is advanced to it; one above it refuses the start (exit 76). Claims recorded after the backup are lost by design; the operator must treat their operations as UNKNOWN and inspect / reconcile. Host-tested (`runtime-windows-broker-journal.test.mjs`, "restoring a backup of the journal") and run under the real service identity in the disposable-VM lab (checks `m1`–`m4`, `docs/architecture/benchmarks/issue-84-broker-parity-lab-2026-10-31.json`, 25 PASS / 0 FAIL / 1 BLOCKED). Clock rollback stays host-tested only.

## Amendment 2026-10-31: the Broker claims an approved `guest.command` / `task.start` receipt (issue #115 follow-up, step A1; provisional)

Until now a claim could only name `broker.operation` / `synthetic.noop`: the Broker fixed that DTO itself, so no receipt for work in a VM could ever be claimed. Decision-log row `2026-10-31+broker-task-start`. Implemented, host-tested with fakes; **not yet run in the disposable-VM lab**.

- **Claim frame.** Two keys, `{ receipt, signature }`, is unchanged (synthetic.noop). A third key, `action`, is new: base64 of the UTF-8 JSON action DTO `{ action, projectId, computerId, args }`. Any other key set, or an `action` that is not a string, is the fixed `request` denial.
- **The DTO is not trusted by itself.** After the signature check the Broker parses it with the contract's strict reader, validates it as a `guest.command` DTO, and requires: `action` is `task.start`; `projectId` and `computerId` equal the receipt's; `args` is `{ task: <non-empty string> }` alone or, since step 4 of #115, with exactly the two args an attested `task.start` names its VM by: `vmId` (a lowercase GUID) and `expectedGeneration` (an integer >= 1) (contract string rules: well-formed, no control / bidi characters, at most 256 UTF-8 bytes). Refusals are `DENY=action_invalid` (does not parse, or breaks a contract rule or the `{ task }` shape) and `DENY=action_mismatch` (another action, project or computer). The DTO then goes to `Receipts.Validate` as the trusted DTO: the Broker recomputes the action digest from it and compares it with the digest the Authority signed. The Authority's signature over that digest is what authenticates the DTO; a task that differs by one byte is `DENY=action_digest`.
- **Expected context.** For the three-key form `purpose` is `guest.command`; every other binding (audience, operationId, idempotencyKey, lease id and generation, broker epoch and challenge, policy) and every challenge check is exactly as for synthetic.noop. A `broker.operation` receipt in a three-key frame and a `guest.command` receipt in a two-key frame are both `DENY=binding`. A v3 receipt with basis `policy` for `task.start` was `DENY=basis_action` at first. Since step 4 of #115 (2026-10-31) `task.start` is an attested policy action: such a receipt is accepted only with `attestationDigest` and a well-formed `args.vmId`, and refused as `DENY=attestation` otherwise (`approval-tiers.md`, "Step 4 as built").
- **Reply.** A claim success names the action that was claimed (`task.start` or `synthetic.noop`), also on an exact replay. The Node client checks that the reply names the action it sent.
- **Frame limit.** A request is at most **4096 bytes** (was 2048), in the Broker, the Node client (`maxRequestBytes`) and the pipe client helper (which keeps 2048 for the Approval Authority's own pipe). The receipt (at most 1280 bytes) and signature fill most of 2 KiB; the DTO does not fit without the change. Replies stay at 256 bytes.
- **Journal.** No migration (user_version stays 3). The claim row does not record the action; the receipt's `action` field, which `Validate` has bound to the DTO, names it in the reply, including on a replay.
- **Not decided here.** Other `guest.command` actions (`task.cancel`, `workspace.inspect`) and `task.start` args other than those above are refused by this Broker; nothing starts a process yet (the Broker records the claim as `UNKNOWN`).

## Amendment 2026-11-03: the Broker performs the room's desktop operations (option C; owner-approved, design only)

The gated room (`room --require-start-approval`) needs to see and drive the screens of VMs that already exist and run. Until now it did that from the calling user (`src/runtime/hyperv-desktop/desktop-io.ps1`), which on the owner's PC is the Control Plane account `albera-cp`, and `albera-cp` has no Hyper-V rights (`host-install.md`, "known consequence"). The owner chose option C on 2026-11-03: **the Broker performs these operations, and the Control Plane gets no Hyper-V rights.** Decision-log row `2026-11-03+broker-desktop-option-c`. Nothing below is implemented yet; this section is the contract the implementation PRs are reviewed against.

### Why Hyper-V Administrators, and what that costs

- **No narrower OS grant exists.** Hyper-V's own role-based authorization (Authorization Manager, AzMan) is deprecated, and membership in `BUILTIN\Hyper-V Administrators` (`S-1-5-32-578`) is the supported way to give a non-administrator access to the virtualization WMI provider. That membership is all-or-nothing: it grants every Hyper-V operation on every VM (define, modify, destroy, state change, checkpoints, device settings), not only the two this amendment uses.
- **It is effectively host-administrator.** A public technique (2020) escalates a Hyper-V Administrators member to SYSTEM through the Virtual Machine Management Service. The design therefore treats the Broker, once it holds the group, as a host-administrator-equivalent process. Its own code, not the OS, is what limits it to the operations below.
- **Why this is still better than giving it to the Control Plane (option A, rejected).** The Control Plane runs the AI-driven room (Node, external model API, guest-derived screen content). The Broker is a small C# service with no network listener, no child processes, a fixed request schema and a tree-hashed build, reviewed under the security merge tier. Concentrating the unavoidable host-admin-equivalent right in the smaller, audited process is the ADR-002 split this contract already requires.
- **The Control Plane stays where it is.** Its "Must not have" row above is unchanged: no Hyper-V Administrators membership, ever.

### Two-layer rights matrix

The ADR-002 gate "the Broker must not be installed with Hyper-V mutation capability until a reviewed per-action rights matrix is proven" is met in two layers, and **both** must be proven before the installer grants the group on a real host:

| Layer | What enforces it | What it allows | Proof |
|---|---|---|---|
| OS | Membership of the Broker's service SID in `S-1-5-32-578`, added and removed only by the installer (`-GrantHyperVToBroker`) and recorded in the install record | Everything Hyper-V offers (see above) | Nested-Hyper-V lab measurement (below): not a member is refused, a member succeeds, separately for a restricted and an unrestricted service SID |
| Operation | The Broker's code: a fixed allowlist of WMI namespace, classes and methods, reached only through the typed desktop pipe; VMs resolved only from Broker config | Exactly the rows below | A unit test pins the allowlist (any new class or method fails it); a disposable-VM run drives both operations through the real service |

Operation-layer allowlist (namespace `root\virtualization\v2` only; WMI is called in-process through COM, never through PowerShell or a child process):

| Desktop operation | Class / method | Bounds | Needs |
|---|---|---|---|
| `desktop.capture` | `Msvm_ComputerSystem` read where `Name` equals the configured VM GUID; its realized `Msvm_VirtualSystemSettingData`; `Msvm_VirtualSystemManagementService.GetVirtualSystemThumbnailImage` | width and height 64..1920; at most one capture per 200 ms per session; PNG reply at most 8 MiB | a `view` or `act` session |
| `desktop.input` | `Msvm_Keyboard.PressKey`, `ReleaseKey`, `TypeKey`, `TypeText`; `Msvm_SyntheticMouse.SetAbsolutePosition`, `SetButtonState`, `SetScrollPosition` | the step bounds of `desktop-io.ps1` today: at most 256 steps, virtual-key 1..254, button 1..3, position 0..4095, wheel -1200..1200, printable-ASCII text at most 512 characters, `sleep` 0..10000 ms per step and 12000 ms per request; keys and buttons pressed in a failed request are released | an `act` session with the current lease generation |

Everything else is refused before WMI is touched, in particular: every other `Msvm_VirtualSystemManagementService` method (`DefineSystem`, `ModifySystemSettings`, `DestroySystem`, and the rest), `RequestStateChange`, `Msvm_Keyboard.TypeCtrlAltDel`, every snapshot / checkpoint class, any other namespace, a VM that is not in the Broker config, and any VM name or GUID sent by the caller.

**VM identity.** The Broker config gains `computers: [{ computerId, vmId }]` (contract id grammar; `vmId` is a lowercase GUID). The caller names only a `computerId`; the Broker resolves the GUID and queries by `Name`, never by `ElementName` (a display name another member of the group could reuse). The installer converts the owner's `-VmName` to the GUID once, at install time.

**Out of scope for the first gated run** (the gated room refuses them): guest capture, done checks and the guest helper (they need guest credentials, which no Broker config holds), and `task.start` checkpoint attestation (it changes VM settings and creates checkpoints, which is mutation). Each needs its own amendment.

### Desktop pipe

A second endpoint, so that high-frequency capture never queues behind the single serial claim pipe:

- **Endpoint** `\\.\pipe\ALBERA\HostBroker\desktop\v1`. The same protected DACL (Broker service SID and SYSTEM full control; the Control Plane SID only `0x00120083`), explicit owner, first-instance and remote-client-rejection rules and the same per-connection peer check (thread token user SID equals the configured Control Plane SID) as the claim pipe. Up to 16 concurrent instances.
- **Session.** The first frame of a connection is `{ "open": { "computerId", "mode" } }` with `mode` `view` or `act` (and, for `act`, `"operationId"` and, optionally, `"leaseGeneration"`; see "Implementation status (step 7)" below). After an accepted open, each frame is one request: `{ "capture": { "width", "height" } }` or `{ "input": { "steps": [...] } }` (steps exactly as in the table above). A connection idle for 60 s is closed. `view` sessions accept only `capture`.
- **Frames.** 4-byte little-endian length plus UTF-8 JSON, request at most 16 KiB. A capture reply is a JSON header frame `{ "ok": true, "width", "height", "bytes" }` followed by one binary frame of exactly `bytes` PNG bytes (at most 8 MiB); every other reply is at most 256 bytes; a refusal is the fixed `{ "ok": false, "code": "denied" }` and closes the connection. The reason goes to the Broker's own log only.
- **Implementation status (step 4, `view` only; Proposed / NOT VERIFIED).** `DesktopPipe.cs` / `DesktopProtocol.cs`. The config's `pipeName` is one plain segment, so the endpoint is `<pipeName>_desktop` (the backslash path above is the logical name); it exists only when the config has `computers`. All 16 instances are created at start (the first with the first-instance flag) and each is served by its own task. An accepted `open` is answered `{ "ok": true }`; a capture that fails is denied (`act` and `input` are step 5, below; in a `view` session an `input` frame is still denied).
- **Capture limits.** One capture at a time in the whole Broker (the WMI scripting API boxes every byte of `ImageData`, about 236 MB at 1920x1920), and a pixel cap of 1920 x 1080 on top of the 64..1920 bounds. Within a session a capture that comes sooner than 200 ms after the previous start waits (it is not refused); a capture that waits more than 30 s for the single slot is denied.
- **Evidence.** Host tests drive the real service loop over the real pipe (everything above except a successful capture); the success path is only the opt-in live test (`ALBERA_HYPERV_DESKTOP_VM_ID`, read only), because a fake WMI would need a seam in the shipped binary. Not yet run as a service in the VM lab.
- **Implementation status (step 6, the client side; Proposed / NOT VERIFIED).** The pipe client helper gains a desktop mode (`windows-broker-pipe-client/DesktopSession.cs`, started as `... desktop`) and Node gets `src/runtime/windows-desktop-broker-client.mjs` with its Fake `fake-desktop-broker-client.mjs` (`captureVmScreen` / `sendVmInput` / `close`, a drop-in for the prototype's two calls). One helper process is one session (a `view` session per computer for captures, an `act` session per computer, operationId and leaseGeneration for input; a newer lease replaces the older session) and lives until Node closes its stdin; Node and the helper exchange 4-byte-length frames on stdin / stdout, the PNG as a binary frame.
- Before the first byte (the `open`) the helper runs the claim helper's own `OpenVerified` on the connected handle: access `0x00120083` with SQOS identification, pipe owner = the expected SID, server PID = the SCM's for the service (state RUNNING), session 0, optional image SHA-256 (Zaku MEDIUM 3 of #164: `<pipeName>_desktop` can be created by any local user while the Broker is stopped). The helper accepts only a pipe name ending in `_desktop`, builds the `open` itself from validated ids, checks every reply against the bounds above (header 256 bytes, PNG exactly `bytes` and at most 8 MiB), and any failure or refusal ends the session. Deadlines: an open timeout (default 5 s) and a request timeout (captures 20 s, input 45 s), both enforced by the helper with a grace in Node; an unused session is closed after 45 s, before the Broker's own 60 s.
- Evidence: host tests drive the real helper against the real Broker service loop (a `view` refusal, `act` opens with and without a real `task.start` claim), against hostile same-user pipe servers (wrong PID, owner or image, a squatter: 0 bytes written) and against a Node stand-in for the desktop pipe (the success path up to exactly 8 MiB, and replies that lie). A successful capture from a real VM is only the opt-in live test (`ALBERA_HYPERV_DESKTOP_VM_ID`, read only); no input is sent to a real VM. The service identity path is lab-only (#23). Not wired into the room.

### Desktop lease (held by the Broker)

ADR-009's desktop-control lease moves from Node into the Broker for the gated room:

- An `act` lease exists only for an `operationId` whose `task.start` claim the Broker has recorded. The claim creates it: `desktopSessionId` = that `operationId`, `computerId` from the claimed DTO, `generation` = previous generation for that computer + 1, expiry = claim time + at most 60 minutes. A newer claim for the same computer revokes the older lease (its `act` sessions are closed).
- The lease lives in Broker memory only. A Broker restart loses every lease, which fails closed: input stops until a new `task.start` is approved.
- `view` needs no lease. The authenticated Control Plane may watch any configured computer, as the room does today with its read-only HUMAN lease. Recorded as a known exposure: whoever controls the Control Plane can see those screens; it already can.
- **Implementation status (step 5, `act` and the lease; Proposed / NOT VERIFIED).** `DesktopLeases.cs`, `DesktopPipe.cs`, `DesktopProtocol.cs`. `BrokerRequests.cs` grants the lease right after a three-key `task.start` claim is written to the journal, never for a replay (the claim reply and the journal schema are unchanged); the table lives in the desktop host and is empty after every start. Only computers in the config get a lease; the generation counts per computer from 1 and keeps counting after an expiry; the deadline is the Broker's **monotonic** clock (`Environment.TickCount64`, never a wall-clock time) at the claim + 60 minutes, so setting the system clock back cannot stretch a lease. A claim whose signed `args.vmId` is not the VM the config binds to that computer makes no lease (log word `LEASE=VM_MISMATCH`; the claim reply is unchanged); a claim with no `vmId` is unchanged (Zaku review of #166).
- An `act` open must carry exactly `computerId`, `mode`, `operationId` and, optionally, `leaseGeneration` (an integer >= 1), and must match the current, unexpired lease of that computer (when `leaseGeneration` is left out, the `operationId` alone decides: see step 7). The session ends with the fixed denied frame when a newer claim replaces the lease or the lease expires; `view` sessions are never affected. In an `act` session `capture` and `input` are accepted; `input` is checked against the adapter's `DesktopStep` limits, runs one request at a time per computer, and asks for the lease again when it gets its turn; the wait for the turn ends when the lease does, and a request that is already running stops before its next step (a `sleep` step ends early) when the lease ends, after the adapter released every key and button it holds (the logged word is the lease's, `lease_revoked` or `lease_expired`). A step already inside WMI is not interrupted. The Broker stops (exit 80) if an input request has not returned after 5 minutes, as it does for a capture.
- The adapter releases keys and buttons left pressed by a failed input on a new WMI connection when the release on the failing one fails, once (Zaku MEDIUM 3 of #161). Evidence: host tests drive the real service loop with real claims over the claim pipe, and the adapter and the lease table against a fake WMI and a fake clock; input is never sent to a real VM (the `desktop_unavailable` ending stands for "reached the adapter"). Not yet run as a service in the VM lab.
- Not decided here (provisional default in brackets): per-input human approval [no; the `task.start` approval covers the lease's input]. Human takeover and releasing a lease on request are listed under "Implementation status (step 7)" below: as built, neither exists in the gated room.
- **Implementation status (step 7, room wiring; Proposed / NOT VERIFIED; decision-log row `2026-11-03+room-gated-broker-desktop`, provisional).** `room --require-start-approval` takes every screen and input through the desktop Broker client (`room-approval-wiring.mjs`: the settings' `broker.pipeName`, a service-name expectation (required; a PID or an `imageSha256` is refused: the Control Plane's restricted identity cannot open the Broker's process, lab 2026-11-03, so an image hash would always end `server_identity_unavailable`; swapping the Broker's image needs an administrator and is outside the threat model), and `desktop.helperPath` / `desktop.helperSha256`; `computers` maps the room's VM names to computer ids); it builds no Hyper-V prototype. Guest capture, `--checks` and workspace checks, the guest password file and a `task.start` attestation are refused at start (`runtime_room_gated_out_of_scope`, exit 1, one fixed line, before the API key is read).
- **Generation-less act open (the Control Plane never learns the Broker's generation, because a claim's reply does not carry it).** An `act` open may leave `leaseGeneration` out: the Broker then joins the lease that is current for the `operationId` (still `lease_unknown` for any other operation, still `lease_generation` when a generation is named and differs). The accepted reply to every `act` open is `{ "ok": true, "leaseGeneration": n }`, the generation of the lease joined; the helper relays it and refuses a reply that lacks it, differs from a named one or has extra keys, and the Node client measures "newer" with it: a call for an older lease never closes a newer lease's session (Zaku LOW of #168). The hands' desktop session is the claimed operation: `task-start-gate` returns `{ ok: true, operationId }` and `agent-fleet` makes that the lease's `desktopSessionId`. What stops the hands, as built (no human takeover exists): the room's HUMAN lease (`room-view`) is display only, it is what the room's own screen captures use and nothing in the room installs it for an AI loop (each loop's driver checks a fixed AI lease). The only stop is a person choosing `stop` on a decision card, which calls `fleet.stopVm` and ends that VM's loop in Node (or the fleet closing on Ctrl+C / the budget). It does **not** touch the Broker: the Broker's lease for that operation stays valid until a newer `task.start` claim for the computer replaces it or its deadline passes (at most 60 minutes), and input keeps being accepted on any `act` session that names it. That is acceptable only because the one process holding the operation id, the Control Plane, has stopped using it; a hostile or compromised Control Plane is not stopped by it (the `task.start` approval and the 60-minute bound are the limit). The driver's own check (`assertLeaseCurrent`: a lease whose owner is not the AI's is refused before the Broker is asked) is tested, but is not a takeover mechanism by itself.
- **Not decided / follow-up (post-step-7): an operation that releases the lease on the Broker side** (for example a `desktop.release` request on the desktop pipe, or revoking on `stop`), so that `stop` and a future human takeover end the Broker's lease and close its `act` sessions at once instead of waiting for expiry. It needs its own amendment (a new typed request, its authorization, and what it does to input that is mid-request). Until then a stopped room leaves up to 60 minutes of live lease.
- **Helper watchdog (Zaku LOW of #168).** The desktop session's timer callback checks an `armed` flag under the same lock that writes the answer, so a callback that fired just before the answer cannot follow it with a timeout.

### Open risk to measure first

The Broker runs with a **restricted** service SID. Whether a restricted token can call DCOM / the WMI provider and the Virtual Machine Management Service is unknown. The nested-Hyper-V lab measures it before any Broker code depends on it. If the restricted SID fails, the fallback is `sidtype unrestricted` for the Broker only, which weakens a recorded accept condition and so needs the owner's decision; nothing proceeds on that branch without it.

**Measured 2026-11-03 (nested-Hyper-V lab, `lab-vm.ps1 -HyperV`, [evidence](benchmarks/broker-hyperv-rights-lab-2026-11-03.json), 14 PASS / 0 FAIL / 3 BLOCKED / 13 MEASURED).** Four virtual-account services, each with only `SeChangeNotifyPrivilege`, against a running inner VM: with a **restricted** service SID, every Hyper-V call after the WMI connection is `Access denied` (`0x80041003`), **even though `S-1-5-32-578` is enabled in the token**: the restricting-SID pass of the access check fails, because the restricting SIDs do not include the group. With an **unrestricted** service SID, a member can find the VM, read the management service and take a thumbnail; a non-member cannot see the VM. Keyboard and mouse calls by the unrestricted member ended `0x80004005` in the probe (BLOCKED: unproven, most likely the probe's COM call, since PR #161 found that reading a WMI result by property name fails from the second call on). **Consequence: the Broker cannot perform these operations with `sidtype restricted`; option C needs the owner's decision on the fallback.**

**Owner decision (2026-11-03): option A, the Broker as a whole runs with an unrestricted service SID** (rejected: B, a separate desktop-only service, which keeps the claim path restricted but adds a process and an IPC channel). Why acceptable: once the Broker is in Hyper-V Administrators it is host-administrator-equivalent anyway, so the restricting-SID write limit protects little; the operation-layer allowlist stays the boundary. What changes and what does not:

- The installer sets `sc sidtype AlberaHostBroker unrestricted` **only together with** `-GrantHyperVToBroker`; without the grant the Broker stays `restricted` exactly as today. The drift check (`albera-host-lib.ps1`, `sid_type_not_restricted`) learns the same pairing: unrestricted is expected exactly when the install record says the grant was made.
- Still required either way: `SeChangeNotifyPrivilege` only (`sc privs`), virtual account, no network listener, no child process, the pipe DACLs and the peer check above. The Control Plane stays `restricted` and never gets the group.
- The lab's service-identity checks keep asserting `restricted` for the default install; a `-GrantHyperVToBroker` install gets its own expected token shape.
- **Re-run with the PR #161 adapter (2026-11-03, [evidence](benchmarks/broker-hyperv-rights-lab-2026-11-03-adapter.json), 21 PASS / 0 FAIL / 2 BLOCKED / 15 MEASURED).** As the unrestricted member: the real adapter's capture returns a valid 640x480 PNG, and the raw keyboard call now succeeds (the earlier E_FAIL was the probe reading a WMI result by property name). The synthetic-mouse call is permitted but returns 32768 (method failed, not access denied): the inner VM has no guest OS, so the VMBus synthetic mouse has no driver to talk to; the adapter's input sequence starts with a move and so stops there (`input_failed`). Restricted SIDs are still denied everything; non-members see nothing. **Proven:** the rights matrix for every allowlisted call, and adapter capture under the service identity. **Still open:** adapter mouse input against a VM with a guest OS, to be shown by the first end-to-end gated room run (after step 8 of the order above); the WMI call shape is the one the prototype has driven on real guests.

### Known limit: the helper pin in the Control Plane settings (provisional; decision `2026-11-03+cp-settings-pin-scope`)

`control-plane\` gives `albera-cp` full control (its journal needs it), so `albera-cp` itself can rewrite `albera.approval.json` and point `desktop` at a fake helper. The pin (`desktop.helperSha256`) therefore guards against a room settings mistake or a mixed-up repository build, not against a hijacked `albera-cp`. Even then the fake helper holds no Broker lease, so its input does not reach the VM. Moving the settings into an administrator-only folder is a follow-up, not decided here.

### Known limit: what the helper's SHA-256 pin covers (provisional; decision `2026-11-03+cp-helper-pin-scope`)

The pipe client helper is published self-contained but not as a single file, so its SHA-256 (the manifest and the `helperSha256` pin, for every mode including `secret`) covers `albera-windows-broker-pipe-client.exe` only, not the .NET runtime and library files beside it. What closes the gap today: setup's tree hash covers the whole `bin\pipe-client` folder at install time, and `bin` is under Program Files, which only administrators can write (administrators are outside the threat model). Publishing the helper as a single file, so that one hash covers everything it loads, is a later task.

### The `_vm` pipe

A third endpoint, for the requests that take long (a checkpoint is about 20 s) or that only read the Broker's own record. Neither fits the claim pipe (one serial connection; its client waits 5 s by default and at most 30 s, `BROKER_CLIENT_LIMITS`) or the desktop pipe (screen and input only).

- **Endpoint** `<pipeName>_vm` (logical name `\\.\pipe\ALBERA\HostBroker\vm\v1`), created only when the config has `computers`, like `_desktop`. The name must stay a plain pipe name of at most 128 characters.
- **Same pipe rules as the claim pipe:** protected DACL (Broker service SID and SYSTEM full control; the Control Plane service SID only `0x00120083`), explicit owner = the Broker service SID, first-instance, remote clients rejected, the per-connection peer check (thread token user SID equals the configured Control Plane SID), identification-level impersonation only, one request per connection. The pipe is created with `LocalPipe.cs` (`CreateNamedPipeW`), **not** with .NET's `NamedPipeServerStreamAcl`, which cannot set `PIPE_REJECT_REMOTE_CLIENTS`: an account on the DACL could then reach it over SMB (measured 2026-11-01, #142).
- **Frames.** 4-byte little-endian length plus UTF-8 JSON, read with the contract's strict reader (`StrictJson`: depth 2 for a request, depth 3 for a reply that carries an attestation). A request over the limit is refused while it is read, before the peer check, as on the claim pipe.
- **Instances and order.** 4 instances, created at start. Requests for the same `computerId` run one at a time in arrival order; different computers run in parallel. The restore and power-on workers take the same per-computer turn, so a worker never overlaps an attest.
- **Time.** The client gives up after 180 s. The Broker's own deadline for one request is 150 s from the moment it read the frame (waiting for its turn counts). At the deadline the Broker answers `denied`, stops waiting for WMI, and does not cancel a job that is already running (`Msvm_ConcreteJob` is read-only, below); what that job leaves behind is an orphan or an UNKNOWN outcome (C7).
- **Refusal.** Every refusal is `{"ok":false,"code":"denied"}`. The reason is a fixed word in the Broker's log and never on the wire. For `attestTaskStart` a refusal means "no statement": the Control Plane takes the person path (approval-tiers.md: unknown means prompt) and does not retry in a loop.

Limits (every row is pinned to `broker-vm-wire-vectors.json` by the test; proposed values are the lead's to change together with this table):

Requests and replies (one top-level key names the request; the body has exactly the keys listed, no others):

| Request | Exact keys of the body | Reply on success |
|---|---|---|
| `vmState` | `computerId` | `{"ok":true,"generation":3,"restorable":true,"state":"ready"}`: `generation` an integer >= 1, `restorable` a boolean (true means a restore claim would be accepted now), `state` one of `ready`, `restoring`, `fenced`; `restorable` is never true while `restoring` |
| `attestTaskStart` | `actionDigest`, `computerId`, `generation`, `leaseGeneration`, `leaseId`, `operationId`, `projectId`, `vmId` (the 8 items) | `{"ok":true,"attestation":<envelope>}` |
| `attestNetwork` | `computerId`, `generation`, `leaseGeneration`, `leaseId`, `projectId`, `vmId` (the 6 items) | `{"ok":true,"attestation":<envelope>}` |

Value rules: ids follow the contract id grammar; `vmId` is a lowercase GUID (a trailing newline is not one); `generation` and `leaseGeneration` are integers 1 to 2^53 - 1; `actionDigest` is `sha256:` plus 64 lowercase hex characters. A key the Broker owns (`network`, `checkpointId`, `checkpointType`, `observedAt`, `expiresAt`) is refused like any other extra key: the Control Plane has no way to say what the Broker observed.

The envelope is the existing one, unchanged: `{attestation, digest, keyId, signature}` with the body of `task-start-attestation.mjs` (domain `albera.task-start-attestation.v2`, 14 keys) for `attestTaskStart` and of `network-attestation.mjs` (domain `albera.network-attestation.v1`, 10 keys) for `attestNetwork`. The reply's own key `attestation` holds the whole envelope. The body echoes the request's bindings; the Control Plane and the Authority verify it with the existing verifiers.

**`attestTaskStart`, in this order; the first failing step answers `denied` and nothing after it runs.**

1. The computer is in `computers`, `vmId` is its configured VM, and the Broker's attestation key is configured and can be opened.
2. Fences: `leaseId` is the config's, `leaseGeneration` is `broker_state.lease_generation`, `generation` is `vm_state.generation`, and `vm_state.state` is `ready`.
3. A row for this `operationId` already exists: take the re-sign path below.
4. Free space on the snapshot volume is at least the floor (K2).
5. Revoke the computer's desktop lease (see "Lease revocation").
6. Read the VM's checkpoint type: it must be ProductionOnly.
7. Read the network: it must be `none`.
8. `CreateSnapshot`; wait for the job within the deadline; the new snapshot must read back as a Production checkpoint (how the Broker tells is NOT VERIFIED, N2).
9. In one transaction, insert the `checkpoints` row (`attested`, `statement_digest` NULL) only if `vm_state.generation` and `state` are still what step 2 saw. Otherwise no row and no statement; the snapshot is an orphan (K3).
10. Read the network again: `none`.
11. Sign with the Broker's key. `observedAt` is the Broker's clock at this step, the TTL is 60 s, `checkpointType` is `production`, `network` is `none`. Store the statement's digest in the row's `statement_digest`, then reply.

**Re-sign (the same `operationId` again).** The row must be `attested` for the same computer, VM, generation and `actionDigest`; any other row is `denied`. The Broker does not take another checkpoint: it revokes the lease, re-reads the checkpoint type, the network and that the snapshot still exists, reads the network again, signs a new statement and replaces `statement_digest`. Only the newest statement of an operation can be claimed.

**`attestNetwork`.** Steps 1 and 2 (with `state` `ready` required, so it is refused while `restoring` or `fenced`), then read the VM's network once and sign what was observed: `none`, `present` or `unknown`. It takes no checkpoint, writes no row and revokes nothing. The Authority judges the value.

**`vmState`.** Reads the journal only (no WMI), so it answers at once. The room shows what it says.

**What a statement is.** `attestTaskStart` signs only `network: none` with `checkpointType: production`; any other observation is `denied`, never a weaker statement. The key is a CNG machine key, non-exportable, usable only by the Broker's service SID (N7, C6); its public half and `keyId` are what AGM-2 registers with the Authority (`PinnedAttestationKey.cs`).

**Config additions (provisional; the lead decides the shape).** One optional key, `attestation: { "keyName": <CNG key name>, "keyId": <contract id> }`, both fields required when the key is present; `keyName` is 1 to 64 letters, digits, dots, underscores and hyphens. Without it the `_vm` pipe answers `vmState` and refuses both attest requests, which is the safe fallback. The installer creates the key (AGM-2) and writes the name; the Broker never creates one.

### Claim pipe: two more actions, wider states

- **Three-key claim.** `{receipt, signature, action}` now accepts three actions, and the purpose follows from the action: `task.start` is `guest.command`; `environment.start` and `environment.restore_checkpoint` are `broker.operation`. This replaces the sentence of Amendment 2026-10-31 that a `broker.operation` receipt in a three-key frame is `DENY=binding`; a receipt whose purpose is not the one the action implies is still `binding`. Any other action in this form is `DENY=action_mismatch`.
- **DTO.** For the two new actions `args` is exactly `{vmId, expectedGeneration}`: `vmId` a lowercase GUID that is the configured VM of the DTO's computer, `expectedGeneration` an integer >= 1. Any other shape is `DENY=action_invalid`. `task.start` keeps its `{task}` or `{task, vmId, expectedGeneration}` form.
- **Extra checks, after the existing ones and inside the claim's transaction.** The computer is configured (`DENY=vm_unknown`). Where the DTO names a VM (always for the two new actions, optionally for `task.start`): `vmId` is the computer's configured VM (`vm_mismatch`) and `expectedGeneration` equals `vm_state.generation` (`vm_generation`). For `task.start` this tightens Amendment 2026-11-03: a claim naming another VM used to be recorded and only made no lease; it is now denied, because the claim also moves `vm_state`. Then per action:
  - `task.start`: `state` is `ready` (`vm_state`). For a receipt with `basis` `policy` the `checkpoints` row of the receipt's `operationId` must exist, be `attested`, and have this `vmId` and generation, `action_digest` equal to the receipt's `actionDigest` and `statement_digest` equal to its `attestationDigest` (`attestation`). A receipt with `basis` `presence` (a person approved it) needs no row. When a row matches, it becomes `claimed` and `restorable` becomes 1; when none matches, `restorable` becomes 0, because the latest task then has no checkpoint. (A presence receipt matches on operation, VM, generation and `action_digest`; it has no `attestationDigest` to compare.) The desktop lease is granted as before, then the prune of K4 runs after the reply.
  - `environment.restore_checkpoint`: `state` is `ready` or `fenced` and `restorable` is 1 (`no_checkpoint`). The transition is S3 below.
  - `environment.start`: `state` is `ready`. The worker powers the VM on; for a receipt with `basis` `policy` it first reads the network again and powers on only if it is `none` (the Broker does not remember network statements, so it does not compare `attestationDigest`; the execution-time read is the check, see L5).
- **Reply.** The claim's reply names the action and, for a first claim, always says `UNKNOWN`: it means "recorded", never "done". The wire stays `{"ok":true,"state":...,"action":...}` (plus `"replayed":true` for an exact duplicate).
- **States.** `Journal.RecordedStates` becomes `UNKNOWN`, `APPLIED`, `NOT_APPLIED`. Only the Broker's worker moves a claim, once, from `UNKNOWN` to `APPLIED` or `NOT_APPLIED`, in the same transaction as the change it describes; a final state never changes again. `task.start` and `synthetic.noop` claims stay `UNKNOWN`: nothing executes for them. An exact replay answers the recorded state. The receipt-less `inspect` answers any of the three and still names `synthetic.inspect`; the Node client (PR5) must accept the two new words.
- **Not changed:** the claim pipe's frame, bounds, key sets, signature and receipt checks, single-use challenges, the clock fence and the exact-duplicate rule.

### Journal v4

Forward-only migration, like v3: `PRAGMA user_version` goes 3 to 4 in the same transaction as the two new tables. A v4 journal opened by an older Broker is "newer" and refused (exit 76); a journal whose version or table text is not exactly one the Broker knows is refused with exit 76 before the pipe exists, as now. There is no downgrade.

```sql
CREATE TABLE vm_state (computer_id TEXT PRIMARY KEY, vm_id TEXT NOT NULL CHECK(length(vm_id) = 36), generation INTEGER NOT NULL CHECK(generation >= 1), state TEXT NOT NULL CHECK(state IN ('ready', 'restoring', 'fenced')), restorable INTEGER NOT NULL CHECK(restorable IN (0, 1)), CHECK(NOT (state = 'restoring' AND restorable = 1)))
CREATE TABLE checkpoints (snapshot_id TEXT PRIMARY KEY CHECK(length(snapshot_id) = 36), computer_id TEXT NOT NULL, vm_id TEXT NOT NULL CHECK(length(vm_id) = 36), generation INTEGER NOT NULL CHECK(generation >= 1), operation_id TEXT NOT NULL UNIQUE, action_digest TEXT NOT NULL CHECK(length(action_digest) = 71), statement_digest TEXT CHECK(statement_digest IS NULL OR length(statement_digest) = 71), created_at INTEGER NOT NULL CHECK(created_at >= 0), state TEXT NOT NULL CHECK(state IN ('attested', 'claimed', 'applied', 'destroyed')))
```

| Table / column | Meaning |
|---|---|
| `vm_state` | one row per configured computer: the VM it is bound to, its generation, its state, and whether a restore would be accepted now (`restorable`). `restorable` is stored, not derived, because "the latest task has no checkpoint" is not visible in the ledger alone. |
| `checkpoints` | the ledger of snapshots the Broker made (K3). `snapshot_id` is the Hyper-V snapshot id (a lowercase GUID). `generation` is the VM generation when it was taken. `operation_id` is the task start it was taken for (one checkpoint per operation). `action_digest` is the action digest it is bound to; `statement_digest` is the digest of the newest statement signed for it (NULL until one is signed, so a row nobody can claim). `state`: `attested` (taken, not claimed), `claimed` (its task start was claimed), `applied` (a restore went back to it), `destroyed` (the snapshot is gone). |
| `claims.state` | the table text of `claims` does not change (it has no CHECK, and SQLite cannot add one without rebuilding the table). The code accepts `APPLIED` and `NOT_APPLIED` besides `UNKNOWN`; a row with any other value still reads as no record. |

At every start, in the same transaction as the epoch bump (`BeginEpochAsync`): for each configured computer, a missing `vm_state` row is inserted (generation 1, `ready`, `restorable` 0); a row whose `vm_id` differs from the configured `vmId` gets the new `vm_id`, generation + 1, `ready`, `restorable` 0 (the old ledger rows keep their old `vm_id`, so no restore can select them); a row in `restoring` becomes `fenced` with `restorable` 1 (S6). Rows of computers no longer in the config are left alone. A configured `generation` (the lease generation floor) is a different thing and is unaffected.

### Generation: who owns it

The VM generation is owned by the Broker's journal (`vm_state.generation`) and by nothing else. It says which incarnation of the VM's content a request is about. It only goes up, by one, in exactly two cases: the configured `vmId` of a computer changed (found at start), and a restore claim is accepted (S3, in the same transaction as `restoring` and the lease revocation). It is never taken from a request: `generation` and `expectedGeneration` in a request are only compared, and any difference is refused. The Control Plane keeps no copy it trusts: it asks `vmState` before each flow, and the room's settings stop carrying a fixed `expectedGeneration` (PR5).

Five counters share the word; they are different things:

| Counter | Owner | Meaning |
|---|---|---|
| `vm_state.generation` (new) | Broker journal | the VM's content incarnation: `expectedGeneration` in `task.start` / `environment.start` / `environment.restore_checkpoint` args, `generation` in both attestations |
| `broker_state.lease_generation` | Broker journal | the claim fence of "Receipt v2": revoked by configuring N+1 and restarting; `leaseGeneration` in receipts and attestations |
| desktop lease generation | Broker memory (`DesktopLeases`) | a per-computer counter of desktop leases; lost at every restart |
| Notes generation | Hyper-V prototype (`env-io.ps1`, same user) | the prototype's own; the production Broker has no Notes (it never calls `ModifySystemSettings`) |
| `computers.generation` | Control Plane SQLite store | the Control Plane's bookkeeping; not trusted by the Broker |

### Lease revocation

The Broker's desktop lease (Amendment 2026-11-03, "Desktop lease") ends, besides its 60-minute expiry and a newer claim for the same computer, in these cases:

| Event | Effect | Why |
|---|---|---|
| `attestTaskStart` for the computer, step 5 (before any read, before `CreateSnapshot`) | revoke the computer's lease; its `act` sessions are closed | no input may reach the VM while the checkpoint is taken or while an older task's hands still hold the lease |
| a restore claim accepted | revoke, **before** the transaction commits | if the commit then fails the lease is gone (fail closed); the next `task.start` claim makes a new one |
| a Broker start | every lease is gone (memory only, as now) | unchanged |
| a `task.start` claim | granted only if `vm_state.state` is `ready` and the claim's `expectedGeneration` (when it names one) equals `vm_state.generation` | a lease never outlives the generation it was granted for |

The desktop pipe still names no VM generation: the hands compare `vmId` only, and the lease is the gate (L7).

### Checkpoint and prune rules

- **K1 One checkpoint per attested task start,** taken by `CreateSnapshot` with the arguments above, in no other path.
- **K2 Free space.** At least 20 GiB (21474836480 bytes; Lin's proposal, the lead decides) free on the snapshot volume; below it, no statement.
- **K3 The ledger is the registry.** A snapshot is the Broker's only if it is a `checkpoints` row. Names play no role. A snapshot that has no row (a crash between `CreateSnapshot` and the ledger write, one made by hand) is an **orphan**: it is written to the log, never destroyed and never applied.
- **K4 Prune.** The Broker destroys a snapshot only when all of these hold: (a) it is in the claim path of a `task.start` receipt, after the claim's reply has been written (never in `vmState`, attest or restore); (b) the snapshot is a row of the same computer and VM, older than the row just claimed; (c) **it has no child**, read from the snapshot tree immediately before each call (the parent link is read from `Parent` of `Msvm_VirtualSystemSnapshotSettingData`; whether that is the right property or an association is NOT VERIFIED, N4); (d) one at a time, waiting for the job, and the row becomes `destroyed` only after the job ended with `ErrorCode` 0 and a re-read finds the snapshot gone; (e) never `DestroySnapshotTree`. Reason for (c): the Japanese Microsoft Learn page of `Msvm_VirtualSystemSnapshotService` says `DestroySnapshot` may, as a side effect, also destroy other snapshots that depend on it (as reported by the 2.5th-round external research of 2026-11-04, not yet re-read by the author of this text: <https://learn.microsoft.com/ja-jp/windows/win32/hyperv_v2/msvm-virtualsystemsnapshotservice>). C4 measures what it really does.
- **K5 Consequence, and a precondition for PR3.** In a linear history the previous checkpoint is the parent of the new one, so under (c) it is **not** destroyed while its successor exists: in the ordinary case nothing is pruned, the checkpoint count and the disk grow by one per task, and only K2 stops it. That is the safe direction (nothing is lost) and it contradicts the approved "keep one checkpoint". PR3 does not merge until C4 decides: **(i)** if destroying a parent provably leaves its child intact and restorable, (c) is relaxed to "its only children are checkpoints this ledger made" and this paragraph is rewritten; **(ii)** if not, either the Broker destroys the previous checkpoint at the start of attest (before `CreateSnapshot`, when it is a leaf; this lets the Control Plane trigger the deletion without an Authority receipt, which worsens L1) or growth is accepted and bounded. The choice is the lead's (disk budget).

### Restore: state transitions

`vm_state.state` and the claim state move only as below; each row is one transaction.

| # | From | Event | To | Effects in the same transaction |
|---|---|---|---|---|
| S1 | `ready` | `attestTaskStart` succeeded (step 9) | `ready` | insert the `checkpoints` row `attested`, only if generation and state are unchanged |
| S2 | `ready` | `task.start` claim recorded | `ready` | the matching row becomes `claimed` and `restorable` 1, or `restorable` 0 when no row matches; the lease is granted; K4 runs after the reply |
| S3 | `ready` or `fenced` | `environment.restore_checkpoint` claim accepted (`restorable` 1) | `restoring` | generation g becomes g + 1; `restorable` 0; the lease is revoked first; the claim is inserted `UNKNOWN` |
| S4 | `restoring` | the worker's `ApplySnapshot` job completed and the VM reads back Off | `ready` | the claim becomes `APPLIED`; the newest `claimed` row becomes `applied`; `restorable` 0 |
| S5 | `restoring` | the worker's call was refused before any job started (the call returned neither 0 nor 4096), or the snapshot is gone | `ready` | the claim becomes `NOT_APPLIED`; `restorable` stays 1, or becomes 0 and the row `destroyed` when the snapshot is gone |
| S6 | `restoring` | the job failed or passed its deadline, the VM did not read back Off, or the Broker restarted | `fenced` | the claim stays `UNKNOWN` (it is never resolved: the outcome is not knowable); `restorable` 1 |
| S7 | `ready` | `environment.start` claim accepted | `ready` | the claim is inserted `UNKNOWN`; the worker then sets it `APPLIED` when the VM reads back Running and `NOT_APPLIED` when its own pre-check refused before the call, and leaves it `UNKNOWN` otherwise; the Broker never retries a start |
| S8 | any | a Broker start finds a different configured `vmId` | `ready` | generation + 1, `restorable` 0, the new `vm_id` |

**The restore worker** (after S3, in the per-computer turn, deadline 240 s from its start, proposed): (1) the VM is the configured VM and the newest `claimed` row's snapshot exists among its snapshots (else S5); (2) if the VM is not Off, depending on C3: *branch X*, `ApplySnapshot` refuses a running VM, so `RequestStateChange(3)` and wait until Off; *branch Y*, `ApplySnapshot` works on a running VM, so nothing (and the row for value 3 is not added to the allowlist); (3) `ApplySnapshot` and wait for the job; (4) read the VM back: Off (S4), otherwise S6. A Production checkpoint is expected to restore to Off and stay Off (the prototype's measurement, 2026-10-31); through WMI it is NOT VERIFIED (N3, C3).

**Afterwards** the Control Plane polls `inspect` for the restore claim for up to 300 s. On `APPLIED` it sends `environment.start {vmId, expectedGeneration: g + 1}` and `attestNetwork` at generation g + 1; at the standard tier that start needs no person when the statement says `none` (D3: the restore never starts the VM by itself). On `NOT_APPLIED` the restore did not happen (`restorable` says whether it can be asked again). On `UNKNOWN` after 300 s the Control Plane reads `vmState`: `fenced` means a new person-approved restore is the repair.

### Known limits

- **L1 The Control Plane can move the restore point forward (second round, finding 1).** A compromised Control Plane can repeat attest, submit and claim; at the standard tier the Authority signs `task.start` without a person for each valid statement, so each claim makes the checkpoint of the *current* state the one `environment.restore_checkpoint` returns to, and a good state is no longer offered. What this amendment does about it: prune only in the claim path, only ledger ids, only snapshots without a child (K4), so the earlier good checkpoints stay in Hyper-V for an administrator to apply by hand, although the Broker's own restore offers only the newest; the `careful` tier and a per-action override on `task.start` make a person approve every task start, which closes it for an owner who wants that. What remains: **"restorable" is a convenience, not a safety boundary.** `environment.destroy` and `environment.purge` still ask a person at every tier and the Control Plane cannot create a statement.
- **L2 The prune is stricter than the approved "keep one checkpoint"** until C4 decides (K5).
- **L3 `projectId` in a statement is the caller's claim.** The prototype took it from the VM's Notes; the production Broker never writes Notes (no `ModifySystemSettings`), and the config binds a computer to a VM but not to a project. The Authority binds it to the action it signs; nothing at the Broker checks it. If that is not acceptable, a `projectId` in the `computers` entry is the smallest fix (the lead decides).
- **L4 Outside the VM nothing is undone.** A restore discards the latest task's changes to the VM's disks. A push, a PR, an API call or a file on another machine is not repeated or reverted (ADR-004).
- **L5 Network statements are not remembered.** `attestNetwork` has no operation to key a ledger row on, so a start receipt's `attestationDigest` is not compared with anything. For `basis` `policy` the Broker reads the network again right before power-on and refuses unless it is `none`; a gap remains between that read and the power-on, and a person-approved start is not held to it.
- **L6 Time-of-check gaps for a host administrator.** The checkpoint type is read before `CreateSnapshot`, and the network between two reads; a member of Hyper-V Administrators or a host administrator can change either in between. They can also create, merge or delete snapshots behind the ledger (the Broker re-reads before each use and treats a missing snapshot as S5, but cannot detect a revert done by hand) and sign with the Broker's own account. All of that is outside the threat model, as for the Broker's other rights.
- **L7 The hands compare `vmId` only.** After PR5 the room's fixed generation is gone; the lease (revoked at attest and at restore) and the claim carry the generation, and the desktop pipe does not name one.
- **L8 A restore interrupted by a stop or a crash leaves `fenced`** and an `UNKNOWN` claim that is never resolved; the repair is a new person-approved restore (S3 from `fenced`). A start that was interrupted stays `UNKNOWN` and is never retried by the Broker (the Control Plane asks again with a new receipt). Orphan snapshots from an interrupted attest stay until an operator removes them (K3).
- **L9 CNG machine key ACL.** No Microsoft document was found for letting only a virtual service account (`NT SERVICE\AlberaHostBroker`) use a CNG machine key. The mechanism assumed is the usual one: the key's file under `%ProgramData%\Microsoft\Crypto` and its ACL (which subfolder holds a Microsoft Software Key Storage Provider machine key is recorded by C6). The request requires prior approval for real ACL changes and service registration, while this environment provides no separate approval for those operations. No service, account, user right, persistent ACL, named-pipe DACL, or network setting was changed. The gated Windows Runtime storage ACL integration was not invoked.
