## Latest local checkpoint — Broker dispatch fence

- The wire Broker request now accepts the same bounded opaque operation identifiers as the SQLite Journal. Its digest is `sha256:` tagged at the wire boundary while the existing database keeps its hex digest representation.
- `resolveBrokerDispatch()` reloads the operation from SQLite, validates the persisted request schema and recomputes its digest, binds the wire reference to the persisted action digest and generation, checks that the matching Lease remains active and unexpired and the Computer epoch is current, then atomically claims dispatch by changing `REQUESTED` to `UNKNOWN` before returning the journaled operation. A second claim is denied; restart after claim remains `UNKNOWN` and must reconcile. This function does not authenticate the caller and is not an IPC endpoint.
- An eight-process synchronized dispatch test initially exposed that running startup recovery in every SQLite opener would convert another live process's `REQUESTED` work to `UNKNOWN`. Store open now exposes `recoverInterruptedRequests` (default `false`). When opted in, open creates a private, exclusive per-database owner marker and holds it until store close; concurrent owners fail closed, and an existing marker is preserved rather than guessed stale. This prevents two cooperative local store processes from concurrently owning recovery, but it is not a Control Plane leader-election service. An owner recovery test verifies an interrupted pre-dispatch request becomes `UNKNOWN`; lock tests verify one owner, non-owner shared access, clean release and stale-marker preservation. There is no automatic stale-marker recovery; an operator runbook and service startup wiring remain required before deployment.

## Latest local checkpoint — typed Hyper-V adapter seam

- Added `HyperVEnvironmentProvider` as a narrow adapter contract. It accepts only the validated `hyperv` operation and dispatches to the fixed Broker client methods `createVm`, `inspectVm`, `startVm`, `stopVm`, and `removeVm`; mutation observations must match the requested Computer generation. Unknown transport/provider failures remain errors for the coordinator to classify as `UNKNOWN`.
- The adapter now captures the validated Broker method functions at construction, so replacing a method on the injected object later cannot redirect an operation; this protects the fixed-method invariant from mutable client wiring.
- Broker observations are projected onto the allowlisted observed-state fields; a synthetic secret or host path in an extra Broker response field is discarded. A synthetic error message containing credential-like text is not copied into the durable operation snapshot.
- Broker-thrown exceptions are also normalized at the adapter boundary to a bounded safe code and `unknown`/`not_applied` outcome; raw messages, paths and credential-like text do not escape through direct adapter calls. Error codes/outcomes are read only from own data properties, so an accessor exception also falls back to the generic unknown result.
- Added durable integration coverage with a synthetic Broker client: a create side effect whose reply is lost remains `UNKNOWN`, reconciles by inspect, and is never replayed; the same Journal/adapter route then verifies start, inspect and stop observations.
- This is not a Host Broker implementation: it has no IPC, authentication, process execution, PowerShell, Hyper-V API, network changes, or Runtime API wiring. The injected client is trusted by assumption; ADR-002 identity and authorization gates remain open. No Hyper-V action was run.

## Serialize mutations behind unresolved Computer operations

- Review of late Provider completion exposed a state race: after one mutation timed out to `UNKNOWN`, the same Lease could start another mutation or release capacity based on a transient `off` observation while the original Provider call might still finish later.
- `beginOperation()` now rejects a new `create`/`start`/`stop`/`destroy` for the same Computer generation while a mutation is `REQUESTED` or `UNKNOWN`. `releaseLease()` also refuses to release capacity under those conditions. Read-only `inspect` remains available for reconciliation. The guard executes inside the same SQLite transaction, so cross-process callers cannot both pass it concurrently.
- Regression coverage checks a second mutation while the first intent is only `REQUESTED`, a stop and Lease release during a timed-out delayed start, and successful reconciliation followed by stop and release. Focused SQLite tests pass 30/30; full `npm test` passes 621 total (614 passed, 7 skipped, 0 failed); `npm run arch` passes 92 role paths with 0 violations.
- The unresolved operation remains `UNKNOWN`; this guard does not cancel or prove termination of an already dispatched Provider call. Authenticated Broker serialization and provider-side fencing remain required before real execution.

## Cross-process mutation serialization verification

The unresolved-mutation guard now has synchronized separate-process regressions in addition to the in-process REQUESTED/UNKNOWN cases. Eight workers open the same SQLite journal and attempt distinct `start` operations against one Computer generation and Lease. Exactly one request is admitted; seven receive `computer_operation_unresolved`. A second race runs Lease release against a new mutation and verifies that only one can win: if mutation wins, release is denied and the Lease stays active; if release wins, mutation is denied as unauthorized. Reopening through startup recovery correctly changes an admitted but undispatched request to `UNKNOWN`. Focused SQLite tests pass 34/34.

Additional worker tests terminate the process with a nonzero exit immediately after durable intent and immediately after the journal's dispatch claim. On reopen, the intent is `UNKNOWN`, the same idempotency key resolves to the existing operation, and the claimed operation cannot be dispatched a second time. These tests cover two process-termination boundaries only; they do not simulate power loss, storage corruption, a production Broker, or a real Provider side effect.
