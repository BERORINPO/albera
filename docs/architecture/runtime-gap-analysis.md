# Runtime Gateway Architecture Gap Analysis

**Reviewed:** 2026-10-28
**Code baseline:** PR #17 base `8a829d116e39ca10f273594f409f38315f20570f` plus the PR #19 implementation branch at this review; latest code, tests, and documentation checkpoints are recorded in `runtime-implementation-progress.md`.
**Architecture baseline:** PR #18, `docs/albera-architecture-v4` at `b7684740322bda5a4e2d1233299bca251d95ed6c`
**Scope:** current implementation compared with the Proposed system design and ADRs. `IMPLEMENTED` means evidence exists for the stated, limited scope; it does not mean the Proposed end-state is production-ready.

## Executive summary

The current product is still a local, read-only Claude Code session Observer. An opt-in `albera-runtime` prototype is isolated from the Observer and offers a separately authenticated loopback approval/control surface for a host-local CLI process. It is **not** an isolated Project Computer, Host Broker, VM provider, or production service. No Hyper-V action was run or added.

The existing Runtime already implements meaningful P0 protections: fixed provider allowlisting, no caller-supplied argv, `shell: false`, canonical executable validation, bounded arguments and working-directory checks, minimized child environments, host-mediated default-deny approval, bounded lifecycle-only events, timeouts, and process-tree supervision. Claude is the only currently permitted profile; Codex and OpenCode fail closed. Tests use synthetic children. The Runtime process executes with the local user's OS identity and its working directory check is **not** an OS sandbox.

This change adds an explicit `AgentHarnessAdapter` seam for the existing Claude read-only profile, a provider-neutral environment contract, a deterministic Computer placement proposal, hard quota/resource reservations, a durable SQLite operation store/coordinator, a fault-injectable `MockEnvironmentProvider`, and transport-independent Broker/Guest message validators. The store persists identity, capacity, generation-fenced Leases, desired/observed state, idempotency and operations before provider side effects; recovery preserves uncertainty and never replays automatically. Broker references bind only to journaled operation ID, generation and action digest; immediately before provider dispatch, the store reloads and validates the operation, checks current generation and active unexpired Lease, then durably changes `REQUESTED` to `UNKNOWN` so a second dispatch is refused and a crash must reconcile. Guest events are normalized as `untrusted_guest` and sequence/generation fenced against host context. The opt-in local Control API can drive this coordinator only when an explicit environment-control composition is supplied; its bearer session is not a verified OS principal and its trusted authorization callback is not proof of human approval. Broker/Guest schema validators remain transport-independent: they do not authenticate IPC, and the Observer, default Runtime host and real Provider remain disconnected. This is a local single-host foundation, not a complete ADR-002/003/005 control plane.

### ADR-003 WAL checkpoint evidence and bound

The store now configures SQLite's per-connection automatic checkpoint threshold to 1,000 pages and exposes an explicit `checkpointWal()` maintenance call that uses `PASSIVE` mode and returns log/checkpointed/remaining frame counts. A regression opens an independent SQLite reader transaction, appends Computer journal records from the store, verifies the pinned reader retains its original snapshot while checkpoint progress is deferred, then closes the reader and confirms a later checkpoint catches up and all records remain readable. This proves the local SQLite connection behavior only; it does not simulate a separate OS process, prolonged production load, power loss, or network storage.

This is **not a hard WAL-size bound**. SQLite's documented PASSIVE behavior does not wait for readers; a sufficiently long-lived reader can keep the log from resetting and the WAL may continue to grow. The current store's own read APIs use short synchronous transactions, but there is no cross-process reader deadline, disk quota, forced-reader cancellation, or WAL-growth alert. ADR-003 acceptance item 7 therefore remains `NOT_VERIFIED` until an operational policy and sustained slow-reader/load evidence demonstrate bounded storage behavior without dropping journal entries. See [SQLite WAL checkpoint documentation](https://www.sqlite.org/wal.html).

## Design issues and alternatives

1. **System Design §17 ADR queue conflicts with the files in the same proposal.** The queue labels ADR-005 as guest identity/lease, ADR-006 as Git integration, ADR-007 as memory, ADR-008 as Canvas and ADR-009 as packaging; actual ADR-005 is Computer Pool, ADR-006 is Agent Memory, ADR-007 is Verified Integration, ADR-008 is Main AI Orchestration, ADR-009 is Canvas, and ADR-010 is Performance/OSS. Treat the numbered ADR files and the acceptance-criteria references as authoritative provisionally; correct §17 before ADR acceptance to avoid links and gate evidence pointing to the wrong decision.
2. **SQLite WAL is a reasonable proposed local single-writer baseline.** A durable store must support transactions, uniqueness, schema migration and safe backup/restore. This branch uses Node's built-in `node:sqlite` to avoid a compiled dependency and its per-user toolchain burden; Node 22.13+ is required because earlier Node 22 releases require an experimental flag, and the API's experimental status remains a compatibility risk requiring version-matrix tests and later reassessment.
3. **The `EnvironmentProvider` contract is not an authorization mechanism.** Broker-side authorization must reload trusted operation/lease state and independently validate the caller, project ownership, generation, quota and exact typed action. A provider interface must not accept arbitrary scripts, host paths or guest-supplied native IDs.
4. **Observer read-only does not imply guest isolation.** The opt-in Runtime can run a local CLI after an explicit host approval, but it executes under the local account. Do not describe that as an isolated VM or enable automatic execution of untrusted code.
5. **Startup recovery requires a single elected owner.** The store's conservative recovery changes all `REQUESTED` operations to `UNKNOWN` when a host starts. Running it in every process that opens the shared WAL can misclassify live work as interrupted. Recovery is now disabled by default; opting in creates an exclusive per-database marker held until close, and competing owners fail closed. An existing marker is never automatically reclaimed, including after a crash; an operator must establish the former owner is stopped before removing it. This is only a local cooperative-process latch, not service leader election. Startup wiring, a safe operator recovery runbook and fault tests remain required before deployment.

## Follow-up review — provider response reflection failures

The latest PR #19 code review found that `HyperVEnvironmentProvider` sanitized exceptions thrown by Broker methods, but called `validateObservedEnvironment()` outside that boundary. A Broker response implemented as a hostile JavaScript `Proxy` could throw from `getPrototypeOf` or another reflection trap; its raw exception message could then escape and reach the operation coordinator. Although a wire JSON decoder cannot directly encode a Proxy, this adapter accepts an injected Broker client and must treat its return value as untrusted.

The adapter now catches failures while validating Broker observations and raises the fixed `invalid_provider_observation` code with `unknown` outcome. A regression test injects a Proxy whose reflection trap throws a credential-like message and verifies the message does not escape. The focused provider suite passes 18/18. This hardens the in-process adapter boundary only; it does not authenticate or implement IPC.

The durable coordinator also has a delayed-Mock regression: an action completing after the configured deadline remains `UNKNOWN`, is resolved by a later inspection, and an idempotent replay does not invoke the mutation twice. The focused SQLite suite passes 30/30 and the full local suite passes 614 with 7 platform skips.

## Follow-up review — serialize unresolved Provider mutations

The delayed-completion test exposed an additional journal race: while a dispatched mutation remained `UNKNOWN`, the same Computer generation could accept a different mutation and could release its Lease using a temporary `off` observation. A timed-out Provider call may still complete later, so those paths could overlap a start/stop or release capacity before execution has converged.

`SqliteEnvironmentOperationStore.beginOperation()` now rejects new `create`, `start`, `stop`, or `destroy` intents while that Computer generation has a mutating operation in `REQUESTED` or `UNKNOWN`. `releaseLease()` applies the same guard; `inspect` remains available for reconciliation. Both checks run inside SQLite transactions. Tests cover the pre-dispatch `REQUESTED` window, a delayed timed-out `start`, refusal of a concurrent `stop` and lease release, then successful inspection, stop, and release after resolution. Focused SQLite tests pass 30/30; full local tests pass 614 with 7 platform skips and `npm run arch` reports 92 paths / 0 violations.

This serializes host journal decisions only. It does not cancel an in-flight Provider call or establish authenticated Broker-side exclusion. If an operation remains `UNKNOWN`, its Lease/capacity remains reserved and additional mutation is refused until state can be reconciled. Real-provider fencing and termination proof remain unimplemented.

The Architecture Draft's `acceptance-criteria.json` was read from `docs/albera-architecture-v4`. It contains 18 criteria, and all 18 remain `NOT_VERIFIED` by design: local tests cover portions of SEC-01/02, DUR-01/02 and CMP-02, but do not provide the required end-to-end host/guest, restore, tenant-isolation, orchestration, Git-promotion, UI ownership or fixed-machine performance evidence. No criterion should be promoted based on this PR.

## Broker IPC design findings (proposal only; ADR-002 remains Proposed)

The current Microsoft documentation supports a Windows-specific candidate, but does not remove the repository's open service-identity and privilege decisions:

1. Use a dedicated Windows service identity for the low-privilege Control Plane and a separate, least-privilege Host Broker service identity. Do not run either as LocalSystem by default. The Broker pipe DACL should admit only the Control Plane service SID, with a logon/session SID restriction if multiple interactive sessions are supported. This assumes the Control Plane is actually hosted under a dedicated service identity; an interactive process or same-user capability does not provide equivalent isolation.
2. Create the named pipe with an explicit security descriptor. Do not accept Windows' default pipe DACL: Microsoft documents broad read access for Everyone and Anonymous in the default descriptor. Avoid broad `GENERIC_WRITE` grants because the documented FILE_APPEND_DATA / FILE_CREATE_PIPE_INSTANCE alias can grant pipe-instance creation authority. Prefer the minimum individual access rights and reject remote pipe clients.
3. After connection, bind the request to the OS client token using named-pipe client impersonation at identification level, read the SID, compare it with the configured Control Plane service SID, and always revert. Any impersonation/token-query failure must fail closed; Microsoft warns that failed impersonation leaves subsequent work running as the server process identity. If reverting fails, terminate the Broker rather than continue in an unexpected thread token. Only then reload the exact operation, Lease, policy version, generation and action digest from trusted storage. Never trust a wire `subjectId` or approval claim.
4. Keep the RPC schema action-specific and bounded. The Broker should map typed lifecycle operations to fixed native calls; no generic PowerShell, shell, host path, executable name, credentials or provider-native ID from the caller. Do not hold client impersonation while performing Broker-owned provider actions; explicitly restore the service identity first.
5. This is Windows-specific and does not solve macOS/Linux peer authentication. A cross-platform Broker needs per-OS authenticated transports and equivalent negative tests, not an unauthenticated TCP fallback.

## Follow-up — hostile reflection at typed boundaries

`boundary-protocols.mjs` previously performed prototype/symbol/property-descriptor inspection directly. If a caller supplied a JavaScript Proxy from an injected in-process transport or test harness, a reflection trap could throw an arbitrary exception through the schema validator. The validators now convert any such failure into the fixed schema-specific `BoundaryProtocolError`; Guest event-type probing is also guarded. A regression injects a credential-like exception from both `getPrototypeOf` and `ownKeys` and verifies that only `invalid_broker_request` / `invalid_guest_event` escapes. A second audit found that Guest intake read `error.code` directly when projecting a Store error; it now reads a guarded own data descriptor and permits only fixed Store codes. A throwing `getOwnPropertyDescriptor` regression proves the intake returns `guest_event_store_unavailable` without exception text. These changes protect local parsing/error-projection seams only; they do not provide transport authentication, IPC isolation, or security against a compromised process sharing memory.

The Hyper-V provider constructor now also snapshots and validates the Broker method descriptors in one guarded reflection pass. Hostile Broker client proxies with throwing `getPrototypeOf` or `ownKeys` traps are rejected with the stable `invalid_hyperv_broker_client` error before method capture. The regression does not turn the injected client into an authenticated or privileged boundary.

The same review found direct `error.code` reads in the Runtime API's Gateway/environment error projection and the opt-in environment Control Plane. These paths now read guarded own data descriptors, allowlist codes, and fall back to fixed generic responses. The API regression confirms a Proxy getter trap yields `runtime_error`; Control Plane execute and reconcile regressions yield `operation_unavailable`. Internal `ApiError` projection is guarded as well. This prevents in-process exception reflection from breaking safe error projection; it still does not supply a trusted principal, policy service, or authenticated transport.

## Follow-up review — restore marker check/create race

The restore-incomplete marker was checked near the start of a normal Store open, before the destination file was opened. Because restore starts from an absent destination, a normal opener could observe no marker, then race with restore installing the marker and copying its snapshot before the opener reached SQLite initialization. The original check therefore did not prove that a normal opener had avoided a destination currently quarantined by restore.

`openSqliteEnvironmentStore()` now checks the marker again after opening and identity-checking the database file, before setting SQLite modes, migrating schema, running recovery or returning a Store. If restore wins the race and creates its marker after the first check, the open fails with `restore_incomplete_marker_present`; the common error path closes the handle and preserves both marker and database bytes. A deterministic injected `DatabaseImpl` regression creates the marker after the first check and confirms the opener refuses the DB before setting its schema version. A competing normal opener can also create the absent destination after restore's initial check; when the exclusive copy returns `EEXIST`, restore now releases only its verified marker and leaves the existing destination bytes intact. A barrier test injects that ordering. A separate fault injection fails event insertion partway through restore invalidation and verifies SQLite rolls back the operation status, Computer generation and Lease state together while retaining the marker. The focused SQLite suite passes 41/41; full local tests pass 630 with 8 platform skips, `npm run arch` reports 92 paths / 0 violations, Observer smoke and package smoke pass, and the gated Windows ACL suite passes 11/11. Actions run `40634002028` passed all six Windows/macOS/Linux × Node 22/24 jobs on code/test head `e5c4c05`, including both real Windows ACL integration jobs. These tests close the covered local check/copy races and verify transaction rollback under the injected failure; they are not evidence of OS power-loss durability, cross-host coordination, or authenticated service ownership.

## Follow-up — scoped Guest event-ingress capability prototype

`src/runtime/guest-session-capability.mjs` adds an in-memory, 256-bit random bearer capability scoped to one Host-resolved Computer/Run/generation. `SqliteEnvironmentOperationStore.resolveActiveGuestSessionContext()` resolves only a current-generation, active, unexpired Lease and returns the minimal scope. The trusted resolver must return that context; the credential expires at the earlier of five minutes or Lease expiry, and the service refuses TTLs above fifteen minutes or pools above 10,000 entries (default cap: 1,024). Only a SHA-256 digest is retained in the service map. Re-issuing for the same Computer/Run replaces the old credential; failed Host resolution, generation change, expiry, close or process restart makes it unusable. Its only consumer is Guest event intake, where event data remains `untrusted_guest`; it grants no Control API, Broker, Provider, filesystem or process authority.

Eight focused capability tests plus three SQLite integration regressions cover active/expired/revoked Lease resolution, database generation fencing, expiry, identity mismatch, bounded capacity, exact transport shape/accessor refusal, renewal, shutdown races, and acceptance into the real SQLite Guest-event journal without completing a Host operation. Focused capability + SQLite suites pass 84/84; the full suite after this prototype passes 683 / skips 8 / fails 0; `npm run arch` reports 95 paths / 0 violations; `npm run smoke`, `npm run package:smoke` and `git diff --check` pass. No external dependency or HTTP endpoint was added.

This is a local credential contract, not the ADR-002 Guest Session endpoint: it has no protected bootstrap/enrollment, TLS or channel binding, persisted credential revocation, independent peer attestation, OS service boundary, Hyper-V restore callback or IPv4/IPv6 egress controls. Because credentials are memory-only, Host service restart intentionally invalidates all sessions. Compromised Guests can still forge claims while holding the scoped token, and those claims remain provisional. ADR-002 stays PARTIAL and all related acceptance criteria remain NOT_VERIFIED.
