# Runtime Gateway Architecture Gap Analysis

**Reviewed:** 2026-10-28
**Code baseline:** `codex/runtime-event-subscription` at `8a829d116e39ca10f273594f409f38315f20570f` (worktree snapshot; PR #17)
**Architecture baseline:** PR #18, `docs/albera-architecture-v4` at `b7684740322bda5a4e2d1233299bca251d95ed6c`
**Scope:** current implementation compared with the Proposed system design and ADRs. `IMPLEMENTED` means evidence exists for the stated, limited scope; it does not mean the Proposed end-state is production-ready.

## Executive summary

The current product is still a local, read-only Claude Code session Observer. An opt-in `albera-runtime` prototype is isolated from the Observer and offers a separately authenticated loopback approval/control surface for a host-local CLI process. It is **not** an isolated Project Computer, Host Broker, VM provider, or production service. No Hyper-V action was run or added.

The existing Runtime already implements meaningful P0 protections: fixed provider allowlisting, no caller-supplied argv, `shell: false`, canonical executable validation, bounded arguments and working-directory checks, minimized child environments, host-mediated default-deny approval, bounded lifecycle-only events, timeouts, and process-tree supervision. Claude is the only currently permitted profile; Codex and OpenCode fail closed. Tests use synthetic children. The Runtime process executes with the local user's OS identity and its working directory check is **not** an OS sandbox.

This change adds an explicit `AgentHarnessAdapter` seam for the existing Claude read-only profile, a provider-neutral environment contract, an in-memory operation coordinator, and a fault-injectable `MockEnvironmentProvider`. They exercise IDs, strict typed inputs, idempotency, desired/observed state, generation fencing and `UNKNOWN` reconciliation without connecting to HTTP, the Observer, a CLI or a host-management API. This harness is explicitly non-durable and does not satisfy ADR-003 production persistence.

## Design issues and alternatives

1. **System Design §17 ADR queue conflicts with the files in the same proposal.** The queue labels ADR-005 as guest identity/lease, ADR-006 as Git integration, ADR-007 as memory, ADR-008 as Canvas and ADR-009 as packaging; actual ADR-005 is Computer Pool, ADR-006 is Agent Memory, ADR-007 is Verified Integration, ADR-008 is Main AI Orchestration, ADR-009 is Canvas, and ADR-010 is Performance/OSS. Treat the numbered ADR files and the acceptance-criteria references as authoritative provisionally; correct §17 before ADR acceptance to avoid links and gate evidence pointing to the wrong decision.
2. **SQLite WAL is a reasonable proposed local single-writer baseline, not yet an implementation choice.** A durable store must support transactions, uniqueness, schema migration and safe backup/restore. Avoid native SQLite dependencies until the Node 22/24 Windows/macOS/Linux lifecycle and supply-chain matrix is established. The current test-only in-memory harness is intentionally not a substitute.
3. **The `EnvironmentProvider` contract is not an authorization mechanism.** Broker-side authorization must reload trusted operation/lease state and independently validate the caller, project ownership, generation, quota and exact typed action. A provider interface must not accept arbitrary scripts, host paths or guest-supplied native IDs.
4. **Observer read-only does not imply guest isolation.** The opt-in Runtime can run a local CLI after an explicit host approval, but it executes under the local account. Do not describe that as an isolated VM or enable automatic execution of untrusted code.
