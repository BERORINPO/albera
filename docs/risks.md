# ALBERA Technical and Security Risks

| ID | Risk | Impact | Mitigation / next action | Status |
|---|---|---|---|---|
| R-01 | No approval UI or production Runtime host exists yet; an isolated scoped-token loopback API prototype and in-process approval queue are not wired into the product | A host that accepts caller-controlled approval data could launch or stop processes | Gateway defaults to deny. The approval broker accepts only its own one-use host decisions and does not publish a decision route. Keep runtime modules disconnected from the app until a trusted UI path, OS process ownership and persistence recovery are reviewed | OPEN; approval-queue prototype only |
| R-02 | Gateway child process runs under the current OS user's privileges; working-directory allowlisting is not a filesystem sandbox | Agent CLI may access/change files outside selected working directory | Do not expose Runtime API until OS sandbox/policy design is approved and tested per platform | OPEN |
| R-03 | PATH resolver canonicalizes and checks executable type/permission but does not attest vendor identity or prevent replacement between validation and spawn | An unexpected or swapped binary may execute as the current user | Host approval includes the canonical path; define signature/ownership and TOCTOU policy before user-facing provider integration | OPEN |
| R-04 | Windows `.cmd`/`.bat` launch is unsupported | npm-installed CLI shims may not start on Windows | Reject shims and accept `.exe` only; never enable `shell:true`; design a separately reviewed fixed adapter if needed | MITIGATED; capability deferred |
| R-05 | POSIX process groups and Windows `taskkill /T /F` differ in ownership and descendant cleanup; Windows stop is forceful; Guardian failure, breakaway descendants and PID reuse remain possible | A Gateway crash is covered by a local guardian on the default spawn path, but a guardian failure or process-ID race could still leave or signal the wrong process | Parent-pipe EOF triggers process-tree cleanup; cross-platform helper-process tests passed in Actions run 40465366567. Keep explicit host approval and the disconnected API boundary; use native process handles/Job Objects and stronger platform containment before persistent hosting | OPEN |
| R-06 | Runtime API restart recovery is journal-backed and conservative, but it cannot restore active processes or guarantee capture of the last event before a crash | Events may be missed between polls; unfinished accepted runs become `interrupted`, and in-flight processes rely on Guardian cleanup | Keep host integration disabled; retain the allowlisted event journal and interrupted-state recovery; add platform crash/restart tests, explicit recovery UX, retention/backup policy and Guardian hardening before persistent hosting | OPEN; partial recovery verified |
| R-07 | Only Claude Code has a generated read-only profile; Codex and OpenCode are refused until external tool/configuration side effects can be excluded | An unverified CLI flag or inherited tool configuration could enable file, shell, MCP or network actions | Generate fixed Claude `--restricted --safe-mode --disallowedTools mcp__*` argv inside the Gateway; reject raw request argv; fail closed for Codex and OpenCode. Organization-managed Claude settings remain trusted host policy. Confirm actual Claude CLI version and behavior before Phase 3; no real provider invocation is claimed | Mitigated at generated profile boundary; real CLI compatibility and managed policy review remain open |
| R-08 | Lifecycle events omit stdout/stderr; journaled events contain only allowlisted state metadata | Limited debugging and no transcript recovery | Continue omitting process output by default; consider bounded provider-aware parsing only after separate threat-model and redaction review | OPEN |
| R-09 | No CPU or memory quota; only active-run count and duration are bounded | A child can consume excessive local resources within its allowed runtime | Evaluate platform-native quotas before public Runtime API and state this limitation in user-facing launch approval | OPEN |
| R-10 | AI CLI account configuration may use paid APIs or transmit prompts externally; the new follow-up input path can send additional approved text | Cost and confidentiality exposure | Do not launch real providers until the host approval UI shows exact prompt/input text, provider account/endpoint, and cost implications and the user opts in. Input defaults to denied; no real provider is invoked by tests | OPEN |
| R-11 | Runtime API bearer credentials are local capabilities over unencrypted loopback HTTP | A process that obtains a session token can use its granted scopes; privileged local packet inspection may observe it | Mint random per-session scoped tokens in memory with expiry/revocation, bind IPv4 loopback only, enforce Host/Origin, return no CORS permission, never persist/log tokens, and keep API out of app startup until an explicit host design is reviewed | OPEN |
| R-12 | The optional audit/event journal is local JSONL with a single-writer lock, finite capacity, and no encryption | Disk loss, corruption, capacity exhaustion, or weak inherited directory permissions can prevent audit/recovery or expose run metadata | Use a user-private directory; never store prompts, paths, argv, tokens, environment or output; any journal write failure permanently disables the API and shuts down the Gateway. Recovery/backup and Windows ACL review are still required before persistent hosting | OPEN |
