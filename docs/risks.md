# ALBERA Technical and Security Risks

| ID | Risk | Impact | Mitigation / next action | Status |
|---|---|---|---|---|
| R-01 | A separate local approval host now exists, but it is not integrated with the read-only Observer or a signed/packaged production launcher | A local process that can observe the one-time terminal bootstrap code can access the local host UI; loopback is not OS-user authentication | Gateway defaults to deny. Broker scopes stay server-side; one-time bootstrap is required, UI uses HttpOnly/SameSite cookies plus CSRF/Origin checks, and API bearer tokens never enter browser storage. Keep the independent Runtime command opt-in; add OS identity and packaged-launch review before treating it as a production boundary | OPEN; standalone host prototype only |
| R-02 | Gateway child process runs under the current OS user's privileges; working-directory allowlisting is not a filesystem sandbox | Agent CLI may access/change files outside selected working directory | The start form and each start/input approval card now explicitly disclose that the root selects only the working directory and does not restrict local access. This is a warning, not enforcement. Add tested OS sandbox/policy enforcement before broad use; keep provider starts explicitly approved and roots narrowly configured | OPEN; Japanese/English disclosure regressions passed Actions run 40506805828 across Windows/macOS/Linux × Node 22/24; OS enforcement remains absent |
| R-03 | PATH resolver does not attest vendor identity or atomically pin the image opened by the OS; path-based version probe and provider spawn retain a final replacement race | An unexpected or swapped binary may execute as the current user, including during the approved version probe | Gateway captures metadata plus SHA-256 from one open file handle, binds the digest into the immutable approval request/UI, and compares metadata+digest after approval and after the version probe. This detects in-place content changes and path replacement present at those checkpoints, but Node spawn still opens by path and the hash does not prove publisher identity. Require a platform-native pinned-image launcher or an equivalent tested protected-executable policy before Runtime publication/broad activation | OPEN; Issue #28 content-hash, in-place replacement and symlink/junction tests plus platform CI are tracked in the issue-specific Draft PR; final OS race and publisher authenticity remain unverified |
| R-04 | Windows `.cmd`/`.bat` launch is unsupported | npm-installed CLI shims may not start on Windows | Reject shims and accept `.exe` only; never enable `shell:true`; design a separately reviewed fixed adapter if needed | MITIGATED; capability deferred |
| R-05 | Windows Job Objects cover ordinary process descendants but do not sandbox service-delegated work; Job owner loss cannot be reconciled after the unnamed handle disappears; Windows termination is forceful | A lost acknowledgement cannot prove process death or safely release a Lease; some host policies can reject nested Job assignment | Windows x64 launches use the self-contained .NET 10 Job Guardian: CREATE_SUSPENDED → AssignProcessToJobObject → ResumeThread, with breakaway disabled and kill-on-job-close. It reports confirmed only after JobObjectBasicAccountingInformation.ActiveProcesses reaches zero. Job-managed runs never use PID fallback; taskkill remains cleanup-only and unconfirmed. Guardian loss triggers kernel cleanup on handle close but leaves API state unknown. POSIX group confirmation remains separate. Keep Runtime publication disabled; test service/outer-job policy combinations and external-service process creation before broader activation | OPEN; local synthetic Windows x64 integration verifies child/grandchild drain, root-exit cleanup, breakaway denial, and owner-loss cleanup without confirmation. Windows Node 22/24 CI pending; service identity, host policy combinations, kill-failure injection and durable reconciliation remain unverified |
| R-06 | Runtime host reuses a journal-specific session ID from a mode-restricted sidecar, but it cannot restore active processes or guarantee the final record across a crash during a write/flush | A hard host/system crash can leave a partial or non-durable tail; startup preserves and refuses an incomplete journal. Unfinished accepted runs become `interrupted`; active recovery remains unavailable | Journal append writes the complete record and synchronously calls `fsync` before returning its Promise. Notification capture starts in the same event turn; periodic polling remains a backstop. Offline `recover-tail` copies only the validated complete-record prefix to a new file while holding the normal writer lock; it preserves the source and tail and does not claim to recover a possibly lost final event. Keep active-process recovery unclaimed; the approval UI labels recovered runs interrupted and warns that the provider process may still be running, with manual process verification required before equivalent work is restarted. Add retention/backup policy and Guardian hardening before persistent hosting | OPEN; sync-before-return and non-destructive prefix recovery are unit-tested; crash during write/flush and active-process recovery remain unresolved |
| R-07 | Only Claude Code has a generated read-only profile; Codex and OpenCode are refused until external tool/configuration side effects can be excluded | An unverified CLI flag or inherited tool configuration could enable file, shell, MCP or network actions | Generate fixed Claude `--restricted --safe-mode --disallowedTools mcp__*` argv inside the Gateway; reject raw request argv; fail closed for Codex and OpenCode. After explicit approval, verify the reported CLI version against 2.1.248 (`--restricted`) or 2.1.259 (streaming `--permission-prompts none`) using a bounded credential-free probe, and revalidate executable identity. Organization-managed settings remain trusted host policy. A sufficient version alone is not a safety certification | OPEN; approved version preflight now enforces documented minima; installed managed policy and runtime behavior remain unverified |
| R-08 | Lifecycle events omit stdout/stderr; journaled events contain only allowlisted state metadata | Limited debugging and no transcript recovery | Continue omitting process output by default; consider bounded provider-aware parsing only after separate threat-model and redaction review | OPEN |
| R-09 | No CPU or memory quota; only active-run count and duration are bounded | A child can consume excessive local resources within its allowed runtime | Evaluate platform-native quotas before public Runtime API and state this limitation in user-facing launch approval | OPEN |
| R-10 | AI CLI account configuration may use paid APIs or transmit prompts externally; the follow-up input path can send additional approved text | Cost and confidentiality exposure | Before approval, the Japanese/English screen warns that approved text may be sent externally and may incur charges; the same warning appears on each start/input approval card. The screen still cannot identify the configured account or estimate cost, and no real provider is invoked by tests. Require per-action approval and keep account/cost discovery open | OPEN; disclosure code-tested only, account/cost discovery unavailable |
| R-11 | Runtime API bearer credentials are local capabilities over unencrypted loopback HTTP; the browser-facing host additionally relies on a one-time terminal bootstrap code and HttpOnly session | Privileged local packet inspection or a process that observes the terminal code can obtain local control; loopback does not authenticate OS users | Keep API bearer token server-side, revoke it as soon as the approval host closes (even if the API remains open briefly for trusted shutdown), issue one-use bootstrap, use a 20-minute idle cookie session with an eight-hour absolute cap, enforce Host/Origin/CSRF, no CORS, and never persist tokens. Review TLS/local OS identity or platform-native app authentication before broader deployment | OPEN; shutdown revocation regression passed Actions run 40569501575 across Windows/macOS/Linux × Node 22/24; OS-user authentication and local loopback trust remain unimplemented |
| R-12 | The optional audit/event journal is local JSONL with a single-writer lock, finite capacity, no automatic pruning; the live journal is unencrypted, with offline encrypted manual backups | Disk loss, corruption, capacity exhaustion, unsafe ownership/permissions, hard links, or full-file replacement can prevent audit/recovery, expose metadata, or modify an unrelated linked file | Never store prompts, paths, argv, tokens, environment or output; any journal write failure permanently disables the API and shuts down the Gateway. Capacity rejection preserves earlier bytes. Windows DACL, POSIX owner/mode, and single-link checks fail closed without repairing existing storage; backup output parent and handle-identified file are checked before ciphertext is written; Windows ACL validation is pathname-based, and writable-ancestor replacement races are not fully excluded. V2 hashes detect record edits/reordering but are not keyed and cannot detect a recomputed full-file rewrite or an unanchored valid suffix truncation. Keep production key recovery, independent head anchoring, disk-loss and retention review open | OPEN; POSIX permission checks passed six-job matrix run 40484508966; hard-link refusal passed run 40485149160; v2 migration/tamper tests and all six Windows/macOS/Linux × Node 22/24 jobs passed run 40498380655; local manual backup/restore regressions and Windows real-DACL integration pass; production key recovery, independent anchoring and retention policy remain open |
| R-13 | Synchronous per-record `fsync` can block the Runtime event loop on slow or remote storage | Approval, stop requests, lifecycle capture and browser polling can stall while storage flushes | Journal records are bounded to 2 KiB and the configured journal is capacity-limited. Keep the path explicit, fail closed on errors, and measure flush latency on supported local filesystems before production hosting | OPEN; on a dedicated user-home directory accepted by the real Windows DACL guard, 100 sequential appends measured p50 0.586 ms, p95 0.723 ms, max 8.271 ms (Windows Node 24.13.0); volume/filesystem and other approved path classes remain unverified |
| R-14 | Browser cookies are not port-scoped, so a loopback cookie may be exposed to another service on the same host | A local web service could receive a browser session cookie if the operator browses to it while Runtime is authenticated | Scope the HttpOnly cookie and approval routes to a fresh 128-bit random per-process URL path as defense in depth; keep bootstrap separate, reject unscoped routes, and retain exact Host/Origin and CSRF checks. Cookie Path is not a security boundary (RFC 6265 §8.5); require OS-user authentication or stronger origin isolation before production hosting | OPEN; route/path regression coverage passed all six Windows/macOS/Linux × Node 22/24 jobs in Actions run 40503853392; local Runtime remains an explicitly untrusted same-user boundary |
| R-15 | A loopback client can hold an approval-host POST open by slowly sending an incomplete body or consume sockets with concurrent connections | A local process could consume request/socket resources, including before it has a browser session | Cap POST bodies at 20 KiB, abort incomplete bodies after a configurable bounded timeout (15 seconds by default), cap concurrent connections at 64, and bound header/request timeouts; retain loopback-only binding | MITIGATED for bounded approval-host request resources; local regressions cover body timeout and concurrent-connection refusal. This does not prevent same-user denial of service through repeated requests or resource use within the connection cap |
| R-16 | The Windows Job Guardian is launched by pathname after its manifest digest has been checked, so a replacement between handle-based hashing and process creation remains possible | A same-user writer could race the guardian image and subvert the tree-stop trust root | The publisher writes an adjacent SHA-256 manifest; Runtime hashes the executable through one opened handle and fails closed for a missing/invalid/mismatched manifest before run registration. Launch Guardian with its publish directory as cwd while passing provider cwd in the existing private protocol. A platform-native pinned-image launch or protected publish directory is still needed to close the final path-open race and authenticate the publisher | OPEN; mismatch regression added but not run in this sandbox |

### Restore input bound (2026-10-28)

The encrypted backup restore path now reads only the opened file's previously validated size and checks for concurrent growth with a one-byte probe before decrypting. This prevents an input file that grows after its initial size check from driving an unbounded `readFile()` allocation. Regression coverage and six-platform CI passed in Actions run 40538766885. This does not provide key recovery, retention, or protection against same-user replacement of a valid backup.

`albera-runtime verify-backup` now authenticates and validates a backup without writing files or starting Runtime/Provider. The passphrase is read from a hidden TTY prompt; the decrypted journal buffer is cleared after validation. Local regression and package smoke passed on Windows Node 24.13.0; Actions run 40542132165 passed all six Windows/macOS/Linux × Node 22/24 jobs, including Windows Runtime storage ACL integration. Key recovery, retention, and protection against same-user replacement remain open.

Runtime bootstrap now rechecks the one-use code state after reading the request body, so concurrent requests cannot both mint a browser session from the same code. The concurrent HTTP regression and full local suite passed on Windows Node 24.13.0; Actions run 40545485266 passed all six Windows/macOS/Linux × Node 22/24 jobs including the Windows storage ACL integration. OS-user authentication and loopback same-user boundaries remain open.
